# Quick Task 260929-p61 — The live challenge stage asks the developer

## Why

Two instrument closures landed today and both worked. `260929-lq1` fixed the stale-snapshot
decision targets and the live gate reached its own pass/fail table for the first time in twelve
rounds. `260929-nxq` fixed the question extractor — it split on a sentence boundary that a
`**bolded question?**` never reached, so it saw 1 of 5 — and made the driver refuse to advance over
a withheld consent.

Live run `01M3P9QF58AAFKXH2EAZ3ZEM65` then extracted **6 questions instead of 1**, read the
challenge → decompose consent as clear, and settled honestly after 3 agent turns. And then the
harness said this about itself, in the diagnostic `260929-nxq` had just added:

> `answer-bank fallback ratio this conversation: 6/6 composed answer line(s) were the
> wholly-generic fallback`

All six answers were one sentence, the generic delegation. The agent noticed and said so, staging
an explicit flagged assumption rather than blocking.

**Three live runs, three different failures, one shape underneath.** Round 12 indexed a stale
snapshot. This morning's run never heard the questions. This run heard them and had no answers.
Each round makes the instrument better at *detecting* that it cannot hold up its end of a product
conversation, and none of them make it able to. The questions it is failing — *"attention router or
activity log?"*, *"where does the board app actually live?"* — are genuine product questions whose
answers exist only in the developer's head. Widening the bank produces the next round.

So the live arm stops composing and starts asking.

may reach it should not sit in a shared library where a fourth script can import it by accident.

### Design decisions, argued

**1. Per-question prompting, not one editor-style block.** All extracted questions are printed
first, verbatim and numbered, so the developer sees the whole turn before answering any of it —
then one prompt per question, in order. The binding of answer *n* to question *n* is then
structural: there is nothing to parse and nothing to mis-align. A single editor block requires
parsing numbered lines back into a list, and a silent mis-alignment there is precisely the class of
defect this wave keeps producing — an instrument that looks clean and reports the wrong thing.

**2. No-TTY is the primary path, not the edge case.** The developer runs this gate backgrounded, so
`process.stdin.isTTY` will be falsy on the real run. The no-TTY transport therefore has to *work*,
not merely fail politely: the source writes a **per-turn questions sheet** to the evidence directory
(carrying the run id, the turn number, the verbatim questions, and one `ANSWER n:` line per
question), logs its path through `step()` into the scrollback the developer is already watching,
and polls for the matching per-turn answers file until a bounded deadline. Filenames carry the turn
number so turn 2 can never consume turn 1's stale answers.

**3. Fail fast with a named reason, and never fall back.** The answer bank becomes unreachable from
the live arm entirely. A deadline with no answers file, a malformed answers file, or an empty answer
for any single question is a named error thrown out of the source — which `driveChallengeConversation`'s
existing `catch` converts to a `ConversationAbortedError` carrying every exchange captured so far,
and the live body's `finally` still writes the evidence sheet. A run that did not get the
developer's answers cannot report clean, because it cannot reach the verdict at all. An empty answer
is a failure rather than a delegation on purpose: a developer who genuinely wants to delegate can
*type* that delegation, and typing it makes it his answer. A blank line is the absence of one.

**4. A malformed file keeps polling; only the deadline fails.** The developer is editing this file
by hand while the run waits, so a half-saved file must not kill the run. The parse defect is logged
(once per distinct message) and polling continues; at the deadline the error carries the **last
parse defect** as its named reason, so the scrollback says what was actually wrong with the file
rather than only that time ran out.

**5. The fallback-ratio diagnostic becomes a live-arm failure.** Keep the `step()` narration exactly
as `260929-nxq` wrote it — it is honest and the offline arms legitimately use the bank. But in the
live arm, a conversation whose every answer line was the generic fallback is now a named failure.
Under this change the live arm structurally cannot reach the bank, so this gate can only fire if a
future edit reconnects it: it is a tripwire on the exact regression this plan prevents, which is
worth more than the same sentence printed and ignored.

**6. The guard is structural in two independent ways.** `assertLiveArm(argv)` refuses construction
when any offline flag is present (runtime, parameterised so the self-test drives each flag without
mutating `process.argv`), *and* a source scan proves the two offline arms that perform real I/O hold
zero call sites while the live body holds exactly one. Stated precisely and without overclaiming:
`--self-test` reaches the factory only by explicitly handing it a fabricated live-shaped argv, and
its own real argv is refused — which the checks assert directly.

## Threat model

| Boundary | Description |
|---|---|
| developer stdin / handoff file → agent conversation | free text authored by the developer is sent verbatim as a turn to a live model session |
| filesystem → harness | the handoff answers file is read from a path the harness chose, inside the evidence directory |

### STRIDE register

| Threat ID | Category | Component | Severity | Disposition | Mitigation |
|---|---|---|---|---|---|
| T-p61-01 | Spoofing | the answer source | high | mitigate | A live run's answers must carry the developer provenance value or the run fails with a named error before any advance-stage — the bank cannot stand in for him (Task 2's provenance gate). |
| T-p61-02 | Tampering | stale handoff answers file | medium | mitigate | Per-turn filenames embed the turn number, so turn N cannot consume turn N-1's file; a dedicated self-test check asserts two successive calls write different names (Task 2). |
| T-p61-03 | Denial of Service | a backgrounded run with no answerer | medium | mitigate | A bounded per-turn deadline throws a named error carrying the last parse defect; the driver's `catch` preserves the exchanges and the live `finally` still writes the evidence sheet (Task 1). |
| T-p61-04 | Elevation of Privilege | an offline arm reaching the prompt | high | mitigate | Refused at construction by argv for each of the three flags, and a source scan proves the two I/O-performing offline arms hold zero call sites while the live body holds exactly one (Tasks 1 and 2). |
| T-p61-05 | Information disclosure | handoff files on disk | low | accept | The files hold the agent's own questions and the developer's own answers, written under the evidence directory that already holds the full verbatim transcript. No new class of content. |
| T-p61-SC | Tampering | package installs | low | accept | No package-manager install task exists in this plan; `node:readline` is a Node builtin. |
