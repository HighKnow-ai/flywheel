# Quick Task 261005-mn5 — The forge never overwrites a column a human just moved

## Why

Plan 07-11 fixed a real blocker: `AppState.db` is one app-wide `Mutex<Connection>` and the forge
tick used to hold it across untimed `gh`/`glab` calls, freezing the whole app. The fix was correct —
`run_forge_tick` now resolves targets under the lock, drops it, polls lock-free, then re-acquires to
write (`scheduler.rs:431` acquire, `:439` drop, `:445` poll, `:454` re-acquire).

What it opened, confirmed by direct reading at planning time: `apply_forge_observation`
(`transitions.rs:99-236`) reads its baseline from the append-only forge event log via
`latest_forge_baseline` and **never consults the task's current status as a precondition**. Its only
guard is `baseline.state != ForgeState::Merged && observed_state != baseline.state`
(`transitions.rs:134`). On an observed merge it calls
`set_task_status_in_tx(task_id, "done")` unconditionally (`:168`), and `set_task_status_in_tx`
(`task.rs:446-485`) only special-cases the current value being *equal* to the new one — never
"changed by someone else since this observation was captured".

So: task is `in_review`, baseline `Open`. The tick gathers it and drops the lock. The `gh` call takes
20s and returns `Merged`. Meanwhile the user drags the card back to `in_progress` because more work
is needed — that command acquires the now-free lock, writes, releases. The tick re-acquires, sees
`Open != Merged`, and writes `done`. The deliberate move is gone, with no event explaining it.

Before 07-11 this was impossible — but only because the user's command blocked on the mutex until
the tick finished. The race was prevented by the freeze, not by any invariant.

`forge/transitions.rs`'s own module header claims the detector is "structurally incapable of
overwriting a manual move in a loop". That claim is currently false for any manual write landing
inside the lock-release window.

### Why this matters beyond the one bug

Both BL-01 and HI-01 were found by **inspection, not by a failing test**, because
`packages/desktop/src-tauri/src/scheduler.rs` has zero coverage of the restructured tick (MED-02).
The third task below is the structurally important one: it turns "we closed the instance" into "the
property has a test".

## Decisions made at planning time

Every one of these was settled by reading the source in this worktree, not inferred.

**D1 — `expected_status: Option<&str>` as a fifth parameter, not an inferred guard.** A guard that
infers the expected status from the baseline cannot work: `merged_against_a_none_baseline_still_
reaches_done` (`status_transitions.rs:290`) proves a `None` baseline legitimately reaches `done` from
*any* status, so there is no status the detector can infer it is "transitioning from". The captured
value must be carried. `None` means "no compare-and-swap" — the honest option for a caller that held
the lock continuously from read to write and therefore has no window. `Some(s)` means "refuse the
status write unless the task is still at `s`".

**D2 — The signature change ripples to 4 files; the compiler is the gate.** Measured at planning
time: `grep -c 'apply_forge_observation('` gives 24 in `status_transitions.rs`, 5 in
`forge_live_chain.rs`, 7 in `forge_board_flags.rs`, 1 in `scheduler.rs`. Every test call site gains a
literal `, None` — a one-token mechanical edit that changes nothing those tests assert (they are all
hermetic single-threaded callers with no lock-release window). The one production call site passes
`Some(&result.status_at_poll)`. Nothing can be missed silently: a missed site is a compile error, so
`cargo test --workspace` is the real ripple gate.

**D3 — The refusal's trace is an `events` row, not a swallowed skip and not an `eprintln!`.** This
module's established discipline is exactly that: its own header says "changes requested" and "closed
without merging" are "each only ever an `events` row". A new
`EVENT_FORGE_STATUS_WRITE_SKIPPED = "forge.status_write_skipped"` row carrying a `label` is rendered
verbatim into the activity trail by `domain::event::render_description`'s label-first behaviour
(`event.rs:95`), so the user can see *why* the card did not move — strictly better than a developer-
only `eprintln!`. No new `TransitionOutcome` field: `events_appended` already fires the scheduler's
`any_changed`, so the board refreshes and the event appears.

**D4 — The state-change event is still appended on a refusal; only the status write is skipped.**
This is load-bearing and non-obvious. If the refusal also skipped the `forge.state_changed` event,
the baseline would stay `Open`, and the *next* tick 120s later would re-observe `Merged`, re-fire,
and overwrite the manual move anyway — the race would merely be deferred. Appending the event
advances the baseline to `Merged`, which is terminal, so the forge hands the column back permanently
— exactly the module header's property one.

**D5 — No migration.** Verified at planning time: `events.event_type` is declared
`event_type TEXT NOT NULL` with no CHECK constraint (`0002_board_schema.sql:124`), so a new event
type needs no schema change. Verified separately that `query/forge.rs`'s `LATEST_FORGE_EVENT_SQL`
filters on a **closed list** — `event_type IN ('forge.state_changed', 'forge.ci_failed')` — so the new
event cannot pollute the baseline. Verified there is no renderer-side event-type allowlist
(`grep -rn "forge.state_changed"` over `packages/desktop/src/**/*.ts{,x}` returns nothing), so no TS
changes and no renderer test impact.

**D6 — HI-01: correct the comment, do not restructure.** `forge_and_repo_path` claims it spawns
nothing; on its `Some(_) | None` fallback (`mod.rs:171`) it calls `detect_forge_from_origin` ->
`git_at(repo_path, ["remote","get-url","origin"])`, which spawns `git`. The claim is false twice
(module header `mod.rs:21`, fn doc `mod.rs:148`). But this is a **bounded local config read**, not a
network round-trip, so it cannot produce the app-freeze this round exists to fix; and
`forge_tick_targets` already memoises per project, so it is at most one spawn per project per tick.
Splitting the function to move detection outside the lock would change all three call sites — a
second restructure for no user-visible gain. A correct comment stating the real, weaker invariant is
the right resolution; a false one is not.

**D7 — MED-02: inline `#[cfg(test)] mod` in `scheduler.rs`, reusing the desktop crate's own two
existing conventions.** The review says "no `tests/` directory exists for that crate at all" — true,
and irrelevant: the crate is **bin-only** (no `lib.rs`, no `[lib]` in its Cargo.toml), so an external
integration test could not import `scheduler`'s private functions without adding a library target.
It does not need one. Verified live at planning time: `cargo test -p desktop` builds
`unittests src/main.rs` and already runs **41 passing inline tests** in four modules
(`commands::agent_run::tests`, `commands::settings::tests`, `sidecar::stderr_tail_tests`, and one
more). Reuse that idiom and these two existing fixture shapes verbatim rather than inventing any:
`seeded_conn_with_task` (`commands/agent_run.rs:2133-2171` — `open_and_migrate` +
`local_human_actor_id` + `create_project` + `create_task`, leaking the `TempDir` with
`std::mem::forget`) and the fixture `INSERT INTO worktrees (...)` at `commands/agent_run.rs:2497-2505`.
`tempfile` is already a dev-dependency of the desktop crate. No new file, no new Cargo target, no
`pub` churn on the scheduler's private functions.

**D8 — No fake `gh`/`glab` stub.** `forge_live_chain.rs`'s harness is ~120 lines of
shell-script-writing, PATH mutation and an env mutex, and it lives in a different crate so it cannot
be imported. Duplicating it buys nothing here: the CLI -> `ForgeRequest` path is already covered by
`forge_live_chain.rs` and `forge_normalize.rs` in core. What is uncovered is the scheduler's
*threading of the captured status across the lock-release window*, and that is what these tests
cover. Target resolution and result threading are proven with `projects.forge = 'local'`, which
`request_for_branch_at` answers `Ok(None)` for **without spawning any process at all** (`mod.rs:196`);
the merged observation is a synthetic `ForgeRequest`, and its `status_at_poll` is copied out of the
real `ForgePollTarget` that `forge_tick_targets` produced — so a scheduler that failed to capture the
status still fails the test.
