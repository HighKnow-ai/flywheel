# Quick Task 260929-lq1 — Re-read before deciding

## Why

Phase 05 has run twelve gap-closure rounds. This task exists to state a property, not to fix a
line. The failing line is a consequence of the property being unstated.

Round 12's live run (`01M3NXWP72VACQJQNVGDK7AXJ8`) crashed in the harness's own reject step. The
mechanism, re-derived by reading the source during planning rather than inherited from the gap
report:

| line (measured today) | what it does |
|---|---|
| 7613 | `const pending = runOps(..., ["list-pending", runId]);` — one snapshot |
| 7620 | `const criterionProposals = pending.proposals.filter((p) => p.targetType === "criterion");` |
| 7647 | `runOps(..., ["accept-subtree", taskProposalId])` — **mutating.** D-96's implied-parent walk plus `accept_subtree`'s own child walk decide every criterion parented to that task, in one transaction |
| 7656 | `runOps(..., ["reject-proposal", criterionProposals[1].id, ...])` — indexes into the now-stale array |

`reject_proposal` (`packages/core/src/domain/authoring_proposal.rs:756-772`) refuses a decided row
by design. The core is right; the harness pointed it at a row the harness itself had just decided.
The run died before `buildCriteriaResults` ever computed the SHAPE-01/02/03/04 table the round
existed to produce.

**This is instance two, and planning found instance three.** The comment block at lines 7610-7612
records plan 05-46 fixing the identical stale-snapshot defect at a *different* call site in round
11. That round fixed the instance and never stated the property, so it moved one call site over.
Auditing the remaining sites for this plan found a third, latent one at line 7663: `amend-criterion`
also takes its target from the same pre-cascade snapshot (`criterionProposals[0]`), and
`amend_proposal` (`authoring_proposal.rs:897-901`) refuses a decided proposal for the same reason
`reject_proposal` does. It has never fired only because the run crashes one step earlier. Fixing
line 7656 alone ships instance three into the next live run — at the cost of another credential.

## The rule this task installs

> The live UAT harness must derive every proposal-**decision** target from a `list-pending` read
> taken immediately before the deciding call, with no mutating operation in between. A proposal
> id read before an `accept-proposal`, `accept-subtree`, `reject-proposal` or `amend-criterion`
> is a fact about a board state that no longer exists.

Two boundaries, both load-bearing, both stated so the next author does not have to re-derive them:

1. **Decision targets only — not measurements.** `draftedCriteriaCount` is deliberately computed
   from the *pre-cascade* snapshot: it measures how many criteria the model drafted, which is a
   fact about the run that the cascade must not be allowed to erase. Routing it through a fresh
   read would silently collapse SHAPE-03's drafted count after every accept.
2. **`accept-proposal` is idempotent; reject and amend are terminal.**
   `accept_proposal_in_tx` (`authoring_proposal.rs:655-672`) documents an already-accepted
   proposal as a no-op returning the existing `materialised_id`. That is why the one deliberate
   stale-target call site in this file (below, site 2) is correct and must be kept.

## Decision — a helper, not an assertion at the call site

Asked to judge which fits this codebase: **a helper**, `pickPendingProposal`, placed beside
`runOps` at module level. Argued, not defaulted:

1. **An assertion still requires the author to remember.** A call-site assertion checks that the
   id you already chose is still pending — it catches the mistake after it has been made, and only
   if the author remembered to write the assertion. The helper makes the fresh read and the pick
   one indivisible operation, so a caller never holds an array across a mutation because the
   helper never hands one out. Correct sequencing becomes the path of least resistance.
2. **The database already enforces the hard half.** `list-pending` resolves through
   `pending_proposals_for_run`, whose SQL filters `status = 'pending'` server-side
   (`authoring_proposal.rs:1049-1052`). "Freshly read" and "still genuinely pending" are therefore
   the *same fact*, established by the database rather than by harness bookkeeping. The helper's
   only job is to stop the harness from separating them.
3. **It stays in the script, not `lib/`.** `uat-08` is the only script in this directory that
   speaks to the `uat_authoring_ops` bridge, and its bridge helpers (`runOps`,
   `createBoardReadHandler`, `createProposalStagedHandler`) all live in the script. A shared module
   for a single consumer would invent a seam this directory does not have.
4. **A helper alone is a convention; it is paired with a structural gate.** Task 2 adds a
   source-scanning self-test that fails if any decision call site in the live body has a mutating
   op between its pick and its decision. That is what makes the rule hard to break rather than
   merely written down.

**Rejected:** re-ordering the live block so reject and amend run *before* `accept-subtree`. It
makes this run pass without making the next one safe — the ordering constraint would still be
undocumented, unenforced, and one edit away from returning.

## Tasks

### Task 1 — The helper, and every live decision target routed through it

**files:** `scripts/uat/uat-08-socratic-authoring.mjs`

**action:**

**(a) Add `pickPendingProposal(opsBin, appDataDir, runId, { targetType, excludeIds = [] })`**
immediately after `runOps` (which ends at line 187), in the same bridge-wrapper block. It performs

`{ proposal, pendingOfType, pendingTotal }` where `proposal` is the first match or `null`. It
returns `null` rather than throwing, so each caller decides whether an absence is fatal or merely
reportable.

because a proposal id read before a mutating decision is a fact about a board state that no longer
exists (naming the round-12 crash and plan 05-46's earlier instance of the same defect as the two

pendingness are one fact from the database rather than two the harness has to reconcile; and that
it is for decision targets only, never for measurement counts, naming `draftedCriteriaCount` as the
measurement that must keep reading the pre-cascade snapshot.
