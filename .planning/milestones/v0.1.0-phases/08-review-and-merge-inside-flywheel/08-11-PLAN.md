<objective>
Close CR-01, narrowed to what 08-VERIFICATION actually confirmed. The destructive half already holds:
`run_merge`, the push and the merge event record follow the plan/run/record split and never hold the
lock (`review.rs:392`, `drop(conn)` in `forge.rs`). What does hold it: `plan_merge` (a `rev-list` plus
two `git diff` runs), `epic_request_preconditions`, `assemble_epic_request_draft` (up to three spawns
per task), and `resolve_review_target`'s `is_integrated` ancestry checks. All read-only and bounded by
a 120 s per-spawn timeout, so this is a board-freeze hazard on a slow repo, not a data-integrity bug —
WARNING, not a goal blocker. The user chose to include it.

`packages/core/src/merge.rs` lines 9-12 currently state that `plan_merge` resolves everything under a
connection and that no caller can hold the lock across a subprocess. That is untrue of the code as
written, and must be corrected once it is true.

Purpose: a slow repository can no longer freeze every other command in the app, and the module headers
stop asserting an invariant the code breaks.
Output: the DB-half/git-half split the review proposes, applied to all four holders, with the git half
taking an opaque inputs value and no connection — which makes the mistake unexpressible rather than
merely discouraged.

Depends on plan 08-09 because that plan adds a query to `packages/core/src/review.rs` and a command to
`packages/desktop/src-tauri/src/commands/review.rs`, the two files Tasks 1 and 2 here restructure. Plan
08-12 (CR-02) depends on this one for the same reason in the other direction.

Sizing note: three tasks across six files is at the upper end of one executor's comfortable budget.
Each task is a complete vertical for one path — core halves plus that path's own command call sites —
and each leaves the workspace building and green, so a context reset between tasks loses nothing.
</objective>
