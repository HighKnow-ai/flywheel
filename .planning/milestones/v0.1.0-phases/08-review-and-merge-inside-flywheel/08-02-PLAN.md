<objective>
Make a criterion check mean something: an anchor recording the file, the line range and the sha
the range was read at, with staleness derived from git and nothing ever unchecked behind the
user's back.

This is the plan behind the ROADMAP note that criterion 2 "is where the core value becomes a daily
habit rather than a slogan". `acceptance_criteria` today carries `statement`,
`verification_hint` and a bare `checked` boolean and nothing about *why*, so a check made while
reading a diff is indistinguishable afterwards from a check made blind. After this plan, the
record says which lines satisfied each criterion, at which sha, and whether that code has moved
since — and the context packet carries all three to the next session.

Purpose: three things here are easy to get wrong and expensive to discover late. The sha must be
resolved server-side or the evidence is whatever the renderer claims. Unchecking must clear the
anchor in the same transaction or a re-check silently resurrects stale evidence. And the existing
revision path already copies `checked` forward — if it does not also copy the anchor, every edit
of a locked criterion produces a row that is checked with its evidence dropped, which is a
regression of D-140 caused by D-77 and the single easiest thing in this phase to miss.

Output: migration `0018`, `check_criterion_with_anchor`, the staleness derivation, two new read
commands, the widened context packet, and two test files.
</objective>

<decisions_resolved>
- **A separate table, not new columns** (research assumption A8, confirmed by reading the call
  sites). `AcceptanceCriterion` is constructed from positional index reads in about eight
  functions; a table touches none of them, and `foreign_keys=ON` plus `ON DELETE CASCADE` makes
  the absence of a row *be* the no-evidence state with no sentinel values.
- **The event type is reused, not added.** `criterion.toggled` keeps its name and gains an
  `anchor` key in its payload, so the activity trail's existing label rendering needs no change.
- **The existing plain toggle survives.** D-140 requires that you can always just check the box;
  `toggle_criterion` keeps its behaviour, with its uncheck branch routed through the same
  anchor-clearing delete so there is exactly one way an anchor disappears.
- **Staleness is three git reads, not one.** A commit count between the recorded sha and the
  scope's head restricted to the anchored path answers the common case; a path that no longer
  exists at head, or that appears as a rename source since the sha, is stale regardless of that
  count; and a sha that no longer resolves is `Unknown`. The exact commit count is cosmetic — D-141
  only requires that stale is marked.
- **The packet asks the same function the rail asks.** `context_packet.rs` already shells git for
  the diff-so-far, so calling the staleness derivation from the packet adds no new capability and
  guarantees the agent and the human read the same verdict.
</decisions_resolved>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → `criterion_check_with_anchor` | the renderer supplies a criterion id and a line range; it supplies no sha and no actor |
| Rust core → `git` subprocess | a recorded sha and an anchored path are interpolated into a rev-list range and a pathspec |
| core → context packet → agent prompt | anchor paths and shas become text an agent reads |
