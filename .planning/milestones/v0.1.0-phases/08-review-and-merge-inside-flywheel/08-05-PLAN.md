<objective>
REVW-05 in the core: one action that turns a finished epic's integration branch into a pull or
merge request, built entirely on the Phase 7 seam.

Everything hard about this already exists. `forge::create_request_at` is connection-free and
dispatches to the installed `gh` or `glab`; `RequestDraft` already carries title, body, head
branch and target branch; the CLI error taxonomy already distinguishes not-installed from
not-authenticated from failed; and the task-scoped draft assembler already proves that a draft
assembled from the board is byte-stable. This plan adds the epic-scoped assembler, the
precondition check that stops the forge from being asked an unanswerable question, and the one
genuinely new step: a push, because the GitHub CLI pushes no branch of its own and errors when the
head is not on the remote.

Purpose: the forge is the one boundary in this phase that reaches outside the machine, and it is
the one place where a half-completed action is possible — the push can land and the request
creation can fail. That outcome must be reportable as what it is. The deterministic-draft
discipline matters for the same reason it did at task scope: the component passes an epic id alone
and never a title or a body, which is what makes the previewed text and the published text the
same text rather than two texts that happen to agree.

Output: `assemble_epic_request_draft`, the precondition check, the push-then-create sequence, one
new test file, and an extension of the existing fake-CLI chain test.
</objective>

<decisions_resolved>
- **The push runs from the project's main checkout, not from the epic worktree.** The generated
  pre-push hook's territory check lets any push whose working directory is outside the configured
  worktree root through untouched, while a push from inside a worktree enters the force-push and
  branch-deletion ancestry checks. A plain fast-forward passes those too, but there is no reason
  to enter that code at all.
- **`origin` is the remote name, passed explicitly.** It is the only remote the rest of the
  codebase names; a project with a differently-named remote surfaces the no-remote precondition
  rather than guessing.
- **Preconditions are checked and named *before* the sheet opens, not discovered on send.** Four
  blockers: the integration branch is NULL; the branch has no commits ahead of the default branch;
  the project's forge is the local (no forge) variant; and the forge CLI is absent or
  unauthenticated. The first three are cheap local reads. The fourth is only knowable by asking
  the CLI, so it is reported from the existing error taxonomy on send as well.
- **The epic request ships read-only** (orchestrator-resolved decision 2). The live read of an
  epic's request is a new *caller* of the existing Phase 7 adapters, which this phase's boundary
  permits; no status is written and no poll is registered, because nothing in Phase 7 observes an
  epic request and D-122 reserves both relevant transitions.
- **The optional compare-page fallback is not built.** Research marked the URL shapes `[ASSUMED]`
  and flagged the whole fallback optional; the typed not-installed and not-authenticated outcomes
  the task flow already shows are the baseline, and an unverified URL that opens the wrong page is
  worse than a correct error. Recorded as a deferred idea rather than a gap.
- **`create_request_at`'s call-site comment is corrected, not gated.** The epic command in plan
  08-08 is a third caller; no test counts them.
</decisions_resolved>
