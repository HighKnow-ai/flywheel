<objective>
The Merge action, where the user can reach it: a confirm sheet that shows the whole cost before
the write, a merge that runs off the main thread with no database lock held, and three outcomes
each of which the core proved before the sheet claims it.

Every mechanism this needs exists after plan 08-03 — the side-effect-free dry run, the merge in a
worktree that belongs to the epic, the abort safety net, the per-epic exclusion guard, the single
event, the derived integrated marker. This plan is the command seam and the surface.

Purpose: two traps sit in this layer specifically. The first is the lock discipline — holding the
database mutex across a merge would freeze every other command for as long as git takes, which is
why the resolve, the run and the record are three separate steps with the lock dropped in the
middle. The second is Pitfall 5: after a merge commit, the three-dot range between the integration
branch and the task branch is empty, because the task tip has become the merge base — so a surface
that kept reading that range would report "no changes" for the work it had just landed. The fix is
to review the merge commit against its first parent once a task is integrated.

Output: two commands, the post-merge diff base, the confirm sheet with its three outcome states,
and one test file.
</objective>

<decisions_resolved>
- **The dry run is the sheet's preview and is re-run by the merge.** `merge_tree_check` mutates
  nothing, so calling it on sheet open is free. The real merge calls it again as its own first
  step, so the sheet's hint going stale between open and confirm can only make the *hint* wrong,
  never the merge. Research open question 4 is resolved by accepting that window rather than
  adding machinery to close it.
- **The merge command takes a task id alone.** Branches, counts, the repository path and the epic
  worktree path are all derived by `plan_merge`. This is the same rule the forge commands follow
  and it is what makes the previewed figures and the merged figures the same figures.
- **The per-epic guard is taken in the command, between the resolve and the run.** It must be held
  across the git work and released by its own drop, and it must not be held while the database
  lock is held — two locks in the same window is how a deadlock is built.
- **`destructive.rs` stays out of this** (D-146). That gate exists to classify what *agents* try
  to run in a shell; this merge runs from Rust as the user's own deliberate action, behind a
  confirm sheet that names everything it will do. Phase 12's trust-boundary work is untouched.
- **The integrated task's review range is the merge commit against its first parent.** The first
  parent is the integration side, so the diff shows what the merge landed. Without this, an
  integrated task's review would be empty — and an empty review would be indistinguishable from a
  task with nothing to review, which is Pitfall 5's second half.
- **The dirty-worktree warning reuses the git-facts read.** D-138's banner needs a count of
  uncommitted files in the task worktree, which the existing git-facts hook already returns; no
  new command and no second porcelain read.
- **The conflict's two ways out are the existing affordances.** Start a resolve session through the
  handler plan 08-01 already wired, and open the task's worktree through the existing
  open-in-editor command. The epic worktree is clean after the abort, so there is nothing there to
  open.
- **No push after a merge** (orchestrator decision 3): the merge stays local and reversible.
</decisions_resolved>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → the merge command | a task id crosses; every branch, path and count is derived server-side |
| command → git write | a merge commit lands in the user's repository |
| command → shared database mutex and the per-epic guard | two locks exist in one call path |
| outcome → the reader | what the sheet claims must be what the core proved |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-07-01 | Tampering | `review_merge_task` arguments | high | mitigate | The command takes a task id alone; the plan function derives the repository path, both branch names, the epic worktree path and both counts from the board. No ref, sha or filesystem path can be supplied by the renderer, asserted by inspecting the signature in the acceptance criteria. |
| T-08-07-02 | Denial of Service | the shared database mutex held across git | high | mitigate | Resolve under the lock, drop it, run git, re-lock to record, drop again, then emit. Asserted by counting the two lock-release points in the command body. The merge runs off the main thread through the async command attribute. |
| T-08-07-03 | Denial of Service | deadlock between the database mutex and the epic guard | medium | mitigate | The guard is taken only after the database lock has been dropped, and is released by its own drop at the end of the call. The two are never held simultaneously. |
| T-08-07-04 | Destruction of work | two merges racing into one integration worktree | high | mitigate | The per-epic guard refuses the second caller by name, and the surface renders that refusal with no retry control, so the UI does not invite the race the guard prevents. |
| T-08-07-05 | Repudiation | an outcome the core did not prove | high | mitigate | The sheet renders exactly the three outcome variants the core returns; the conflicted variant carries the file list the dry run produced, and the merge path's own abort-and-re-check means a reported conflict is a conflict that touched nothing. |
| T-08-07-06 | Information Disclosure | git stderr reaching the sheet | medium | mitigate | Conflicted file paths cross the boundary as values; raw git output does not. The command maps failures to named categories and logs the rest. |
| T-08-07-07 | Elevation of Privilege | the agent-facing destructive gate | low | accept | D-146: the user's own deliberate merge, behind a sheet naming every consequence, deliberately stays outside the gate that classifies what agents run in a shell. The gate's own layers are untouched because this merge runs from Rust. |
| T-08-07-08 | Tampering | a status moved as a side effect of merging | high | mitigate | No status write exists in the command, the core merge path or the surface; the test module mock lists no status-setting function, so an attempt would fail structurally rather than silently. |
