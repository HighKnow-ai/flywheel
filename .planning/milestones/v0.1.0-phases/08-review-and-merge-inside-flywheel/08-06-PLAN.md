<objective>
The criteria rail: the moment the core value stops being a slogan. The item's acceptance criteria
sit beside the diff, a hunk or line range selected in the diff becomes a criterion's evidence, and
a criterion checked with nothing selected says so rather than passing itself off as verified
against code.

The storage, the staleness and the write command all landed in plan 08-02. This plan is the
interaction: compose the existing criteria row rather than fork it, add the three evidence states
to it, give the diff a selection, and connect the two.

Purpose: the ROADMAP's own note says criterion 2 "is where the core value becomes a daily habit
rather than a slogan — the review surface is the moment structured acceptance criteria pay for
themselves against a chat blob." Two things make that true rather than decorative. The rail must
be the *same* criteria component the item panel uses, so revision markers and the check
interaction cannot drift into two implementations. And the no-evidence state must be visible
everywhere a criterion appears, because a record that cannot distinguish a verified check from a
waved-through one is no better than a chat blob that claims the work is done.

Output: `CriteriaRail.tsx`, the selection plumbing through the diff, four legend marks, and one
test file.
</objective>

<decisions_resolved>
- **The line-level hook is `widgets` plus `selectedChanges` plus `gutterEvents`, not
  `Decoration`.** D-135 names "the decoration API", but in `react-diff-view@3.3.3` `Decoration`
  wraps *hunks* — hunk headers and expand-context rows. The line-level anchor the decision
  actually wants is a widget keyed by change key, with the selection highlight coming from
  `selectedChanges` and the click handling from `gutterEvents`. The interaction D-139 describes is
  fully supported; only the prop names differ from the ones the decision named.
- **The selection lives on the surface, not in the diff.** `ReviewSurface` owns the selected
  change-key set and the path they belong to, because the rail — a sibling of the diff — is what
  consumes it. The diff reports gutter clicks upward and renders the highlight and the widgets back
  down.
- **A selection spanning two files is not a thing.** Selecting a change in a second file replaces
  the selection rather than extending it: an anchor is one path with one range, by schema.
- **The anchor's side comes from the change kind** (research assumption A9): a deletion anchors to
  the old side, anything else to the new side. The line range is the minimum and maximum of the
  selected changes' line numbers on that side.
- **The rail composes the row, and the row gains the fields.** `AcceptanceCriteriaList.tsx`
  exports its row so the rail can render the same component with evidence and staleness props;
  the item panel's own use gains the no-evidence marker from the same change, because D-140
  requires it visible in both places.
- **All four new marks land here, including the integrated mark** that plan 08-07 renders. The
  legend rule runs one way — no mark without an entry — so an entry ahead of its renderer is
  fine, and it keeps the legend file owned by exactly one plan in this phase.
- **The rail always renders a header**, unlike the file-list and diff panes. It follows the
  criteria list's own always-render discipline rather than the git-facts section's
  absence-is-the-design one, because an item with zero criteria is the case the review surface
  most needs to make visible.
</decisions_resolved>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| reader's selection → recorded evidence | a line range becomes a durable claim that a criterion was verified |
