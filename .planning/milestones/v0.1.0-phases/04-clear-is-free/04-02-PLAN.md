<objective>
**As a** developer who force-kills a hung agent, **I want to** still find a summary on the board for
that run, **so that** the word *every* in "every session ends by writing a summary" is literally true
— including for the sessions where continuity matters most.

D-35 guarantees that Stop is interrupt-then-force and that a session can die without saying anything.
D-64 closes that gap: when a run reaches a terminal state with no summary row, the core writes a
best-effort one from the event log and the run record, flagged `auto_generated`, so reconstitution
never has a hard hole in it. This plan builds only the *fallback* producer; the agent's own
`report_summary` write surface is plan 04-03, and the file-list half of the fallback's `changed`
field is filled in by plan 04-07 once the git diff helper exists.

Purpose: make CTX-01 unconditional. Output: `synthesize_fallback_summary` plus the presence check
inside `apply_session_closed`'s existing transaction.

**Deliberate seam (recorded, not accidental).** The synthesizer reads the event log and the
`agent_runs` row only — it issues no git call. `apply_session_closed` is a database-only function
whose caller (`handle_inbound_session_closed`) is documented as never panicking and never doing IPC
work inline; spawning a `git diff` subprocess inside its transaction would couple the shared sidecar
reader loop to a process spawn. Plan 04-07 fills the `changed_files` half from the real
`git diff --name-only` at the command layer, which is a functionality fill, not an architectural
change.
</objective>

  <action>
Add `pub fn synthesize_fallback_summary(tx: &Transaction, agent_run_id: &str, close_reason: &str) ->
anyhow::Result<String>` to `packages/core/src/domain/session_summary.rs`, returning the new summary's
id.

It takes a `&Transaction`, **not** a `&mut Connection` — it runs inside the caller's transaction, the
same way `agent_run::set_run_blocked` already does for `permission_request::create_pending_request`.
That is what makes "a run can never be terminal while its fallback summary is missing" a property of
the database rather than of call ordering. Factor the insert-plus-event body of `create_summary` into
a private `fn insert_summary_row(tx: &Transaction, agent_run_id: &str, fields: &SummaryFields,
actor_id: &str, now: &str) -> anyhow::Result<SessionSummary>` so both the public `&mut Connection`
entry point and this transaction-scoped one share exactly one insert site — never two INSERT
statements against the same table.

What the synthesizer may claim, resolving CONTEXT.md's open discretion item explicitly:

- `changed_files`: an empty `Vec` in this plan. The row is honest about having no file list rather
  than guessing one. Plan 04-07 fills it from the real `git diff --name-only` once that helper exists.
- `changed_prose`: `Some(...)`, a sentence built only from facts already in the database — the close
  reason, the run's start and end timestamps, and the count of `events` rows whose `stream_id` is
  this run or whose `task_id` matches within the run's window. Read that count with a literal `&str`
  SELECT bound through `params![]`.
- `remains`: `Some(...)`, a fixed sentence stating that the session ended without recording its own
  summary and that the working tree is the authority on what is finished.
- `next_session_must_know`: **`None`, always.** This is the one field only the agent can fill — D-64's
  own argument for why the agent authors summaries at all is that this content is unrecoverable from a
  diff. A synthesized value here would be an invented claim, which prohibition P2 forbids.
- `decisions`: an empty `Vec`. Same reasoning — a decision the agent did not state is not a decision.
- `acknowledged_decisions`: an empty `Vec`.
- `diff_ref`: `None` in this plan; plan 04-07 fills it.
- `auto_generated`: `true`.

Resolve the actor: read `actor_id` from the `agent_runs` row inside the same transaction and attribute
the row to it, so DATA-03's actor model stays honest — the run's own agent actor is who the board says
produced this, and the `auto_generated` flag is what says the core wrote it on that agent's behalf.

Add tests in `packages/core/tests/session_summary_lifecycle.rs` covering the four behaviours above.
Each test opens its own transaction to call the synthesizer directly, so the function is exercised
without going through `apply_session_closed` — that wiring is Task 2's subject.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sidecar stdout → Rust core | The `session_closed` event's `runId` and `reason` are untrusted values crossing a process boundary into a write path. |
| synthesized prose → board | Text the core itself authors enters a store whose other rows carry an agent's voice; the two must stay distinguishable. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Spoofing | `apply_session_closed`'s `runId` | high | mitigate | The existing ULID guard rejects a malformed id before any statement is issued; the synthesizer resolves task, project and actor from the `agent_runs` row, never from the event. |
| T-04-05 | Repudiation | synthesized vs agent-authored provenance | high | mitigate | `auto_generated` is a CHECK-constrained NOT NULL column set by the synthesizer and never by `create_summary`'s agent path; the renderer marks it; the tests assert both directions. |
| T-04-06 | Denial of service | fallback firing inside the shared sidecar reader loop | medium | mitigate | The synthesizer issues database statements only — no process spawn, no network call, no filesystem read — so it cannot stall the reader task that `handle_inbound_session_closed` runs on. |
| T-04-07 | Tampering | partially applied close | high | mitigate | The status update and the summary insert share one transaction; a failure rolls both back, so a terminal run with a missing summary is not a reachable state. |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable — this plan installs no package. Any newly surfaced dependency need routes back through the legitimacy gate before it is added. |
