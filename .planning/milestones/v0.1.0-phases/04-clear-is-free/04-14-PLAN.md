<objective>
**As a** developer betting a product on the claim that the board can reconstitute a context, **I want to**
see an automated test run one task through ten session cycles with its acceptance criteria provably
unchanged, **so that** I am not shipping a thesis on a single happy handoff.

`PITFALLS.md`'s "Looks Done But Isn't" checklist names this exact failure: context reconstitution is
often "tested" only on session 1 to 2 — the case where accumulated drift has not yet had a chance to
appear. ROADMAP.md's Phase 4 Notes carry the matching research flag: *build the synthetic multi-cycle
test suite and the context-quality metrics before shipping this phase — do not ship without evidence the
thesis holds.* This plan is that evidence.

Purpose: CTX-07, and the phase's own permission to ship.

**Planner call, resolving CONTEXT.md's open item on how the cycles are driven.** The primary harness is
**Rust-core-driven and synthetic**: each cycle writes a summary through the real `create_summary` path,
assembles a real packet and renders a real prompt, with no agent and no model anywhere. WINDOWS.md rows
11 and 12 record two consecutive end-of-phase `scripts/uat/run-all.sh` runs failing 4 of 6 on
live-`claude`-session scripts, judged pre-existing flakiness — and a flaky harness would make the phase's
headline deliverable unfalsifiable, which is worse than having no harness. Phase 3's precedent of proving
process-level guarantees with real spawned processes still applies, but to *process* guarantees; this is
a data-fidelity guarantee, and `ContextPacket` already derives `PartialEq`, so it needs no process at all.
The secondary harness drives the real MCP write surface with `fake-claude.mjs` — deterministic, but real
sockets and real tool calls — so the wire path is proven to survive repetition too. Neither harness calls
a live model.

**What "context-quality metrics" means here, made concrete.** Four measurable properties, asserted per
cycle rather than once: criteria fidelity (byte-identical statements), decision retention (every id from
cycle one still present at cycle ten), bounded verbatim carry (exactly five verbatim summaries past the
window, with no folded narrative leaking in), and per-cycle determinism. Plus one negative: zero drift
warnings across ten honest cycles.
</objective>

  <behavior>
    - **Bounded verbatim carry.** At every cycle from the sixth to the tenth, the packet's compaction boundary reports exactly five verbatim summaries, and the folded count equals the cycle number minus five.
    - **No narrative leakage.** Each cycle's summary carries a prose string unique to that cycle. At cycle ten, the rendered prompt contains the prose strings of cycles six through ten and contains none of the prose strings of cycles one through five.
    - **Decision retention under folding.** At cycle ten, the rendered prompt contains every one of the ten decision statements, including those from folded cycles — the losslessness claim, asserted on rendered output rather than on a struct.
    - **Per-cycle determinism.** At every one of the ten cycles, two assemblies against the unchanged database are equal and two renders are byte-identical.
    - **Zero false positives.** At every cycle, `detect_drift` over honest inputs — a claimed file list matching the real one, a matching head ref, a clean tree, a matching pin, a complete echo — returns an empty vector.
    - **Growth is in the folded region only.** The rendered prompt's verbatim region byte length at cycle ten is within ten percent of its byte length at cycle five, because the window is fixed at five summaries of comparable size.
  </behavior>
  <action>
Turn "context-quality metrics" from a phrase in the roadmap into six assertions.

Extend `packages/core/tests/five_cycle_reconstitution.rs`, reusing Task 1's cycle driver. Give each
cycle's summary a prose string containing the cycle number and a marker substring that appears nowhere
else, so the leakage assertions can search for it unambiguously. Give each cycle's decision a statement
containing its own unique marker for the same reason.

Write the six behaviours above as six named tests. For the verbatim-region byte-length comparison,
extract the region between the verbatim subsection heading and the next heading rather than measuring
the whole prompt — the whole prompt legitimately grows with the folded region, and measuring it would
assert the wrong thing.

For the zero-false-positive test, construct `DriftInputs` honestly at each cycle: the claimed paths equal
the real paths, `head_ref` equals the latest summary's `diff_ref`, the tree is clean, the pin equals the
current criterion ids, and the echo covers every recorded decision. Any warning at any cycle is a
detector that cries wolf as history grows, which is the failure mode that would make the board signal
worthless.

Add a module-level comment listing these six metrics by name, so a future reader can tell at a glance
what "the thesis holds" was taken to mean when this phase shipped — and so a later phase that changes the
window or the fold knows exactly which assertions it is renegotiating.
