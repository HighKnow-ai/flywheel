<objective>
**As a** developer who edited a task's acceptance criteria between sessions, **I want to** be told the
criteria moved in the run I actually start — not only in the preview I glanced at — **so that** the board
never un-tells me something it already told me.

Gap #2 from `04-VERIFICATION.md`. `packet_extras_for` resolves the run whose criteria-revision pin should
be compared by calling `query::permissions::latest_run_id_for_task`, which is
`SELECT id FROM agent_runs WHERE task_id = ?1 ORDER BY started_at DESC LIMIT 1`. In `agent_run_preview`
that is correct — no run row exists yet for this start, so it resolves the task's genuine most recent run.
In `agent_run_start` it is called AFTER `start_agent_run` has already inserted the new `agent_runs` row
with `started_at = now`, so it resolves the BRAND-NEW run, whose `criteria_revision_pin` is still NULL
because `pin_criteria_revisions` does not run until later in the same function. `criteria_revision_pin_for_run`
returns `None`, `pinned_criterion_ids` becomes `None`, and `detect_criteria_revision`'s early-return guard
(`let pinned = inputs.pinned_criterion_ids?;`) makes it silently return `None` even when the criteria
really did move.

`agent_run_start` is the ONE call site whose whole purpose is to persist the warning
(`record_drift_warnings`) and forward it into the agent's own prompt (`render_prompt`'s `## Warnings`
section). Both silently skip it. The developer sees `CriteriaRevisionMoved` in the launch sheet preview,
clicks Start Work moments later, and gets a prompt with that exact warning missing — and no
`drift.detected` event is ever written, so `query::recovery`'s needs-you arm 3 can never fire for this
detector through the real start path either. That is precisely the "told, then left to discover it in the
diff" failure roadmap Success Criterion 4 exists to prevent.

Purpose: CTX-06, roadmap Success Criterion 4.
Output: the pin comparison resolves the run that actually preceded this one, and an integration-level
assertion drives `agent_run_start`'s own DB half end-to-end rather than the preview.

**Scope discipline.** The three other detectors (`ClaimedFilesMismatch`, `StaleSinceLastSummary`, and the
decision read-back pair) are correct and are not touched. `detect_criteria_revision` itself is correct as a
pure function (30/30 in `drift.rs`) and is NOT modified — this is a wiring fix at the call site, exactly as
the verifier framed it. The out-of-scope warnings from `04-VERIFICATION.md` are not addressed here.

**Wave note.** This plan is wave 2 solely because it edits the same file as plan 04-15
(`packages/desktop/src-tauri/src/commands/agent_run.rs`). It has no logical dependency on gap #1's fix.
</objective>
