<objective>
**As a** developer who notices a badly worded criterion three hours into an overnight run, **I want to**
sharpen it and get an edit, **so that** the board stays honest without my fighting the tool — and the
original wording stays intact so nobody can rewrite what an agent was told.

BOARD-03 is the phase's second requirement thread, independent of summaries until the packet reads
them both. D-76 fixes when the lock engages: the existence of the first `agent_runs` row for the task,
ever — a fact already in the schema, needing no new flag, and not a status value a human can hand-edit.
D-77 fixes what an edit does once locked: append a revision row, mark the predecessor superseded, never
UPDATE the original `statement`. Immutability is enforced at the write path, the same way Phase 1 made
the CHECK constraint the authority rather than app code.

Purpose: land the revision schema and the one write path that decides. The Tauri command and the
"revised" marker in the UI are plan 04-09; the run's revision pin (D-78) is plan 04-09 too.

Output: migration `0009`, `revise_criterion` plus its lock check, and three read paths filtered to
current revisions so superseded wording can never reach an agent.

**Reversibility note (no checkpoint inserted).** Task 1 carries a `one-way` rating: D-77 is a schema
change to a table Phase 1 shipped. No `checkpoint:decision` is inserted because `04-CONTEXT.md` D-77
records the developer choosing this exact option with both alternatives named and rejected, and because
the change is *additive only* — three nullable-or-defaulted `ADD COLUMN` steps, which is precisely what
`0002_board_schema.sql`'s own comment predicted ("Phase 4's revisioning is an additive column"). No
CHECK constraint changes, so `0006`'s backup-first table-rebuild sequence is deliberately not needed
here; the undo is a column drop, not a data migration.

**Planner call (deviation from 04-PATTERNS.md, recorded).** The pattern map sketched one combined
migration `0008_session_summaries_and_revisions.sql`. This plan splits it into `0008` (summaries, plan
04-01) and `0009` (revisions, here) because the two workstreams are independent, both halves are purely
additive, and one migration per plan keeps the two plans in separate waves without an artificial file
conflict. `rusqlite_migration` numbers them independently and applies them in list order, so nothing
about the combined form was load-bearing.
</objective>
