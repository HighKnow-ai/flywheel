<objective>
The roadmap's own note says criterion 2 is the one that decides whether fleet supervision beats
tab-cycling through terminals: **a dedicated queue showing every agent currently blocked and waiting on a
human, across all projects at once** — and answerable without leaving it.

Purpose: draining four blocked agents across three projects should cost four keystrokes, not four round
trips. That is the queue's entire reason to exist (D-173). It needs no new verb: 02-UI-SPEC Discretion #6
already specifies one card component mounted in two places, both reading and writing the same row, so the
queue is simply the third mount.

Research measured the one way this goes badly wrong. `PermissionRequestCard` gates keyboard on the index
within the array a *single* card instance receives, and each enabled row registers its own window-level
keydown listener with no deduplication. Mounting one card per blocked run — the natural reading of D-173 —
makes every row a keyboard owner, so one `a` press answers every queued agent across every project,
including destructive requests. This plan adds the `keyboardEnabled` prop that makes exactly one card the
owner, and pins it with a test that one keypress produces exactly one answer.

Output: `query::fleet::blocked_queue`, the `fleet_blocked_queue` command, `BlockedQueue.tsx` as the card's
third mount, the `keyboardEnabled` prop, the queue view on the fleet surface, and the project rail's
review-queue row turned into its entry point.
</objective>
