<objective>
The fleet row answers the second half of FLEET-01 — not just *that* an agent is running, but **what it is
doing**. One truncated line per live row, taken from that run's own session log through the normaliser the
session feed already uses.

Purpose: a row that says only "running · 18m" is not a liveness signal; it cannot tell you whether the
agent is on track, which is the actual question D-167 was written against. Research measured two reasons the
obvious implementation does not work: the latest feed row cannot come from SQL at all (the log is a JSONL
file and the existing window read scans every line first), and `board:changed` is never emitted per agent
event, so the cell would not move until something unrelated fired.

**Deliberate deviation from D-171, recorded here as the plan's own decision (RESEARCH Finding 2, Open
Question 1, and the orchestrator's instruction to record it):** D-171 says one cross-project query re-run on
`board:changed`. That stays true. This plan **adds one** app-level `agent:event` listener — not one per run
— whose only job is to trailing-edge-throttle an invalidation of that same single query key to about once a
second. D-171 rejected *N subscriptions churning as runs start and end, duplicating the normaliser outside
the session surface*; this is one static listener doing invalidation only, with the normaliser still living
in exactly one place. One read path, two triggers.

Output: `session_log::read_tail`, the activity projection on `fleet_list`, the throttled listener in
`useFleet`, and the activity cell in the fleet row.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session log file → renderer | Log lines are model-produced data reaching the webview as text in a dense list; they are the same lines the session feed already renders. |
