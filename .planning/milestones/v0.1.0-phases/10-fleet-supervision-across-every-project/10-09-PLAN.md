<objective>
WORK-07's last third: **the user reclaims stale worktrees**, across all projects, in one pass. Multi-select,
one confirmation naming the total bytes, per-row results.

Purpose: WORK-07's value is reclaiming the *accumulation* — doing it one dialog at a time is why nobody
does it. But D-179's "loop the existing `worktree_remove` verb" is unsafe exactly as written, and research
measured why: that command is a synchronous main-thread handler that takes the database mutex and runs
`git status --porcelain` plus `git worktree remove` inside it, and deleting a worktree holding
`node_modules` and `target/` takes seconds — eight in a row would freeze the window and every other
command. It also never checks that no run is live, so a bulk UI with a stale selection could remove a
worktree an agent had just started in.

So this plan builds a **new async batch command** that re-derives eligibility server-side per row with the
same function the inventory read uses, then calls `remove_worktree_for_task` **unchanged** so its own
porcelain re-read stays the final guard. D-179's actual commitment — that no new bypassing path is created
and the capability file's standing rule that no parameter at any layer can skip that guard is not weakened
— is honoured by keeping the removal verb untouched, not by looping the command.

Output: `reclaim_worktrees` in the core, the `worktree_reclaim` command, and the inventory's multi-select,
confirmation and result list.
</objective>

The loop's shape is the whole point: per row, re-derive the disposition with `reclaim_eligibility` — the
**same function** the inventory read uses, so the list and the action share one definition — and when it is

refusal must not fail the batch, which is why the return type is a vector of outcomes and not a
`Result<()>`. De-duplicate the submitted ids before looping.

Do not modify `remove_worktree_for_task` in any way. Its porcelain re-read is the final guard and the
reason the capability file's standing rule stays true: there is no new path that can skip it, and no
parameter is added anywhere that could. Say that in the new function's doc comment, so the next reader does
not add a `force` flag.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer selection → destructive server action | The renderer's selection is the highest-consequence input in this phase: it names directories to delete. |
| database mutex → `git worktree remove` | A multi-second removal must never run while the single mutex is held. |
| worktree directory → removal | The directory may hold uncommitted work that must never be destroyed. |
