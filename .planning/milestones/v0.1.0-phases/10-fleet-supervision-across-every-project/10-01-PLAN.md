reproduced rather than invented):** Cyril answers "what is every agent, everywhere, doing — and what needs

`fleet.rs` command module, the fleet surface and the single run-status vocabulary. Proving them against the
real schema, the real event push and the real surface stack before the queue, the notifier and the
inventory exist means an architectural dead end costs one commit instead of eight.

generalisation breaks — a first-launch flood of every historic run (Pitfall 1), a task with two
unacknowledged terminal runs reading twice (Finding 1b), and a third copy of the run-status vocabulary
(Finding 14).

**2. `packages/core/src/query/fleet.rs` (new), added to the module list in `packages/core/src/query/mod.rs`.**

- `pub struct FleetRow` with: `agent_run_id`, `project_id`, `project_name`, `project_key_prefix`,
  `project_status`, `subject_kind: FleetSubjectKind`, `task_id: Option<String>`,
  `task_key: Option<String>`, `task_title: Option<String>`, `task_status: Option<String>`,
  `epic_id: Option<String>`, `epic_key: Option<String>`, `authoring_stage: Option<String>`,
  `run_status: String`, `fleet_state: String`, `started_at: String`, `ended_at: Option<String>`,
  `blocked_since: Option<String>`, `cost_usd: Option<f64>`, `tokens_in: Option<i64>`,
  `tokens_out: Option<i64>`.
- `pub enum FleetSubjectKind { Task, Epic, Authoring }` — derived from which of `task_id` / `epic_id` is
  present plus `authoring_stage`, because `agent_runs` allows both to be NULL and forbids both being set
  (Finding 10). A run with neither is `Authoring` when it carries a stage and `Epic` when it carries an
  epic; the renderer must still be able to render a row with no subject key at all.
- `pub struct FleetList { rows: Vec<FleetRow>, total_rows: usize }`.
- `pub const FLEET_ROWS_MAX_LIMIT: usize = 200;` and
  `pub fn fleet_rows(conn: &Connection, limit: usize) -> anyhow::Result<FleetList>` clamping `limit` to
  that constant.

One literal `FLEET_SQL` constant. Selection: `agent_runs` joined to `projects` (inner — every run has a
project), `LEFT JOIN tasks` and `LEFT JOIN epics` (Finding 10). `WHERE` admits a row when either the run
status is `running` or `blocked`, **or** the run status is one of `completed`, `failed`, `interrupted`,
`abandoned` **and** `acknowledged_at IS NULL` **and** the Finding-1b latest-run rule holds: the row is
admitted when its status is `abandoned` (which keeps `recovery.rs`'s any-unacknowledged rule so the rail
count and the band agree), or when `task_id IS NULL`, or when the run's id equals the task's most recent
run id by the `ORDER BY ar2.started_at DESC, ar2.id DESC LIMIT 1` subselect `recovery.rs` already uses.

`fleet_state` is a `CASE` alias, not a column (D-168): a `completed` run whose joined task exists and
whose task status is not `done` reads `awaiting_review`; every other case is the run status unchanged.
`blocked_since` is a correlated `MIN(created_at)` over that run's `pending` `permission_requests` rows.

`ORDER BY` does all the banding and ordering in SQL — the renderer only groups (D-03, and the
anti-pattern RESEARCH names explicitly). First key: a `CASE` over `fleet_state` giving `blocked` 1,
`awaiting_review` 2, `abandoned` 3, `running` 4, and `completed`/`failed`/`interrupted` 5 — the fixed band
order from D-164's sketch. Second key: the waiting timestamp ascending, longest-waiting first, as
`COALESCE(blocked_since, ended_at, started_at)`. Third key: `ar.id ASC`, which is what makes the order
stable and repeatable when the second key ties. Then `LIMIT ?1`.

`total_rows` is the length of the returned rows, so the header count and the list can never disagree.
