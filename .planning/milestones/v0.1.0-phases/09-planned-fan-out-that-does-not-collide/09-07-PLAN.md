## What this plan changes about Phase 8, stated up front

D-156 re-interprets Phase 8's success criterion 3. Per-task review before merge **stops being mandatory
during fan-out**, and the review of record moves to the epic integration diff before the request. Per-task
review remains available; it is no longer a gate. This is a **one-way** change: once a fan-out has
auto-merged task branches into an epic integration branch, reinstating the per-task gate does not un-write
that history, and wave two's commits sit on top of wave one commits that were never individually reviewed.

**Why there is no `checkpoint:decision` in front of it, despite the `one-way` rating.** The reversibility
taxonomy's own anti-pattern list names this case: *"Gating a decision already made — if the phase CONTEXT.md
records the human choosing this exact option, the door is already walked through. Keep the rating for the
record; do not insert a checkpoint to re-ask."* CONTEXT.md records the owner choosing D-156 by name and
records its one-way rating in the same breath. The rating is therefore carried on the task for the record
and the decision is not re-asked. The structural validator cannot read CONTEXT.md and will warn about the
missing checkpoint; that warning is expected and this paragraph is the answer to it. Both the plan SUMMARY
and the phase artifacts must state the Phase 8 re-interpretation plainly rather than leaving a reader of
Phase 8's criteria to discover it.

  <action>
Add the decision half to `packages/core/src/dispatch.rs`. It is **database-only**: no git, no subprocess,
no sleep, no clock of its own. `now` is a parameter. That constraint is what makes the whole dispatcher
testable without a timer and safe to call while holding the database lock, and it is what lets the Tauri
crate execute the actions after releasing that lock.

`pub enum Action { Spawn { task_id }, Merge { task_id }, AdvanceWave { plan_id }, MarkNeedsAttention
{ task_id, cause } }`, and `pub fn decide(conn, now_epoch_secs) -> anyhow::Result<Vec<Action>>`.

The evaluation, in order:

1. Read the gate. Paused: emit no spawn actions at all, and no new planning pass either; merge actions are
   still emitted, because a merge is local git and touches no backend. Warning tier: spawn actions inside
   the current wave are fine, advance actions are not.
2. Read the cap and `occupied_slots`. The spawn budget is the cap minus the occupied count, floored at
   zero — never negative, because a user's own launches can legitimately put the live count above the cap
   and the correct response is to spawn nothing, not to refuse anything.
3. For each live plan, collect its ready tasks. A task is ready when its wave equals the plan's cursor,
   every predecessor edge's task is merged or user-skipped, and its declared entries overlap no currently
   in-flight armed task's set in the same project. **Merged, not finished**, is load-bearing: worktrees are
   cut lazily at spawn from the epic integration tip, so a successor spawning the moment its predecessor's
   process exits would be cut from a base without that work, and the collision the edge exists to prevent
   would reappear as a merge conflict. The cross-plan overlap test uses the same `in_flight_declared_sets`
   query the widen re-check uses — the plan-level check only ever sees one plan's tasks, and two epics'
   plans can touch the same files.
4. Emit spawn actions for the ready tasks up to the budget. A task whose existing worktree row has a base
   whose tip predates the epic integration tip gets a needs-attention action with that named cause instead:
   worktree reuse is real in this codebase, so a reused worktree does not get a fresh base, and this plan
   adds no rebase logic.
5. For each task whose run has ended, decide between merge and needs-attention. A clean worktree with
   commits ahead of its base is a merge. A dirty worktree, or zero commits ahead, is needs-attention with
   the cause named — the agent's briefing instructs it to commit (Task 2), and an uncommitted finish must
   stop that task rather than advance the wave past work that is not in the base. Never auto-commit: that
   rewrites the authorship of the agent's output.
6. Emit one advance action per plan whose cursor wave is entirely merged or skipped. A failed, stopped,
   conflicted or needs-attention task blocks its wave and is surfaced; the user retries or skips it.

All state is in the database, so the function is idempotent and restart-safe by construction: recomputing
"what should happen next" from rows is correct after a crash, and an in-memory state machine would not be.
This dispatcher writes no `tasks.status` — a status has exactly one owner per transition, and the
wave-plan state is the dispatcher's own display.
