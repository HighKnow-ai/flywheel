<objective>
**As a** developer deciding whether this authoring surface earns its place, **I want to** the two
numbers it reports to be the real ones, **so that** the Product Kill Criterion's verdict is evidence
rather than an artefact of a read bound.

`05-REVIEW.md` WR-05, confirmed unfixed at HEAD and confirmed by `05-VERIFICATION.md` truth #9's
caveat. `measure_authoring_run` (`packages/core/src/query/authoring.rs:364-397`) has two ordering
defects in one function:

1. The proposal-lifecycle event read is `ORDER BY e.occurred_at ASC LIMIT ?2`. `last_accepted_at` is
   derived by scanning that result for its maximum, so once a run's accept/amend event count exceeds
   the bound, the read keeps the OLDEST events and discards the newest — reporting an acceptance
   earlier than the run's real last one. Every sibling bounded read in this crate orders `DESC`
   before `LIMIT` precisely so a bound trims the tail, never the head.
2. The proposal read has no `ORDER BY` at all, so which rows survive the bound is unspecified.

This is the round's one live spec-less-probe edge (`SHAPE-04 / ordering`: when elements compare
equal, is output order specified and stable?), and `measure_authoring_run` is exactly where it bites.

One thing the review's own prescription does not cover, and this plan must: ordering the single
combined event read `DESC` fixes `last_accepted_at` and breaks `amended_before_accept` in the same
motion, because amendments necessarily precede the acceptance they belong to — the newest-first
window would discard them. One window cannot serve both ends of one set. The fix is therefore two
purpose-shaped reads, each bounded at the end that its own answer depends on.

Purpose: make the kill criterion's numbers correct under a bound, not merely ordered.
Output: two reads that each keep what they need, a deterministic proposal read, and three tests.
</objective>

  <behavior>
    - With a run whose accept/amend event count exceeds the requested limit, the reported last acceptance is the newest one, not an earlier one.
    - With an amendment recorded well before several later acceptances, and a limit smaller than the total event count, the amended criterion still counts toward amended-before-accept.
    - A run with no accepted proposals still reports zeroes, no last acceptance and no elapsed span — never an error.
    - Two calls with the same arguments against an unchanged database return equal results.
  </behavior>
  <action>
    Replace the single combined event read with two purpose-shaped reads, both still compile-time
    literals with `params![]` bindings.

    **Last acceptance.** Read it as a single-row aggregate:
    `SELECT MAX(e.occurred_at) FROM events e JOIN authoring_proposals p ON p.id = e.stream_id WHERE
    p.agent_run_id = ?1 AND e.stream_type = 'authoring_proposal' AND e.event_type =
    'proposal.accepted'`. Read it with `query_row` into an `Option<String>` — `MAX` over an empty
    set yields SQL NULL, which is exactly the existing `last_accepted_at: None` case, so the
    no-acceptances behaviour is preserved without a special branch. This read returns one row by
    construction, so it takes no `LIMIT` and no `ORDER BY`: there is no bound left for a bound to
    truncate, which is the point. Say so in a comment, since a later reader scanning for this
    module's clamp idiom will otherwise flag its absence.

    **Amended ids.** Read them as their own bounded set:
    `SELECT DISTINCT e.stream_id FROM events e JOIN authoring_proposals p ON p.id = e.stream_id
    WHERE p.agent_run_id = ?1 AND e.stream_type = 'authoring_proposal' AND e.event_type =
    'proposal.amended' ORDER BY e.stream_id DESC LIMIT ?2`, collected into the same
    `HashSet<String>` the derivation already uses. `DISTINCT` means the bound now counts amended
    PROPOSALS rather than amendment EVENTS, so a proposal amended repeatedly no longer consumes the
    window several times over — the bound is spent on the thing being counted.

    Delete the combined read and the `for` loop that split it by `event_type`; `amended_before_accept`
    stays the intersection of the accepted-criterion id set with the amended id set, unchanged.

    **The proposal read.** Add `ORDER BY created_at DESC, id DESC` before its `LIMIT ?2`, matching
    `list_rejected_for_epic` exactly. The `id` tie-break is what makes the read stable when two rows
    share a `created_at` — ids here are ULIDs, so the tie-break is total and reproducible.

    Update the function's doc comment to state, in one sentence each, why the last-acceptance read
    carries no bound and why the amended read is distinct-by-proposal — both are the kind of
    deliberate asymmetry a later reader would otherwise "correct" back into the defect.

    Add the three cases to `packages/core/tests/authoring_measurement.rs`, using the established
    `UPDATE events SET occurred_at` control and passing a small explicit `limit` rather than
    manufacturing two hundred rows:

    - `the_last_acceptance_is_the_newest_even_when_the_event_count_exceeds_the_bound`: three or more
      accepted proposals with backdated, strictly increasing acceptance timestamps, measured with a
      limit smaller than that count; assert `last_accepted_at` is the newest timestamp and
      `elapsed_minutes` is computed from it. This must fail against the pre-fix `ASC LIMIT`.
    - `an_amendment_older_than_the_bound_still_counts_toward_amended_before_accept`: one criterion
      proposal amended and then accepted, plus enough later acceptances that the total event count
      exceeds the limit passed; assert `amended_before_accept` is 1. This is the guard against
      "fix it by ordering the combined read DESC", which would drop the amendment.
    - `the_proposal_read_is_stable_when_two_rows_share_a_created_at`: two proposals of the same run
      forced to the identical `created_at` by an `UPDATE`, measured twice with a limit of one;
      assert the two measurements are equal to each other. This is the spec-less probe's ordering
      row: equal elements have a specified, stable order.
  </action>
