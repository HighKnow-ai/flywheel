<objective>
**As a** solo developer running a fleet of agents, **I want to** stop, discard, crash out of or walk
away from a shaping conversation and have the board still make sense afterwards, **so that** an
authoring session is as safe to abandon as any other agent run.

D-84's whole argument for making an authoring session an `agent_run` was that Phase 3's supervision
apparatus — the watchdog, the heartbeat, the kill record, the `abandoned` reconciler, the session log,
cost tracking — already exists and should not be built twice. That inheritance is free for the
mechanisms but not for the *semantics*: `05-CONTEXT.md` leaves six questions open precisely because
D-35's Stop, D-66's Discard, D-64's closing summary, `mark_abandoned`, D-37's needs-you count and
D-52's spawn stagger were each written for a run with a task, a diff and a worktree, and an authoring
run has none of the three.

This plan answers all six. It also closes a question `STATE.md` has carried since Phase 4 —
*`mark_abandoned` is a third terminal path that writes no summary* — which `05-CONTEXT.md` explicitly
asks the planner not to widen silently. D-84 hands it a second kind of run to reconcile, so this is
where it gets answered rather than deferred again.

Purpose: make the supervision inheritance complete rather than partial.
Output: the summary subject generalisation and its migration, the authoring fallback synthesiser,
`mark_abandoned`'s answer, and the Stop/Discard/cost/count/stagger readings.
</objective>

**(a) Stop, for a conversation.** D-35's "interrupt, then force the whole process group" premise
holds unchanged — it is a statement about processes, not about worktrees — so an authoring run's Stop
reuses `stop_agent_run_recording_first` and `interrupt_agent_run_in_tx` exactly as they are. Plan
04-15's single-transaction guarantee carries with it: the terminal status and the summary land
together, which is why Task 1's authoring fallback had to exist before this one.

What changes is the surface copy, not the mechanism. `SessionSurface.tsx`'s Stop gloss for a task run
says the worktree was left as the agent left it; for an authoring run that sentence is meaningless.
Say what is true instead: the conversation ended and every staged proposal is still waiting on the
board. Assert that the staged proposals survive a Stop, because it is the reassurance the copy is
making.

**(b) Discard, for a conversation.** D-66's discard-asks-for-a-summary-first premise **also** holds —
the bounded wait exists so the agent can record what it learned before its context is thrown away,
and that is if anything more valuable for a conversation than for a diff. Keep it.

What does not hold is the destination. For a task run, discard means "start fresh on the same
worktree". An authoring run has no worktree, so discard means **start fresh on the same epic, primed
from the board** — which is exactly SHAPE-05's reopening path arriving from a different door. The
hand-off therefore pre-fills an authoring launch rather than a task launch, carrying the epic id (or
its absence) through the same `uiStore` channel plan 04-13 threaded for the task case. Staged
proposals survive untouched, and the new session is primed with them through the epic packet, so the
conversation can resume mid-shape rather than restarting.

**(c) `mark_abandoned`'s answer.** `STATE.md` records this as genuinely open: a run nobody watched
die may have no session worth summarising, and Phase 4 excluded it deliberately rather than by
oversight. D-84 changes the calculus by giving it a second kind of run, and this plan answers it
rather than widening the gap silently:

**An abandoned run gets a fallback summary, written inside `mark_abandoned`'s own transaction.** The
reasoning is that the Phase 4 objection — "there may be nothing worth summarising" — is an argument
about a *task* run, where the fallback is synthesised from a diff that may be empty. An authoring
run's fallback is synthesised from staged proposals and the stage reached, both of which are facts
that exist whether or not anyone was watching, and both of which are exactly what the reopening
packet needs. Making the rule uniform is also cheaper to reason about than a third terminal path
whose behaviour differs: `05-CONTEXT.md` asks the planner not to widen the gap, and closing it is
strictly better than documenting it again.

Apply it to both kinds of run, for one summary shape each, so `mark_abandoned` stops being the
exception. Record in its doc comment that this closes the `STATE.md` warning and why the Phase 4
reasoning did not survive contact with a second run kind.

Three of `05-CONTEXT.md`'s Discretion items are readings rather than features. Each gets an answer,
a one-line rationale in the code, and a test — because an unrecorded reading is one a later phase
re-litigates.

**(a) Cost attribution: an authoring run is an ordinary run.** Its `cost_usd`, `tokens_in` and
`tokens_out` are written from the terminal result event's summed usage block exactly as a task run's
are (the Phase 2 rule that token counts are written once from the terminal event, never accumulated
per message), and `StatusStrip` shows them unchanged. A conversation costs money and the developer
should see it while it is happening; there is no argument for a second accounting. Assert that a
completed authoring run carries non-null cost and token columns and that the strip renders them.

**(b) The needs-you count: a pending proposal does not join it.** D-46's rule is that only money
burning blocks, and D-37's rail count is the money-burning signal. A proposal waiting on a decision
burns nothing — the session may already have ended, which plan 05-08 asserts. So `board_blocked_summary`
and `board_recovery_summary` are both left untouched, the rail gains no badge, and a test asserts
both rollups return identical results with and without pending proposals present.

What *does* need a reading is the opposite case: an authoring run **blocked on a permission request**
is burning money and already joins the blocked count through the existing path, because it is an
ordinary run. Confirm that with a test rather than assuming it, since it is the case where the two
rules meet.

Record the rationale in `query/recovery.rs`'s doc comment beside the existing arms, phrased as the
distinction rather than the outcome: the rail answers "what is burning money and waiting on me", not
"what is waiting on me", and the triage lane and the epic-row count are where the second question is
answered.

**(c) The spawn floor: an authoring run counts.** D-52's stagger is keyed by repository path and
exists so parallel starts do not collide in `.git/index.lock`. D-86 puts the authoring session in the
project's registered main checkout — a repository, and the one the developer is most likely to also be
using. So `authoring_spawn` calls `SpawnFloor::wait_turn(repo_path)` exactly as `send_spawn_request`
does, with the same `SPAWN_FLOOR_MS` floor and no second constant.

The read-only posture does not exempt it: the floor protects against concurrent *starts*, and an
authoring session's own start-up reads (D-86's whole point is that it looks at the working tree) are
precisely the kind of concurrent git activity the floor was measured against. Assert that two
authoring spawns against the same repository path are separated by at least the floor, and that two
against different repositories are not.

**(d) Coverage**, extending `packages/core/tests/authoring_lifecycle.rs` and

unchanged by pending proposals; a permission-blocked authoring run appearing in the blocked count; the
rail rendering no proposal badge; and the two spawn-floor cases.
