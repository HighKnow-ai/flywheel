<objective>
**As a** solo developer running a fleet of agents, **I want to** walk away from a half-finished
shaping session and still find its proposals waiting on my board, **so that** an interrupted
conversation leaves work behind rather than nothing.

This is the half of D-80 that makes staging worth its migration. Proposals are durable board state,
not session state: *if staged proposals died with the session, the session would be the store of
record, which is precisely what the Core Value forbids.* A tray inside the authoring surface is where
they are decided while the conversation runs; the triage lane is where they exist afterwards.

D-82 puts the lane at board level rather than inside `ItemDetailPanel` for a concrete reason: a
wholly-staged new epic has **no row to hang a detail-panel section on**, and that is the exact case
SHAPE-01 is about. A lane serves both the fresh and the reopened path with one surface.

And it is built here rather than in Phase 6 on purpose. `ROADMAP.md`'s Phase 5 Notes call this phase
"the write path Phase 6 extends"; D-82 says the same of the surface. Phase 6's triage of
agent-proposed issues extends this lane rather than reinventing it, so its shape is a Phase 5
decision.

Purpose: make pending work visible where the developer already looks.
Output: the triage lane, the epic-row proposal count, and the route from a proposal back to the
session that produced it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model-authored text → the board surface | Proposal payloads are rendered on the board itself, outside the authoring surface |
| renderer → project-scoped read | A project id from the renderer selects which proposals are returned |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-08-01 | Information Disclosure | cross-project proposals in the lane | high | mitigate | `list_pending_proposals` is project-scoped with the id bound through `params![]`, and a two-project fixture asserts zero foreign rows; the query key includes the project id so a stale cache cannot render under another project |
| T-05-08-02 | Denial of Service | the lane's read at board volume | medium | mitigate | Bounded and cursor-shaped like every other board read, served by `idx_authoring_proposals_project_status`, and the 1,000-item budget is re-asserted with a populated lane |
| T-05-08-03 | Tampering | model-authored text rendered on the board | medium | mitigate | `ProposalRow` renders every payload field as React text content; the lane reuses that component rather than rendering payloads itself, so there is one place this property holds |
| T-05-08-04 | Elevation of Privilege | a lane-wide decision control | medium | mitigate | The header carries only a count and a collapse control; plan 05-06's accept-everything source gate scans `packages/desktop/src`, which includes this file |
| T-05-08-05 | Repudiation | a pending proposal lost when its session ends | high | mitigate | The abandoned-session case is asserted against all four terminal run statuses in Rust and rendered in React; nothing in the terminal paths deletes or hides a staged row |
</threat_model>
