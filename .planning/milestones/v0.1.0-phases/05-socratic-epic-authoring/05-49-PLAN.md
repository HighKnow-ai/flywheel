<objective>
Make the UAT harness answer a held staging call in-turn, and end the fixture divergence that let
twelve rounds of offline green coexist with live red.

Purpose: plan 05-48 makes the product return the id. This plan makes the harness capable of
supplying it, removes the structural in-turn emptiness of `proposal_list`, and adds the assertion
gap `G-05-10`'s `missing[3]` asks for.

contract, and a live-path assertion that fails when `proposal_list` is empty inside a staging turn.
</objective>

<measurement_record>
Read from the shipped source before this plan was written.

**The fixture divergence (this is the headline).** `scripts/uat/lib/fake-authoring-claude.mjs`
hand-writes `{ staged: true, id: ... }` as a scripted `tool_result` at lines 853, 865 and 905 — three
places. The real `stageAuthoringProposal` has never produced an `id` key at all. The offline
`--replay-check` slice therefore validated the harness against the fixture's own invention. Two
separate defects are stacked here and BOTH must be closed:
1. the key name is `id` in the fixture and will be `proposalId` in the product (plan 05-48), and
2. the fixture's tool results are scripted rather than derived, so nothing structurally prevents the
   next divergence.

**The harness handler seam is clean.** `drainInboundCoreRequests(sidecar, runId, { handlers: { ... } })`
takes an event-type-keyed handler map. It is called at exactly two live sites
(`scripts/uat/uat-08-socratic-authoring.mjs:5406` and `:6749`), each currently registering
`permission_request` and `board_read_request`. Adding `proposal_created` is a drop-in at both.

**The bridge already returns the id.** `packages/core/tests/bin/uat_authoring_ops.rs`'s
`apply-proposal-created` arm already prints `{"outcome": "created", "proposalId": proposal.id}`. No
change to the bridge binary is needed — the value the handler must relay is already on stdout.

**`assertAllHeldRequestsAnswered` comes for free.** `scripts/uat/lib/sidecar-harness.mjs` records any
inbound held request with no registered handler in `unansweredHeldRequests`. Once `proposal_created`
is a held call with a registered handler, a starved staging call surfaces itself through machinery
that already exists.

**Deliberate simplification, per the loop diagnosis.** `drainProposalsUntilQuiet` (with
`PROPOSAL_DRAIN_QUIET_MS` / `PROPOSAL_DRAIN_DEADLINE_MS`) was round 11's compensating mechanism for
proposals arriving after a stage advance. Once staging is held, the id-reachability property no
longer depends on it at all. It is NOT deleted — it still legitimately sweeps events that arrive with
no held caller — but its doc comment must stop claiming responsibility for reachability, so two
mechanisms are not left appearing to own the same property.
