<objective>
Expansion slice: the credential boundary — one explicit, auditable place, with both paths first-class.

Purpose: `PITFALLS.md` rates local-credential reuse as an existential dependency outside Flywheel's
control, and 02-RESEARCH.md sharpened that from a future risk into an already-enforced policy:
Anthropic's own current documentation states that third-party products may not offer subscription
login through the Agent SDK. That is exactly why this phase spawns the user's own `claude` binary
rather than driving the SDK, and exactly why D-39 makes the API-key path first-class from day one
rather than a later addition. This plan builds both paths, keeps the secret in the Keychain, and
proves the key can never reach a process listing.

Output: the Keychain-backed store, the settings schema with a global default and a per-project
override, the single resolver called once per spawn, and the backend-availability probe.

Boundary note: the Settings surface itself is plan 02-10. This plan builds the mechanism and its
command surface.
</objective>

## Flagged assumptions carried into this plan

**AGNT-03 was `unclassified` by the edge probe.** The assumption executed against: the local path
works because `claude -p`, run without bare mode, resolves the user's own already-stored session
from the system keychain exactly as it would in a terminal. Flywheel never reads, replays or stores
an OAuth token; it spawns the user's binary and inherits their environment. That boundary is what
makes "no credential ever leaves the machine" true by construction rather than by policy.

**RESEARCH.md assumption A1 is unresolved by documentation.** Whether `ANTHROPIC_API_KEY` alone
reliably overrides a present subscription session, or whether bare mode is required to force
API-key-only, is not stated by the fetched docs. Task 2 measures it. The stake is D-39's "a client
repository bills to an API key" guarantee, so a wrong assumption here bills the wrong account
silently — cheap to falsify, expensive to get wrong.

**Resolve once, immediately before the spawn.** In `packages/desktop/src-tauri/src/sidecar.rs`, add
`resolved_env_for_run(conn, project_id)` which calls `credentials::resolve_credential` and returns
the environment additions for that spawn. Call it at the point the spawn request is built — once per
spawn, not once at launch and not cached in `AppState`. A cached credential outlives the setting that
produced it, which would break the per-project override the moment a user changes it mid-session.

Attach the resolved environment to the spawn request. **The environment is the only channel**: the
argv builder has no credential parameter and must not gain one, because argv is visible in a process
listing while a child's environment is not. Do not log the resolved environment anywhere — not at
spawn, not on error, not in the session log writer. The sidecar receives an already-resolved
environment and never reads settings, never reads the Keychain, and never decides which credential
applies.

skills and tool configuration that the agent needs to do the task, so it is the wrong instrument here
even though it would force API-key-only. Instead:

    session exactly as it would in a terminal.
  - The API-key path spawns the identical invocation with the key added to the child's environment.
