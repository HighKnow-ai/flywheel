<objective>
Close gap 3 of 4 (`02-VERIFICATION.md`, CR-01 in `02-REVIEW.md`): this phase's migrations
`0003_agent_runtime.sql` and `0004_permission_gate.sql` added `triggers.target_task_id`,
`worktrees.task_id`, `agent_runs.task_id` and `permission_requests.task_id` as
`NOT NULL REFERENCES tasks(id)` with no `ON DELETE` clause, while `apply_pragmas` sets
`foreign_keys = ON` for every connection. `domain::task::delete_task` — written before those tables
existed — orphans `issues.task_id` and deletes `acceptance_criteria`, but knows nothing about the
four new tables. So deleting a task that has ever had Start Work pressed on it raises a raw
`FOREIGN KEY constraint failed`, rolls the transaction back, and reaches the user as an opaque string.
That is a regression in shipped functionality (task deletion), introduced by this phase, with no test.

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Decide the deletion semantics for a task with agent-run history</name>
  <decision>What happens when the user deletes a task that has agent-run history — block the deletion, or cascade the agent-runtime rows?</decision>
  <context>
This phase's migrations made four tables hold `NOT NULL REFERENCES tasks(id)` with no `ON DELETE`
clause, so SQLite's implicit `NO ACTION` currently blocks the deletion with a raw constraint error.
Nobody chose that; it is the default leaking through. `02-CONTEXT.md` records no locked decision about
task deletion (D-23 through D-39 cover worktree layout, branch topology, Start Work, watching, the
permission gate and credentials — none of them deletion), so this is genuinely undecided and must be
decided by you rather than guessed by the planner.

Why it is a one-way door: whichever semantics ships becomes the behaviour the board's delete action
publishes, and the schema-level form of Option B rebuilds four tables that a real database on your
machine already holds — SQLite cannot `ALTER` a column's foreign-key clause, so that form needs the
full create-copy-drop-rename rebuild and a forward migration to undo.

One fact that bears on both options: `events.task_id` is a plain `TEXT` column with **no** foreign key
to `tasks` (migration `0002_board_schema.sql`, line 121), so the append-only event log — including the
`agent_run.started` / `agent_run.interrupted` entries — survives the deletion either way. What Option B
destroys is the **structured** records (`agent_runs`, `permission_requests`, `worktrees`, `triggers`),
not the event stream.

A second fact: nothing in this product removes a git worktree yet. WORK-08 says a worktree is removed
only on explicit completion or user action, and no such path exists. So under Option B the directory at
`~/Flywheel/<PROJECT-KEY>/<TASK-KEY>/` — possibly holding uncommitted agent work — survives with
nothing on the board pointing at it.
  </context>
  <options>
    <option id="option-a">
      <name>Block the deletion, with a sentence the user can act on (recommended)</name>
      <pros>
Preserves the non-repudiable record of what an agent did on the task, which is this product's core
value ("every unit of agent work is anchored to a structured board item"). Cannot orphan an on-disk
worktree holding uncommitted work. Needs no migration, so the decision itself stays cheap to revisit:
it is a guard in one function, not a schema rebuild. Makes the schema's existing implicit restriction
legible instead of letting it leak as `FOREIGN KEY constraint failed`. Matches D-23's "one worktree per
task, ever" framing, where the worktree is a durable resource the task owns.
      </pros>
      <cons>
A task that was started by mistake cannot be deleted at all until a worktree-removal path exists
(Phase 3, "Nothing Lost, Nothing Left Running"). You would have to live with a stale row on the board
until then. Note that today's behaviour already blocks it — this option changes the error from opaque
to actionable, it does not newly forbid anything.
      </cons>
    </option>
    <option id="option-b">
      <name>Cascade the agent-runtime rows and let the task delete</name>
      <pros>
A task is always deletable; the board never carries a row you cannot remove. Implementable without a
migration (explicit deletes inside `delete_task`'s existing transaction, child-before-parent), in which
case it is as reversible as Option A.
      </pros>
      <cons>
Destroys the structured record of every agent run, permission decision and worktree for that task —
the event log survives, but the queryable history does not. Leaves the worktree directory on disk with
nothing in the board referencing it, and no product path to remove it. If you want the schema itself to
express the decision (an `ON DELETE CASCADE` clause rather than Rust-side deletes), that form requires
a `0006` migration rebuilding four tables via SQLite's create-copy-drop-rename procedure against a
database that already holds your real data — genuinely one-way.
      </cons>
    </option>
  </options>
  <resume-signal>Reply `option-a` or `option-b`. If you choose `option-b`, also say whether you want the Rust-side form (no migration, reversible) or the schema-level `ON DELETE CASCADE` form (a `0006` migration, one-way).</resume-signal>
</task>
