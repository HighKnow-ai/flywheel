<objective>
Close verification Gap 2: success criterion 3's live arm has never been exercised end to end. Every component on the path is unit-tested against synthetic fixtures and passes; the chain itself — a real `gh pr create` / `glab mr create` child process, a real poll of its output, a real status write — has never run.

The verifier's suggested test was a manual walkthrough against disposable authenticated repositories. This plan does not do that. The standing project preference is that verification is automated, and "requires a live authenticated forge" is a gap to close with tooling rather than a reason to hand the developer a procedure. So the chain is driven for real against a substituted CLI on the executable path: the only thing faked is the forge server. Everything the application actually owns — argv construction, body transport, process spawn, JSON normalisation, baseline reconstruction from the append-only log, the transaction that writes the status — runs exactly as it does in production.

Purpose: turn the single largest untested surface in the phase into a durable check that re-runs for free on every future commit, instead of a one-off walkthrough that cannot be repeated.

Output: `packages/core/tests/forge_live_chain.rs`, one test command, both forges.

**What this harness does not reach, stated plainly:** whether the real GitHub and GitLab APIs still emit the JSON shapes these adapters read. No local harness can answer that. That guarantee stays with the existing one-command live arm from plan 07-08 — `cargo run -p core --bin forge_probe -- --both <repo>:<branch> <repo>:<branch>` — which is one copy-pasteable command against real repositories, not a procedure. It is not a prerequisite for closing this gap.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| harness → executable path | The harness mutates a process-global environment variable to substitute a CLI, which every other test in the binary would observe if it were not serialised |
| substituted CLI → normaliser | Attacker-shaped JSON reaching a defensive `serde_json::Value` read |
| harness → real forge | The boundary that must never be crossed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-12-01 | Tampering | the real forge | high | mitigate | The harness reaches only the stub it wrote: the stub records every invocation and the harness asserts the marker exists before trusting a result, so a failed substitution fails the test instead of creating a real request |
| T-07-12-02 | Information Disclosure | forge credentials | medium | mitigate | No credential is read, written or named; the suite is asserted to pass with the authentication variables unset |
| T-07-12-03 | Denial of Service | path mutation racing other tests | medium | mitigate | A module-level mutex serialises every substitution and the original path is restored before each closure returns, following `forge_degrade.rs`'s own documented pattern; each integration-test file is its own binary, so the static cannot race across files |
| T-07-12-04 | Tampering | body transport | high | mitigate | The harness reads what the child actually received and asserts the body is absent from the recorded argument vector, so the off-argv transport is proven through a real spawn rather than from a pure function |
| T-07-12-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed: the harness uses `tempfile`, already a dependency, and a shell stub; `packages/core/Cargo.toml` is asserted unchanged, so no package-legitimacy checkpoint applies |
</threat_model>
