<objective>
Make `git log` self-describing: every commit on a `flywheel/`-namespaced branch carries
`Flywheel-Task:` and `Flywheel-Run:` trailers, written by a `commit-msg` hook installed beside
the Phase 12 pre-push hook in the same per-project `core.hooksPath` directory.

**Phase goal (ROADMAP, verbatim):** Cyril can answer "where does this task actually stand in git
and on the forge?" from the board, without opening a terminal.

This is the write half of Phase 7's round trip — plan 07-05 reads these trailers back. It catches
the user's own hand-typed commits, not only an agent's, because a git hook fires for every commit
and a model instruction does not.

Purpose: a hash in a `git log` three months from now must still name its board item with no
database present. Output: a second generated hook, its install/uninstall pair, and a real-git
integration test.
</objective>

<decisions_resolved>
- **Trailer-append mechanism (discretion, RESEARCH.md open question 2): `git interpret-trailers
  --if-exists doNothing --in-place`.** It is purpose-built for exactly "append if absent, never
  duplicate" and handles the two cases a `grep -q` plus `printf >>` guard gets wrong — an existing
  trailers block with no blank-line separator, and trailing whitespace before it. The hook already
  shells out to the baked real git for `rev-parse`, so this costs no new dependency and no new
  `PATH` resolution. `--if-exists doNothing` is what makes a `git commit --amend` idempotent.
- **Trailer ordering (discretion): `Flywheel-Task:` first, `Flywheel-Run:` second** — two
  `--trailer` arguments in that order on one `interpret-trailers` invocation. The task key is the
  identifier a human scans for; the run id is the follow-up.
- **The task key extraction, and RESEARCH.md assumption A2.** The branch shape is
  `flywheel/<key-lowercased>` optionally followed by `-<slug>`, and the key itself is
  `tasks.key` lowercased — which for this project is `<prefix>-<n>`. The script therefore
  extracts with `sed -n 's#^flywheel/\([a-z0-9]\{1,\}-[0-9]\{1,\}\).*#\1#p'` and, critically, the
  test file asserts that extraction against `branch::task_branch_name`'s **real output** for
  several keys and titles — including a title whose slug begins with a digit and a title
  containing non-ASCII bytes — rather than against a hand-written branch string. A branch that
  does not match (notably `flywheel/epic/...`, which has no `<n>` in the first segment) yields an
  empty key and the hook exits 0 writing nothing, because a trailer naming the wrong task is
  worse than no trailer at all.
- **The one-way rating on Task 1 deliberately carries no preceding `checkpoint:decision`.**
  `REVERSIBILITY_GATES` is on and D-125 is genuinely a one-way door, so the rating is recorded on
  the task. No checkpoint is inserted because `07-CONTEXT.md` already records the developer
  choosing this exact option — two trailers, these two exact keys, rejecting both the task-key-only
  and the three-line `Flywheel-Epic:` alternatives — with the one-way rating attached. Inserting a
  gate here would re-ask a question the discuss phase already answered, which
  `gsd-core/references/planner-reversibility.md` names as an anti-pattern ("Gating a decision
  already made … the door is already walked through. Keep the rating for the record; do not insert
  a checkpoint to re-ask"). Expect `verify plan-structure` to emit the corresponding advisory
  warning for this plan; it is accepted, not an oversight.
- **Two sibling install functions, not one merged installer.** `install_pre_push_hook` keeps its
  name, signature and `PrePushInstall` outcome type — `packages/core/tests/git_hooks_pre_push.rs`
  is ~860 lines of tests bound to them, and churning that surface buys nothing. The one shared
  predicate that must widen is `is_flywheel_hooks_dir`, so a directory holding either marked hook
  is recognised as Flywheel's regardless of which install ran first.
</decisions_resolved>

|----------|-------------|
| Flywheel → the developer's own repository configuration | installing a hook sets `core.hooksPath`, which **replaces** the repository's default hooks directory for every linked worktree |
| the git branch name → a trailer value in permanent history | a branch name is attacker-influenceable only by whoever can create a branch in the repository, but its parsed key is written into immutable history |
| the hook's environment → the trailer value | `FLYWHEEL_RUN_ID` is read from the committing process's environment |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-02-01 | Tampering | `install_commit_msg_hook` vs. the developer's own hook chain | high | mitigate | The install applies the identical, not a weaker, refusal logic the pre-push install already has: refuse a `core.hooksPath` holding neither marked hook, and refuse a pre-existing executable `commit-msg` in the default hooks directory. Both refusals are returned values rendered on stderr, never silent. |
| T-07-02-02 | Tampering | the generated script's branch-namespace guard | high | mitigate | `core.hooksPath` is repository-wide (this codebase does not enable `extensions.worktreeConfig`), so the hook fires for the main checkout too. The `case "$branch" in flywheel/*) ;; *) exit 0 ;; esac` early-out runs before any write, and `commit_msg_hook.rs` asserts a `main`-branch commit is left byte-identical. |
| T-07-02-03 | Spoofing | the task key parsed out of a branch name | medium | mitigate | The extraction accepts only `[a-z0-9]+-[0-9]+` in the first segment after the namespace, and an empty extraction exits 0 writing nothing — a trailer naming the wrong task is worse than no trailer. The test asserts extraction against `branch::task_branch_name`'s real output rather than a literal. |
| T-07-02-04 | Tampering | `interpret-trailers` invoked from inside the hook | low | mitigate | The invocation uses the absolute real-git path baked in at install time through `shell_quote`; the hook performs no `PATH` search, so a shell-init `PATH` reorder cannot redirect it (the round-ten discipline in `docs/destructive-gate-trust-boundary.md`). |
| T-07-02-05 | Information Disclosure | `FLYWHEEL_RUN_ID` written into permanent git history | low | accept | A run id is a ULID minted by this application; it names a local database row and discloses no credential, path or user identity. |
| T-07-02-06 | Denial of Service | a failing hook blocking the user's own commits | medium | mitigate | Every guard path exits 0; the only non-zero status the script can return is `interpret-trailers`' own, on a branch Flywheel itself created. A refused install reports on stderr and leaves commits entirely unhooked rather than half-hooked. |

**Canon referral:** command-injection hardening of the generated script is canon — covered by
`/gsd-secure-phase` and by T-07-02-04 above; not minted as a separate prohibition here.
