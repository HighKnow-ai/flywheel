<objective>
Put the forge on the item: the request's state, its CI result with a link out to the run, a
board-visible flag when the build is red, the unresolved-criteria marker a merge can raise — and
nothing at all where no forge is configured.

**Phase goal (ROADMAP, verbatim):** Cyril can answer "where does this task actually stand in git
and on the forge?" from the board, without opening a terminal.

Plan 07-03 built the adapter and plan 07-07 made it drive the status column. This plan is where
the user finally sees it. It also carries the phase's one genuinely live check: GitHub and GitLab
both reached against real projects, run as a single command rather than a manual walkthrough.

Output: `ForgeSection.tsx`, two Tauri commands, the board-row CI flag, the forge override in
Settings, and the live two-forge verification.
</objective>

<decisions_resolved>
- **The item panel's forge read is live; the board's flag read is from the log.** A request's state
  and CI result are read by shelling out when the panel is open (D-75's derive-at-read-time, and
  one `gh`/`glab` call per panel open is affordable). The board cannot shell out once per row, so
  the row flag is read from the `forge.ci_failed` and `task.done_with_unmet_criteria` events the
  poll job already writes — the same append-only log `board_blocked_summary` and
  `board_recovery_summary` already read from. Two read paths, one source of truth: git and the
  forge, with the log as the record of what was observed.
- **D-120's absence, implemented as `return null` before any header.** `ForgeSection.tsx` follows
  `WorktreeSummary.tsx`'s precedent and not `ActivityTrail.tsx`'s: with `Forge::Local` it renders
  nothing — no labelled empty state (rejected: permanent furniture on every item of a project that
  may never have a forge) and no project-level notice (rejected: a third place to look).
- **Error presentation (discretion, RESEARCH.md open question 3) — three distinct readings.**
  *No forge configured* renders nothing at all. *CLI not installed* renders a one-line notice
  naming the missing command and that a forge is configured for this project. *CLI not
  authenticated* renders a one-line notice naming the command to run. `CliFailed` and
  `MalformedJson` render a generic one-line "could not read the forge" notice carrying the error
  *category* only — the CLI's raw stderr stays core-internal, the same discipline
  `sidecar.rs`'s `emit_persistence_failure_notice` already applies to OS error text.
- **The CI flag reuses the existing row-pill mechanism (D-124, D-37).** It is a third pill
  alongside blocked and needs-decision in `BoardRow.tsx`, read through a `useForgeFlags` sibling
  of `useBlockedSummary` — not a new indicator mechanism, not a colour-only cue, and it never
  touches the status column.
- **The unmet-criteria marker (D-123) renders in the forge section, not in the criteria list.**
  It is a consequence of a forge merge, so it belongs beside the merge that caused it; the criteria
  themselves stay exactly as unchecked as they are in `AcceptanceCriteriaList.tsx`, which this plan
  does not touch.
- **The forge override is a Settings row (D-119).** A per-project select with four values —
  Detected, GitHub, GitLab, Local only — where "Detected" writes NULL. It lives beside the existing
  per-project credential override, which is the same shape.
</decisions_resolved>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| forge CLI output → the renderer | third-party content, including a title and a URL, reaches the UI |
| forge CLI stderr → the renderer | diagnostic text that may name local paths or tokens-adjacent detail |
| renderer → `settings_set_project_forge` | a value that selects which external binary is later spawned |
| the board's paint path → the event log | a per-row read on the hot rendering path |
