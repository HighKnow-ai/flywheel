<objective>
Close the second `missing:` item of verification Gap 1: **a wall-clock timeout around every `gh`, `glab` and `git` child process.**

Today `spawn_gh` (`forge/github.rs:35`), `spawn_glab` (`forge/gitlab.rs:34`) and `spawn_git` (`git.rs:37`) each perform an unbounded capture-and-wait. Code review WR-02 recorded this as a problem independent of the locking structure: even once plan 07-11 moves these calls out of the database mutex, a hung child still never completes and the scheduler tick that spawned it is starved forever.

Purpose: bound the hang at its root. These three functions are the only subprocess spawn sites in the git/forge path — a guard placed in one shared helper they all call covers every present and future caller, which is why this is a shape fix rather than a per-call-site patch.

Output: `packages/core/src/proc.rs` with one bounded-wait function, the three spawn helpers routed through it, and `packages/core/tests/subprocess_timeout.rs` proving the kill happens and the routing holds.
</objective>

    Behaviour, in order:
    1. Configure the child's three streams. Standard output and standard error are set to `Stdio::piped()`. Standard input is set to `Stdio::piped()` when `stdin` is `Some`, and to `Stdio::null()` when it is `None` — `Stdio::null()` is load-bearing, not tidiness: the previous unbounded capture call closed standard input implicitly, and a bare `spawn()` would instead inherit it and let a CLI block on an interactive prompt (one of the three hang modes code review CR-01 names).
    2. `cmd.spawn()?`. A spawn failure propagates unchanged, so `run_gh`'s existing `ErrorKind::NotFound` arm still maps to `ForgeError::CliNotInstalled`.
    3. Take the child's `stdout` and `stderr` handles and move each into its own `std::thread::spawn` closure that reads it to end into a `Vec<u8>`. Both must be drained concurrently with the deadline watch — a child writing more than the pipe buffer holds would otherwise block on its own write while this function waits for it to exit, and neither would ever progress.
    4. When `stdin` is `Some(bytes)`, take the child's `stdin` handle, move it plus an owned copy of the bytes into a third thread that writes them and drops the handle (closing it). Doing this off the calling thread is for the same reason as step 3: a child that never reads its input must not be able to block the deadline watch.
    5. Poll `child.try_wait()` in a loop with a `std::thread::sleep` of 50 milliseconds between attempts, until either an exit status is observed or `std::time::Instant::elapsed` since the start exceeds `timeout`.
    6. On the deadline path: call `child.kill()`, then `child.wait()` to reap it, then join the reader threads, then return `Err(std::io::Error::new(std::io::ErrorKind::TimedOut, format!("{label} exceeded {}s and was killed", timeout.as_secs())))`. The error text carries only `label` and the ceiling — never the captured stdout or stderr, so a token a failing CLI echoed cannot be relocated into a log line by this path.
    7. On the normal path: join the reader threads and return `Ok(Output { status, stdout, stderr })`, assembled from the observed status and the two drained buffers.

    A reader thread that panics is not a reason to fail the call: treat a join error as an empty buffer for that stream, keeping this function's failure modes limited to spawn failure and timeout. Document that the only pid this function ever signals is the one its own `spawn` returned.
