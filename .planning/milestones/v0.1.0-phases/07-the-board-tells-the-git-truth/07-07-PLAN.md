<objective>
The board status column starts following the forge — forward only, on the edge, and then it hands
the column back.

**Phase goal (ROADMAP, verbatim):** Cyril can answer "where does this task actually stand in git
and on the forge?" from the board, without opening a terminal.

This is the one plan in the phase that writes to the status column, which Phase 2's D-29 declared
nothing ever moves out of. D-121 reconciles the two: the column does gain automatic outward moves,
but the mechanism is *structurally incapable* of overwriting the user in a loop, because it fires
on a transition it observes once and never re-asserts a level.

Output: a fourth scheduler job polling the forge, the edge detector, a transaction-scoped status
writer, and the restart-safe baseline that makes "edge" mean something across an application
restart.
</objective>

<decisions_resolved>
- **RESEARCH.md open question 1 — the baseline is derived from the `events` log, not a new
  column.** `query::forge::latest_forge_baseline(tx, task_id)` reads the most recent
  `forge.state_changed` / `forge.ci_failed` event for the task and reconstructs the last observed
  `(ForgeState, CiResult)` from its payload. This follows the crate's own D-75/D-128 discipline —
  derive at read time, never add a second source of truth — and it is durable across an
  application restart for free, which is exactly what Pitfall 3 requires. No migration, no
  mutable column, and the record distinguishing an automatic transition from a human one is the
  same `events` trail that already exists.
- **One transaction per observation, with the baseline read inside it.** `apply_forge_observation`
  opens the transaction, reads the baseline, decides, writes the status through
  `set_task_status_in_tx`, appends its own events, and commits. This is what makes the LINK-05
  concurrency edge true by construction rather than by a lock: two overlapping polls serialise on
  SQLite's own write transaction, and the second one reads the first one's baseline.
- **`set_task_status_in_tx` is extracted, and `set_task_status` delegates to it.** The existing
  public function keeps its exact signature and behaviour — including its no-op guard, its event
  payload and its label — and becomes a thin wrapper that opens a transaction and calls the new
  one. This is the crate's established `*_in_tx` idiom (`accept_proposal_in_tx`,
  `interrupt_agent_run_in_tx`) and it is what lets the edge detector avoid a nested transaction
  without ever issuing a raw `UPDATE tasks SET status`.
- **Forward-only, two transitions, per D-122.** `ForgeState::Open` (or `ChangesRequested`, which
  is still an open request) rising from `None` → `in_review`; `Merged` rising from anything →
  `done`. `ChangesRequested` rising from `Open`, `ClosedUnmerged` rising from anything, and
  `CiResult::Failed` rising from anything each append an event and call no status writer at all.
  D-122's two rejected backward moves are named in the module's doc comment so a later reader
  does not add them.
- **Poll cadence: a fourth scheduler job at `FORGE_POLL_SECS = 120`.** Declared beside plan
  07-01's three interval constants, in the same one place. A forge read never rides the hot git
  tick — the anti-pattern `07-RESEARCH.md` names explicitly, because `gh`/`glab` hit a real API
  rate limit that local git reads never do.
- **A forge error is not an observation.** `ForgeError` from the poll is an `eprintln!` value that
  writes nothing — no baseline move, no event, no transition. An unreachable forge must never be
  mistaken for a closed request.
- **D-123's unresolved marker is an `events` row, not a column.** On the merged edge the detector
  counts the task's unmet, non-superseded criteria and, when that count is above zero, appends
  `task.done_with_unmet_criteria` carrying the count and a `label`. It never touches a criterion
  row: the criteria stay exactly as unmet as they were, which is the whole point.
</decisions_resolved>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| forge observation → the board's status column | third-party state drives a write to the most visible field in the product |
| background job → the status writer | an automatic mutation with no human in the loop |
| the forge's view of "done" → the project's acceptance criteria | a merge can carry a task to Done past criteria nobody checked |

## STRIDE Threat Register

| T-07-07-01 | Tampering | a forge observation overwriting a manual board move | critical | mitigate | D-121's edge semantics: the detector writes only on an observed change against a baseline read from the append-only log, and never re-asserts a level.
