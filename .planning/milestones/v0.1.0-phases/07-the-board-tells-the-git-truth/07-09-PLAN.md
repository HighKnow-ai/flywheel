<objective>
The board item becomes the pull request. The user presses one action on the task and Flywheel
opens the request on the forge, titled from the task and described from its acceptance criteria
and session summaries — having shown them the body first.

**Phase goal (ROADMAP, verbatim):** Cyril can answer "where does this task actually stand in git
and on the forge?" from the board, without opening a terminal.

D-118 states the reason plainly: this is the product thesis applied literally to the forge. The
board already holds the title, the criteria and the record of what each session did; re-describing
all of it in a web form is the work the board exists to eliminate. It is also the one action that
advances a task to In Review, so leaving it outside the app would leave the loop open.

Output: deterministic draft assembly, a `create_request` arm on each adapter, one Tauri command,
and a preview-then-open action on the forge section.
</objective>

<decisions_resolved>
- **Assembly is a pure function over board state, and the preview is the same function.** The
  action first calls a read-only command that returns the assembled `RequestDraft`, renders it on
  the item, and only sends it when the user confirms. The preview and the send call the *same*
  assembly function, so what the user approved is what reaches the forge — the privacy prohibition
  above is satisfied by construction, not by a promise. This mirrors `context_packet.rs`'s own
  determinism rule (CTX-04) and the launch sheet's "see the briefing before tokens are spent"
  shape from plan 02-04.
- **Body on stdin (GitHub) or a temporary file (GitLab), never argv.** `gh pr create --body-file -`
  reads standard input. `glab mr create --description-file <path>` reads a file, so the GitLab arm
  writes the body to a `tempfile::NamedTempFile` with owner-only permissions and passes its path,
  deleting it when the call returns. A multi-kilobyte body in argv would be both truncatable by
  the platform's argument limit and visible in a process listing — the same reasoning
  `credentials.rs` already records for secrets.
- **Opening a request writes no status.** The task reaches In Review when the forge poll next
  observes the request, through plan 07-07's single edge detector. Writing the status here too
  would create a second status-writing path for the same fact — exactly the duplication D-121's
  single-mechanism design exists to avoid. The item's own forge section refreshes on the next
  `board:changed`, so the user sees the request immediately regardless.
- **Body shape (discretion):** the task's title as the request title; the body as three labelled
  sections — the task key and a one-line statement of what the task is, then its current-revision
  acceptance criteria as a checklist with each criterion's verification hint where present, then
  the session summaries in chronological order. No diff, no commit list: the forge renders both
  itself, and duplicating them is noise a reviewer scrolls past.
- **Draft title and body are plain text, and the criteria checklist reflects the real `checked`
  state.** An unchecked criterion renders unchecked. The request is not an occasion to present the
  work as more complete than the board says it is.
- **The action's three absence conditions.** No forge configured (the whole section is already
  absent, D-120); no worktree (no branch to open a request from); a request already exists for
  the branch (the section renders that request instead). None of these is an error state — the
  action simply is not there.
- **No agent path, and no schedule.** D-118 rejected having the agent open the request as its last
  act, for the reason it records: an agent that misjudges "done" would then push a branch and open
  a request on a real forge. This plan adds no tool, no MCP surface and no scheduler job that can
  reach `create_request` — asserted by a grep that the only caller is the one Tauri command.
</decisions_resolved>
