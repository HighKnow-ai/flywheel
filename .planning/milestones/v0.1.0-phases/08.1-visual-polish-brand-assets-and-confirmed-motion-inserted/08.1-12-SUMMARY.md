# Phase 08.1 Plan 12: Inline Challenges Summary

**An epic's open agent challenges now render as 48px rows above its tasks inside the one virtualized rack, and Accept or Reject on them goes through the tray's own mutations so the task, the epic's total and the pending list refresh on the core's `board:changed` push.**

## Performance

- **Duration:** about 22 min (the start time was not captured by a command; estimated from the first test run)
- **Completed:** 2026-10-08T07:15Z
- **Tasks:** 2
- **Files modified:** 7 (3 source, 1 new component, 1 new test file, 2 RED-evidence records, plus the deferred-review register)

## Accomplishments

- `ChallengeRow` renders a proposal in `ProposalRow`'s vocabulary (uppercase target type, verb when not `create`, title) at the A-03 challenge height. The agent's text is React text only.
- `BoardView` emits `challenge` rows into the same flat rows array before an expanded epic's tasks, from the proposals it already fetches. No new query, no second virtualizer, no nested list. An epic with none emits nothing.
- The epic header's proposal count and the challenge rows now come from one grouped list.
- Accept and Reject call `useAcceptProposal` and `useRejectProposal` with the proposal id only. No optimistic removal; a failure leaves the row, shows an alert and stays retryable.
- The tray and the triage lane are untouched. Their own test files pass unchanged.

**The real board has no challenges.** `authoring_proposals` in the live database holds 0 rows, so no challenge row appears on the real board today. Nothing was seeded to make the surface look populated. The comp's "3 challenges" were fixture values.
