## Summary

The four non-presentational Rust surfaces the brief singled out are sound. Findings below are what I could
prove; the verified-sound list is short on purpose.

Verified sound (no finding):

- **Lock-safe split in `change_flags`.** `commands/change_flags.rs` takes the mutex, runs only
  `change_flag_inputs` (no process spawn), drops `conn` explicitly, then runs git in `spawn_blocking`.
  The split holds.
- **`has_worktree` filter.** It is one `concat!` literal. Six `named_params!` sites bind `:has_worktree`:
  `mod.rs` 286, 331 and 407, and `search.rs` 190, 237 and 312. Every query that splices `FILTER_WHERE`
  also supplies a `kind` column and `:project_id`. The epic half is keyed on `b.kind`, not `epic_id`.
- **`board_epic_progress` bound.** The result size is bounded by epics times five statuses, plus the
  explicit `EPIC_ROSTER_CEILING` error. The allowlist note is accurate.
- **Decline path.**
  - `request_changes` re-derives state inside its own transaction, so a stale `Ready` cannot write.
  - The status write goes through `set_task_status_in_tx`, and the event is appended in the same
    transaction.
  - A double click returns `AlreadySentBack`.
  - The command takes a task id only, and no raw error text crosses IPC.
  - The marker is cleared by a later `task.status_changed` to `in_review`.
- **Security surface.** `capabilities/default.json` changed only in its `description` string. The real
  command boundary is `generate_handler!`, and the three new commands take only ids. No renderer text
  reaches git or SQL. No colour literals exist outside the token files.

Not re-reported, because they are already recorded as open: the epic lens showing every roster epic with
the aggregate's unfiltered count under an active filter (`deferred-items.md`, escalated to the owner), and
the missing blocked-duration feed for `summaryLine`.

## Warnings

### WR-01: One bad worktree row blanks every change cue on the board

**File:** `packages/core/src/query/change_flags.rs:84-103`
**Issue:** The doc comment says a vanished worktree "gets no annotation" and cannot poison the sweep.
That holds only for the `path.is_dir()` check. Everything after it uses `?`:

- `crate::git::ahead_behind(...)?` returns `Err` when the branch no longer exists. `rev-list base...branch`
  fails with "unknown revision".
- `porcelain_entries(path)?` returns `Err` when the directory exists but is no longer a usable worktree.
  Examples: a pruned admin dir, a dangling `.git` file, a path replaced by a plain directory.

Either error aborts `finish_change_flags` and `board_change_flags` returns `failed:board_change_flags:git`.
The whole project loses every ahead and dirty cue, and the rail's Worktrees count. TanStack Query then
retries the failed query (default 3 retries), and each retry re-runs the full serial sweep.

This is the state the app's own orphan-recovery flow exists to handle (worktree row `active`, directory
or branch gone), so it is reachable. `core/tests/change_flags.rs` has no test for a vanished directory or a
broken worktree, so the documented skip is itself untested.

**Fix:** Make each worktree independent:
```rust
for input in inputs {
    let path = Path::new(&input.path);
    if !path.is_dir() { continue; }
    let ahead = match &input.base {
        Some(base) => crate::git::ahead_behind(path, base, &input.branch).ok().flatten().map(|(a, _)| a),
        None => None,
    };
    let Ok(entries) = crate::domain::worktree::porcelain_entries(path) else { continue };
    flags.push(ChangeFlag { task_id: input.task_id, epic_id: input.epic_id, ahead, dirty: !entries.is_empty() });
}
```
Add two tests: one with the worktree directory removed, one with the branch deleted. Each asserts that the
other worktree's flag is still returned.

### WR-02: `useChangeFlags` is mounted twice, so its coalescing and its refetches double up

**File:** `packages/desktop/src/board/useBoardQuery.ts:1125-1157` (callers `board/BoardView.tsx:490`, `projects/ProjectRail.tsx:157`)
**Issue:** The 1s coalescing lives inside the hook's `useEffect`, so it is per mounted instance. The hook
is now mounted by both `BoardView` and `ProjectRail`, for the same project. Each instance has its own
`subscribeBoardChanged` listener and its own timer. One burst of `board:changed` events therefore produces
two `invalidateQueries` calls. `invalidateQueries` cancels and restarts an in-flight refetch by default
(`cancelRefetch: true`). The cancellation only aborts the JS promise. The Rust `spawn_blocking` sweep
cannot be cancelled and keeps running, so overlapping sweeps accumulate.

At the current 5 worktrees this is cheap. At the 200-worktree cap, with the roughly 48 ms per worktree the
plan cites, a sweep is about 10 s. Any board churn faster than that keeps cancelling the fetch, so the
cues can starve while the sweeps stack up.

The rail also prints `Worktrees` as `data?.length`. That is the number of successfully measured,
still-present, capped (200) flags. It is not the number of active worktrees, and it disappears silently
when the sweep fails (see WR-01).

**Fix:** Pass `{ cancelRefetch: false }` as the second argument to `invalidateQueries`, so a sweep in
flight is reused instead of restarted. Move the subscription and timer out of the hook body into one
module-level or app-level subscriber, or at least make only one instance subscribe. For the rail count,
either label it "Measured" or add a cheap `COUNT(*)` of active worktrees to the board half.

### WR-03: `GroupItems.truncated` is computed but nothing reads it

**File:** `packages/desktop/src/board/useBoardQuery.ts:1289` (consumer would be `board/BoardView.tsx` rows memo, ~line 560)
**Issue:** The phase's purpose was to stop a group from looking complete when it is a prefix: the
"plausible and wrong" failure of the 200-row page. `useGroupItemsMany` sets `truncated: total > 500`, but
`pickGroupData` returns the `GroupItems` objects and `BoardView` reads only `.items`. Grep finds no consumer
of `.truncated` outside the hook. A group with more than 500 rows (an epic, the no-epic bucket, a status
band) renders its first 500 rows, under a header that prints the true count and an `aria-setsize` of the
true total, with no indication that rows are missing.

The summary records this as "a guard rather than a live constraint" today (largest band 193). The guard has
no output. The first project that exceeds 500 gets exactly the silent short list the phase set out to
remove.

**Fix:** In the rows memo, when `fetchedGroups[index]?.truncated` is true, emit a final non-selectable
notice row after the group's tasks. Use the existing `challenge` height or add a fifth kind. For example:
"Showing 500 of 640. Narrow with a filter." Alternatively, surface it beside `epicRosterNotice`.

### WR-04: A roster epic bypasses the Done-with-unchecked-criteria warning

**File:** `packages/desktop/src/board/BoardView.tsx:204-216` (`rosterEpicItem`), used at 775-796 (`requestStatusChange`)
**Issue:** `rosterEpicItem` builds the epic's selection target from the roster and copies only `status`
from the board window. It drops `criteriaChecked`, `criteriaTotal`, `priority`, `rank`, `estimate` and
`assigneeId`, even when the full window row exists. `requestStatusChange` resolves its subject with
`selectableItems.find(...)`, which returns this placeholder, so `checked` and `total` are both 0.

The row-level pickers refuse a roster epic via `isRosterEpic`, but the detail panel's `onSetStatus` does
not go through that guard. `ItemDetailPanel` shows its Status control whenever `item.status` is truthy,
and it is truthy for any epic that happens to be in the 200-row window. An epic moved to Done from the
panel therefore skips `DoneWarning` even when it has unchecked criteria. D-08 ("warn, never block")
silently becomes "never warn" for epics reached from the home surface.

`EpicSummary` now carries `status` (08.1-14), which `rosterEpicItem` also ignores.

**Fix:**
```ts
function rosterEpicItem(id, key, title, window, rosterStatus?: string): BoardItem {
  const loaded = window.find((i) => i.id === id);
  if (loaded) return loaded; // carries criteria counts, rank, priority, estimate
  return { id, kind: "epic", key: key ?? "", title: title ?? "", status: rosterStatus ?? "",
           rank: "", priority: 0, epicId: null };
}
```
Keep `isRosterEpic` keyed on the row, not on the item, so the pickers stay refused. Add a test: epic with
`criteriaTotal: 3, criteriaChecked: 1` in the window, Done chosen from the detail panel, and `DoneWarning`
is shown.

### WR-05: Selection logic still reads the 200-row window, while the rack renders group-fetched rows

**File:** `packages/desktop/src/board/BoardView.tsx:398-416` and `packages/desktop/src/board/CommandPalette.tsx:162-163, 232-262`
**Issue:** After A-01/A-02 the rack's rows come from `useGroupItemsMany`, up to 500 per group. Two consumers
still reason about the unscoped, unfiltered `board_list` window of 200.

1. **BoardView selection-follows effect.** It re-selects "the nearest surviving neighbour" when
   `selectedId` is absent from `items` but present in the previous `items`. A task that is still
   rendered, in its epic group or in the Done band, drops out of the 200-row window as soon as a status
   change sorts it past row 200. Its selection then jumps to an unrelated windowed item. That item may be
   inside a collapsed epic, so the user's cursor vanishes from the screen.
2. **CommandPalette.** It builds `items` from its own `useBoardQuery(open ? id : undefined)`. That is the
   window with no filter or search term. `move-down`, `move-up`, `select-first` and `select-last` walk the
   window order, not the rack order that `j`/`k` walk. `selectedItem` is `undefined` for any task that
   only exists in a group fetch. The palette then enables "Set status", "Set priority" and similar
   (the `disabled` check tests only the id), and `if (selectedItem) setOverlay(...)` does nothing. The
   command appears to work and silently does not.

**Fix:** Drive both from the rack. Lift `selectableItems` into the store as ids or items, or expose
`resolveItem(id)`. Have the selection-follows effect compare against `selectableItems` rather than
`items`. Have the palette read the same list, and disable the commands whose subject it cannot resolve.

### WR-06: Epic "agents running" omits epic shaping (authoring) runs

**File:** `packages/core/src/query/epic_progress.rs:92-105`
**Issue:** The agent-count query uses `JOIN tasks t ON t.id = a.task_id` and groups by `t.epic_id`. Since
migration 0010, authoring runs have `task_id IS NULL` and `epic_id` set (the table CHECK forbids both). An
inner join drops every one of them. An epic with a live or blocked Socratic shaping session therefore
renders "0 agents", and the summary line's "N agents running" under-counts. A-01 specifies "a count of
agents running on the epic", and a shaping session is an agent running on the epic. No test covers
`agent_runs` with a NULL `task_id`.

**Fix:**
```sql
SELECT COALESCE(t.epic_id, a.epic_id), a.status, COUNT(*) FROM agent_runs a
LEFT JOIN tasks t ON t.id = a.task_id
WHERE a.project_id = ?1 AND a.status IN ('running','blocked')
GROUP BY COALESCE(t.epic_id, a.epic_id), a.status
```
If excluding authoring runs is deliberate, say so in the module doc and in the header's accessible name,
and add a test that pins it.

## Info

### IN-01: `seed_criteria` is a data-mutating tool compiled into the product crate

**File:** `packages/core/Cargo.toml:34-36`, `packages/core/tests/bin/seed_criteria.rs`
**Issue:** The tool is registered as a `[[bin]]` of `flywheel-core`, so every `cargo build` compiles it.
The crate already does this for UAT helpers, so it is consistent with precedent, but this one writes to the
owner's real fleet database. It hard-codes the five `THRE-xx` keys and their criteria text. Its
`delete_probes` runs over every project's `acceptance_criteria`, not one project. It also deletes a
criterion whose trimmed statement is exactly `test` or `hello` regardless of checked state. The
`--i-mean-the-real-database` flag and the exact-match allowlist are real mitigations. The risk is that
someone else's board carrying a criterion literally named `test` loses it.
**Fix:** Move it to `examples/` or delete it once the board is seeded. If it stays, scope `delete_probes`
to an explicit `--project <key>`.

### IN-02: `aria-selected` on `role="listitem"`

**File:** `packages/desktop/src/board/EpicHeaderRow.tsx:179-182`
**Issue:** `aria-selected` is not a supported attribute of `listitem` (ARIA 1.2 allows it on `option`,
`row`, `gridcell`, `tab` and similar). Assistive tech may ignore it, so the selected state is not
announced. `BoardRow` already has the same pattern, so this is new code copying an existing defect. The
epic header is also a clickable `div` with a `tabIndex={-1}` inner button, and there is no keyboard route
to expand it.
**Fix:** Give the list `role="listbox"` and the rows `role="option"` with `aria-selected`, or drop
`aria-selected` and use `aria-current`. Separately, an Enter/Space or Left/Right expand binding on a
focused epic header would need an owner decision, because A-02 and A-03 grant no Keyboard Map change.
Epics default to collapsed (`collapsedByStatus[key] ?? true`), so in the epic lens, which is the home
surface, a keyboard-only user cannot reach any task row.
