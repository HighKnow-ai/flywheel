# Phase 08.1 Plan 08: Has-worktree filter dimension Summary

**A sixth filter dimension, "Has worktree", as one compile-time clause in the core's single filtering query, with epics matching when any child task has an active worktree (owner decision A-04), carried through a chip with no client-side narrowing.**

## The decision (Task 1)

**Question asked, verbatim:** "Define what an epic row does when the has-a-worktree filter is on, amending `01-UI-SPEC.md` § Information Architecture > Search and filter."

Worktrees are keyed to tasks, so an epic row can never have one of its own, yet the filter fragment had to say something about epic rows or the roster would lose its headers the moment the chip was used.

**Options offered:**

| Option | What it does | Consequence |
|--------|--------------|-------------|
| `any-child` (recommended) | An epic matches when any of its child tasks has an active worktree | The roster keeps its headers and the chip reads as "show me the epics with live work". An epic can appear while most of its tasks are filtered out of it. |
| `never` | Epics never match | The chip collapses the view to a flat list of exactly the tasks that have worktrees. Turning the chip on destroys the roster's grouping entirely. |
| `always` | Epics always match | Headers never disappear, but the chip no longer narrows the roster at all, only the tasks inside it. |

**Owner's answer (2026-10-08): `any-child`.** Recorded as A-04 in `08.1-AMENDMENTS.md`, citing `01-UI-SPEC.md` § Information Architecture > Search and filter, with the chosen reading quoted and the git-fact boundary stated.

**Verified on the real board before he answered:**

- `worktrees.task_id` is `NOT NULL UNIQUE REFERENCES tasks(id)`, so an epic can never own a worktree. The literal clause is false for every epic row by construction.
- There are 5 active worktrees. All 5 of their tasks belong to epics, in 5 distinct epics, one live task each.
- So under `any-child` the real roster goes from 13 epics to 5, each showing its one live task, with grouping intact. Under `never` it would have collapsed to a flat list of 5 tasks, destroying the home surface A-01 established. Under `always` all 13 headers would stay, with 8 as empty shells.

**Re-confirmed by this executor** with a read-only query of the live database using the shipped clause shape: 5 active worktrees, 13 epics, 5 epics with an active-worktree child, 5 tasks with their own active worktree.

**Boundary recorded in A-04:** commits-ahead and dirty are not filter dimensions. They are git facts with no database column; filtering or sorting by them would need a materialized column and therefore a migration, which CONTEXT lists as deferred. They remain annotation only.

## Accomplishments

- A-04 recorded in the amendments file, in the shape of A-01..A-03.
- One clause added to `FILTER_WHERE`, still a single `concat!` literal. A task matches on its own active worktree (index seek on the unique `worktrees.task_id`); an epic, selected by `b.kind = 'epic'`, matches when any child task has one (probe scoped by `wt.project_id` so the `(project_id, epic_id)` index serves it).
- The new value binds as `:has_worktree`, `Some(1)` or NULL, at all six named-parameter sites.
- The chip: draft field (default false, cleared by Clear Filters), `hasWorktree?: true` on the wire (absent when off), and a "Has worktree" button whose accessible name says in words what it narrows to.

## Decisions Made

- A-04 (any-child), as above.
- Core field is `bool`, not `Option<bool>`: with "false means unfiltered" an `Option` would add a third state nothing uses. The command input stays `Option<bool>` and folds `None` and `Some(false)` together.
- The clause uses `CASE b.kind WHEN 'epic' ... ELSE ... END` rather than an id-equality trick, so it reads as the A-04 rule and never touches `b.epic_id`.

**3. [Plan premise corrected] A missed bind site does not error at run time**
- **Found during:** Task 2, by mutation-testing the six sites
- **Issue:** The plan says a missed bind "fails at run time on a parameter the statement declared and the call did not supply". It does not: rusqlite leaves an unbound named parameter as SQL NULL, so a missed site silently means "unfiltered". My first version of the six-sites test passed with the first-page bind deleted, because a one-row first page happened to land on a match.
- **Fix:** Rewrote the test to assert the exact matching set at every site (full first page, cursored page, band counts, for both list and search). Verified by deleting each of the six binds in turn: all six now fail the test.
- **Files modified:** `packages/core/tests/search_filter.rs`
- **Committed in:** `82a7a78`

**4. [Plan inaccuracy] `adapters/tauri.ts` needed no change**
- **Issue:** The plan lists it as holding a mirrored filter input type. It does not; the wire type is `BoardFilterInput` in `board/useBoardQuery.ts`, which was updated. No edit to the adapter was warranted.

**5. [Verify window] A-04 header carries a boundary line**
