### Where the reason lives, and why

A `task.changes_requested` event is appended **in the same transaction as the status write**, following the `task.done_with_unmet_criteria` precedent in `forge/transitions.rs`. The event is a marker and an audit snapshot: it stores `unchecked_count`, the criterion ids in rank order, `from_status` and a human `label`, and **never the statement text**. The reason itself is derived live from the unchecked current-revision criteria every time it is read, so it cannot go stale and is never a second copy of board text. The agent receives it as a `review_feedback` field on the context packet, rendered as a `## Review Feedback` section in `render_prompt`; the launch sheet's DTO and section take the lead sentence and statements from the same Rust constant and list. **No table, column or migration was added.**

Rejected, with reasons recorded in the plan: an issue (allocates a project key per click and `context_packet.rs` never reads issues); a comment (no comments table exists); `session_summaries.next_session_must_know` (the agent's own statement keyed to a run; a human decline there forges a session); the drift channel (relaunch would write `drift.detected` and raise a false Needs Decision pill).

### The D-122 distinction

D-122 (Phase 7) says a forge-reported "changes requested" raises an `events` row and **moves nothing**. That is the forge speaking: an outside review Flywheel records but never lets drive its board. A-08(a) is the owner speaking, inside Flywheel's own review surface, about work he has just read. **The forge-driven changes-requested path still moves nothing and is untouched.** What changed is that the review tree no longer writes no status at all: one single-purpose command, invoked by an explicit human press, can write one named edge. The structural guarantee is narrowed, not dropped: no generic status setter is reachable from the review tree (grep gate plus a strict-mock test), and D-145 (a merge moves no status) is untouched. Forge baselines are edge-triggered, so a decline on a task with an open request is not flipped back by the next poll. The D-122 reading is already recorded in `08.1-AMENDMENTS.md` A-08(a) (written by the orchestrator in `43927a2`); this plan did not edit it.

### Why `in_progress` as well as `in_review`

Verified read-only against the real board on 2026-10-08 (by the planner and orchestrator; this close-out did not re-query the database, and no test in this plan writes to or seeds it):

- THRE-33, THRE-38, THRE-43, THRE-53 and THRE-58 are the only five tasks with a worktree. All five are `in_progress`, each with three current criteria, all three unchecked: 15 current task criteria, 15 unchecked.
- 181 tasks are `in_review`. None has a worktree and none has a criterion.
- 0 `task.changes_requested` events existed.

Gating on `in_review` alone would have offered the action on **zero** real tasks. The brief's edge (`in_review` to `in_progress`) is real, but the reviewable tasks are already `in_progress`; there the shared writer's documented redundant-transition guarantee means the status does not move, and the decline is still recorded and still reaches the agent. This is a no-op by design, not a bug.
