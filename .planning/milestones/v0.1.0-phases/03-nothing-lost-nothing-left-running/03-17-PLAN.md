<objective>
Make the two process-termination controls fire once per human decision.

**Phase goal (quoted verbatim from ROADMAP.md):** "Cyril can quit, crash or interrupt Flywheel at
any moment and know that no uncommitted work was destroyed and no agent is still spending his
money."

**User story (MVP framing):** **As a** developer who has just relaunched after a crash and is
killing processes that are spending money right now, **I want to** click Kill once and have it mean
once, **so that** the recovery screen's report of what happened matches what actually happened.

Purpose. Three separate plans in this phase independently diagnosed the same React defect and fixed
it with a `useRef` (`WorktreeSummary.tsx`'s `actingRef`, `RunsSection.tsx`'s `ackActingRef`), each
recording in STATE.md that a real failing test found it: two synchronous clicks both observe the same
stale state before the first re-render flushes the `disabled` attribute. Two surfaces in this phase
were left without it, and these two are the process-termination path:

- `OrphanRecoveryModal.tsx`'s `handleKill` and `handleKillAll` have NO guard at all — not even a
  state check at entry. `handleKill` sets `killing: true` through `setRows` and immediately dispatches;
  a second click in the same tick reads the same pre-flush row and dispatches again. `handleKillAll`
  filters on `!row.killing`, which is the same stale read.
- `SessionSurface.tsx`'s `handleStop` sets `stopping` and dispatches, relying on `disabled={stopping}`
  alone.

Neither causes data loss — `orphan_kill` checks pending-orphan membership before signalling, so a
second kill returns a not-found error rather than a stray signal — but both produce a spurious
failure message on the one screen whose entire job is to report honestly what is and is not still
running.

Output: a per-run guard on the recovery modal, a single guard on the Stop control, and tests that
reproduce the defect before fixing it.
</objective>

**`packages/desktop/src/recovery/OrphanRecoveryModal.tsx`.** Declare a ref holding a `Set<string>`
of run ids currently in flight — name it `killingRef` — beside the existing `firstKillButtonRef`.
Carry the same explanatory comment the sibling surfaces use: the row's `killing` flag is not a
sufficient guard against two activations in one synchronous tick because React has not necessarily
flushed the re-render that replaces the button with the in-flight label; a ref reads and writes
synchronously and has no such window. The row state remains the source of truth for what renders.

A set rather than a boolean, because this modal kills several runs concurrently by design: Kill All
dispatches one call per row, and a single boolean would let the first dispatch suppress every
sibling.

keeps its existing `setRows` marking and `killOne` dispatch unchanged.

`handleKillAll` builds its target list from rows that are not `failed` AND whose run id the set does
not already hold — replacing the stale `!row.killing` read with the synchronous one. It then adds
every target's id to the set before dispatching any of them, so a second activation in the same tick
finds them all held.

`killOne` deletes the run id from the set on the two paths where the call is over and the row did not
disappear: the not-killed outcome branch and the thrown branch. Do not delete on the killed branch —
the row is removed there, so the id can never be activated again, and deleting would reopen the
window this guard closes. Mirror `acknowledge()`'s catch-path reset comment.

Change nothing else: not the seed-exactly-once effect, not `anyUnresolved`, not the focus ref, not
the undismissable behaviour, not any copy.
