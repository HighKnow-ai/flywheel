<objective>
Make the destructive gate ASK, which is what AGNT-07 requires and what the product currently does
not do.

**Phase goal (quoted verbatim from ROADMAP.md):** "Cyril can quit, crash or interrupt Flywheel at
any moment and know that no uncommitted work was destroyed and no agent is still spending his
money."

**Requirement (quoted verbatim from REQUIREMENTS.md):** **AGNT-07** — "Destructive actions
(force-push, branch deletion, recursive delete) always require explicit confirmation, even when the
session is running in an auto-accept permission mode."

**User story:** **As a** developer running an agent in auto-accept mode, **I want** a destructive
command to stop and ask me, **so that** I decide whether my branch is deleted — rather than having
the agent told no on my behalf, and finding out only from a transcript.

Purpose. `scripts/uat/uat-03-destructive-gate.mjs` drives a real `claude` session against a real
scratch remote and measured the gap directly, twice, against claude 2.1.267:

- **Safety holds.** The remote branch is untouched and the agent receives `This would delete a
  branch.` rather than a bare non-zero exit.
- **Confirmation does not happen.** No `permission_request` is ever raised. The session never
  blocks. The tool result reads `non_execution_kind: "permission-rule"`.

The mechanism. `claude-code-adapter.ts::writeHookSettings` registers the PreToolUse hook with
`matcher: "Bash"` — EVERY Bash tool call — and `pretooluse-hook.ts` returns
`permissionDecision: "deny"` for every non-`safe` verdict. Both the hook and the shim classify
through the SAME `destructive::classify`, so the hook refuses precisely the set of commands the
shim's socket would otherwise have asked a human about. D-58's indefinite block — the only thing
that raises a `permission_request` — is unreachable for anything the agent runs through Bash.

`pretooluse-hook.ts`'s own doc comment already describes the intended, narrower scope: it exists to
cover "what the shim (D-51) structurally cannot see — a destructive `git`/`rm` invoked by absolute
path, which never resolves through the shim's own `PATH`-shadowed directory at all." That is the
correct design. The implementation simply never restricted itself to it. This plan makes the code
match the comment.

Two consequences worth stating, because they are why this is a gap and not a preference:

1. AGNT-07 says *confirmation*. A refusal is not a confirmation — the human is never consulted.
2. The destructive permission card (03-12, 03-16) is **unreachable in normal use**. Phase-03 UAT
   item 4 could only inspect it by seeding a pending request straight into the database. An entire
   designed surface — the stop-sign glyph, the branch-naming consequence sentence, the reversed
   button emphasis, the "just this once" wording — cannot currently be produced by any session.

Output: a shim mode that reports interception reachability, a hook that defers when interception is
provable and refuses when it is not, and the UAT script passing both of its properties.
</objective>

### Task 1 — The shim reports whether it can intercept

**files:** `packages/shim/src/main.rs`, `packages/sidecar/test/destructive-gate.test.mjs`

**where the tests go.** `packages/shim/` has no `tests/` directory; the established pattern for
testing this binary's behaviour is `destructive-gate.test.mjs`, which already resolves the compiled
`flywheel-shim` the same two places `flywheel_core::shim::resolve_shim_binary` looks and has a
`--classify-command mode` section. Add the new mode's cases there, beside it.

**action:**

Add a `--classify-invocation <text>` mode alongside the existing `--classify-command`, checked in
the same place (before the `argv[0]`-stem dispatch). It reaches the SAME
`classify_raw_command_text`, and additionally reports what the caller needs in order to decide
whether the shim can intercept: the program name of the destructive segment, and whether that
segment invoked it by bare name.

`classify_raw_command_text` already has both facts in hand at the point it finds a destructive
segment — it computes `program_stem(first)` and holds `first` itself. "Invoked by bare name" is
`!first.contains('/')`: a token with any separator names a path and can never resolve through a
`PATH`-shadowed directory. Refactor the function to return the stem and the bare-name flag
alongside the verdict rather than duplicating the scan.

Emit one line of JSON on stdout so the shape is self-describing and can gain fields later without
breaking its reader:

```json
{"category":"branch-deletion","program":"git","invokedBareName":true}
```

For a safe command: `{"category":"safe"}`. A missing or unreadable argument fails closed exactly as
`--classify-command` does — `{"category":"uncategorized","invokedBareName":false}` and a non-zero
exit, so a caller that cannot read a verdict treats the command as both destructive and
un-interceptable, which is the most restrictive reading available.

**`--classify-command` is left exactly as it is** — same one-word output, same exit codes.

Be accurate about what that means after Task 2: `pretooluse-hook.ts:112` is its ONLY runtime caller
today, and Task 2 switches that call to `--classify-invocation`. So this mode becomes test-only
surface, asserted by `destructive-gate.test.mjs` and referenced in doc comments. It is kept rather
than deleted because those assertions are real, cheap coverage of the pure classification path, and
because deleting a public mode is a separable decision from fixing the gate. Do not quietly remove
it as "dead code" during this plan; if it should go, that is its own change.

**verify:** parse the JSON rather than string-matching it — field order is an implementation
detail and an exact-match assertion would break on a harmless reordering.
```bash
cargo build -p flywheel-shim
node -e '
const {execFileSync} = require("node:child_process");
const bin = "./target/debug/flywheel-shim";
const run = (t) => JSON.parse(execFileSync(bin, ["--classify-invocation", t], {encoding:"utf8"}));
const assert = require("node:assert/strict");
assert.deepEqual(run("git push origin --delete x"), {category:"branch-deletion", program:"git", invokedBareName:true});
assert.deepEqual(run("/usr/bin/git push --force"),  {category:"force-push",     program:"git", invokedBareName:false});
assert.deepEqual(run("git status"),                 {category:"safe"});
console.log("classify-invocation ok");
'
test "$(./target/debug/flywheel-shim --classify-command 'git push origin --delete x')" = "branch-deletion"
test "$(./target/debug/flywheel-shim --classify-command 'git status')" = "safe"
```

**done:** The shim can answer "is this destructive, and could my own PATH shadow have caught it?"
in one call, and the old mode is byte-for-byte unchanged.

### Task 2 — The hook defers when interception is provable, refuses when it is not

**files:** `packages/sidecar/src/pretooluse-hook.ts`, `packages/sidecar/test/destructive-gate.test.mjs`

**action:**

Switch the hook to `--classify-invocation` and give it two branches instead of one.

```
category == "safe"                    → print {} (no opinion), exit 0     [unchanged]
category != "safe" && shimWillIntercept(program) → print {} (no opinion), exit 0     [NEW]
category != "safe" && !shimWillIntercept(program) → deny with consequence copy       [unchanged]
```

`shimWillIntercept(program)` must PROVE interception, not assume it. It returns true only when all
of these hold, and false the moment any cannot be established:

- `invokedBareName` is true in the shim's own report;
- `FLYWHEEL_SHIM_BIN` is set, and its directory is the FIRST entry of `PATH` (the shim's
  `shim_env_for_run` prefixes exactly that directory, so anything else means the environment is not
  the one this hook was designed for);
- that directory contains an executable file named exactly `program` (`git` or `rm`) — the shadow
  entry `install_for_run` writes.

Any failure to establish the above is a `deny`, not an allow. This is the single most important
property in the plan: the hook is trading its own refusal for the shim's question, and it may only
do that when it can show the shim is actually there to ask. A missing shim directory, a
PATH the adapter did not build, or an unreadable environment all mean nothing downstream will stop
the command — so the hook must.

**The hook still never waits.** It performs one `spawnSync`, decides, and exits. The blocking lives
in the shim, on `FLYWHEEL_PERMISSION_SOCKET`. Preserve the existing source-level gate that asserts
this file opens no socket, polls nothing and sleeps never — a hook that waits gets cancelled at its
timeout and its tool call proceeds anyway, which is the failure 03-07 measured and designed around.

Update the module doc comment: it currently describes the intended narrow scope as though it were
implemented. Say plainly that the hook is the refusal layer for the class the shim cannot see, and
the pass-through for the class it can, and that the question layer is the shim's socket.

**tests** in `destructive-gate.test.mjs`, alongside the existing real-binary measurements:

- a bare destructive command, with a correctly-shaped shim directory leading PATH → the hook prints
  no opinion (so the command would run and be intercepted);
- the same command with `FLYWHEEL_SHIM_BIN` unset → `deny`;
- the same command with a shim directory that is NOT first on PATH → `deny`;
- the same command with a shim directory missing the `git` shadow entry → `deny`;
- an absolute-path destructive command with a perfectly good shim directory → `deny` (the shim
  cannot see it, so the hook must);
- a safe command → no opinion, as before.

**verify:**
```bash
npm --prefix packages/sidecar run test
```

**done:** The hook refuses exactly the class it alone can see, defers exactly the class the shim can
catch, and proves interception before deferring.

<risks>
- **The hook allows a command the shim then fails to catch.** Mitigated by requiring positive proof
  of the shadow entry before deferring, and by the shim's own fail-closed behaviour when
  `FLYWHEEL_PERMISSION_SOCKET` is unset ("refusing a destructive command with nothing to ask").
- **A compound command chains a bare destructive segment after a path-invoked one.**
  `classify_raw_command_text` returns on the FIRST destructive segment, so the reported program and
  bare-name flag describe that segment. That is the correct one to reason about, since it is the
  one that would execute first — but state it in the code comment so the next reader does not have
  to re-derive it.
- **`claude` may resolve `git` itself rather than via PATH.** UAT item 5 already measured the
  opposite — the agent's own shell resolved `git` to the per-run shim directory — so this is
  covered by an existing passing test, not an assumption.
</risks>
