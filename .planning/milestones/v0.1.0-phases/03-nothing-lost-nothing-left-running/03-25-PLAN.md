<objective>
Make a broken shim install fail loudly at spawn, so that D-60's deny-everything posture can never
be experienced as "Flywheel randomly stopped letting my agent run anything."

**Phase goal (quoted verbatim from ROADMAP.md):** "Cyril can quit, crash or interrupt Flywheel at
any moment and know that no uncommitted work was destroyed and no agent is still spending his
money."

**Requirement (quoted verbatim from REQUIREMENTS.md):** **AGNT-07** — "Destructive actions
(force-push, branch deletion, recursive delete) always require explicit confirmation, even when the
session is running in an auto-accept permission mode."

**User story:** **As a** developer whose shim install has gone wrong, **I want to** be told at
launch, by name, that the session cannot be protected, **so that** I fix the install instead of
discovering a session that refuses `npm test` and concluding the gate is broken and should be
turned off.

Purpose. D-60 is explicit that its consequence is not only a hook change: "A failed, partial or
missing install must surface as a named, visible supervisor error at or before spawn, never as a
session that silently denies every command the agent tries. That obligation lands on
`install_for_run` / `shim_env_for_run` … and it needs its own test: a run spawned with a
deliberately broken shim directory must fail loudly, not quietly."

Today `install_shadow_entry` returns `Ok(())` the moment `entry.is_file()` is true — a zero-byte
file, a non-executable file or a stale binary all pass — and nothing verifies the result. Plan
03-24 makes that silence expensive: the hook now refuses every command in a session whose shadow
directory it cannot prove. This plan closes the loop on the other side.

Output. Two verification layers on the supervisor side, and the tests that prove each is loud:
structural checks in `install_for_run` (cheap, no process spawn, paid by every caller), and one
classification-contract probe in `shim_env_for_run` (one process, paid only on the spawn path).

**Already true, confirmed rather than assumed** — do not rebuild it: `merge_shim_env_for_run`
already propagates an `Err` that `agent_run_start` turns into `Err(String)`, and
`LaunchSheet.tsx`'s `handleSubmit` already catches it and renders the message in the sheet's error
slot. The "visible" half of D-60's obligation exists. What is missing is that the message says
something a human can act on, and that a broken install produces one at all.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the on-disk per-run shim directory -> the spawned session's `PATH` | Whatever sits at that path becomes the program every bare `git` and `rm` in the session resolves to |
| a previously-installed entry -> this run's install | `install_shadow_entry` deliberately leaves an existing entry alone, so a run can inherit a file it did not write |
| the supervisor's error -> the launch sheet | The one place a human learns the session could not be protected |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-25-01 | Tampering | a pre-existing broken entry in the per-run shim directory | high | mitigate | Task 1 verifies both entries after install, so a zero-byte, non-executable or directory-shaped entry stops the install by name instead of being inherited through the exists-already fast path |
| T-03-25-02 | Spoofing | an executable that is not the shim sitting at the shadow entry path | high | mitigate | Task 2's probe requires the entry to answer `--classify-invocation` with the current contract, which an arbitrary executable cannot do |
| T-03-25-03 | Elevation of privilege | a shim binary older than plan 03-24's contract | high | mitigate | Task 2's probe requires both new fields to be present, so a stale binary is refused at spawn rather than producing a session that denies everything and invites the gate to be disabled (D-60) |
| T-03-25-04 | Denial of service | the probe refusing spawns in a developer environment with a stale build | medium | mitigate | The message names the entry path and the failed expectation, and `cargo build --workspace` is the documented fix; this is the intended loud failure, not a regression |
| T-03-25-05 | Denial of service | the probe spawning a process on every `install_for_run` caller | medium | mitigate | The probe lives in `shim_env_for_run`, not `install_for_run`, so install-only callers pay only the structural checks |
| T-03-25-06 | Repudiation | an install failure with no actionable message | medium | mitigate | Every failure branch carries the same fixed prefix plus the entry path, the run id and the unmet expectation, and that string is what the launch sheet renders |
| T-03-25-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task exists in this plan — `serde_json` and `anyhow` are already `core` dependencies and `std::process::Command` is in the standard library. If execution finds an install is needed, halt and route through the package-legitimacy gate rather than installing |
</threat_model>
