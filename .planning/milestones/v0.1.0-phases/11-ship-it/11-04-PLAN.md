<objective>
**As** Cyril, **I want to** push one tag and have a downloadable Flywheel appear, **so that**
releasing is not a ritual I can get wrong.

D-182 makes GitHub Actions the only sanctioned way a Flywheel binary comes into existence, which is
also what keeps DIST-03 continuously true: every release is itself a clean-clone build. D-184 makes
the tag the single source of the version — today `0.1.0` is hand-written in three files that can
drift apart silently.

Purpose: the release pipeline, built and provable **unsigned first** (D-185), so nothing but
criterion 1 waits on an Apple Developer account.
Output: `release.yml` and a tested version-stamping script.
</objective>

    - `apply-tag-version.mjs v0.1.0` writes `0.1.0` into all three manifests and prints the version it applied.
    - A tag that is not `v` followed by a semantic version exits non-zero and writes nothing, not even to the manifest it would have reached first.
    - A second run with the same tag changes no bytes, and key order plus Cargo comments survive.
    - A manifest missing its version key is an error naming the file, never a silent skip.

  <action>
Write `scripts/release/apply-tag-version.mjs`, a plain Node ESM script taking the tag as `argv[2]`.
Strip the leading `v`, validate the remainder against a semantic-version pattern that also accepts a
prerelease suffix, and refuse before touching any file when validation fails. The refusal message
must name both the rejected tag and the expected shape.

For the two JSON manifests use `JSON.parse` then `JSON.stringify` with two-space indent and a
trailing newline, mutating only the `version` key. For
`packages/desktop/src-tauri/Cargo.toml` do a line-scoped replacement of the first line matching a
`version = "` prefix **inside the `[package]` table only** — that file's dependency comments and
dependency lines carry the pinned strings `=2.11.5` and `=2.4.0`, and a file-wide substitution
would rewrite them.

`packages/sidecar/package.json` also carries a `0.1.0` and is deliberately not stamped: it is a
private workspace package whose version is never published and never read at runtime. State that in
a comment so the next reader does not "fix" the omission.

Write `scripts/release/apply-tag-version.test.mjs` beside it, driving all four behaviours against
copies in an `fs.mkdtempSync` directory, never against the real tree.

Trigger: `on: push: tags: ['v*']` and nothing else. No `workflow_dispatch` with a typed version —
D-184 rejected it as trivially desynced from the tag and the changelog. One job, `release`, on
`macos-14`, with `permissions: contents: write` and nothing wider.

Steps:
1. `actions/checkout@v4` with `fetch-depth: 0`, because the release-notes step reads history.
2. `node scripts/release/apply-tag-version.mjs "${{ github.ref_name }}"` — first, so a malformed
   tag fails the job before a toolchain is installed.
3. Node 22, the Rust toolchain and the two caches, exactly as `ci.yml` sets them up.
4. `npm --prefix packages/sidecar ci` then `npm --prefix packages/desktop ci`.
5. `npm --prefix packages/sidecar run build:dist`, before any cargo step, with the same comment
   naming the `tauri_build::build()` externalBin precondition.
6. `npm --prefix packages/sidecar test` and `cargo test --workspace`. A release that cannot pass its
   own tests must not produce an artifact.
7. Release notes: resolve the previous tag with `git describe --tags --abbrev=0 "${{ github.ref_name }}^"`,
   falling back to the first commit when there is no previous tag, then
   `git log --pretty=format:'- %s' <previous>..${{ github.ref_name }}` into a file. These commit
   subjects are the "what changed" text D-187's banner shows the user, so they must be real history,
   never a placeholder string.
8. `tauri-apps/tauri-action@v0` with `tagName: ${{ github.ref_name }}`,
   `releaseName: Flywheel ${{ github.ref_name }}`, the body from step 7, `releaseDraft: false`,
   `prerelease: false`, `args: --target aarch64-apple-darwin`, and `includeUpdaterJson: true` so the
   action publishes `latest.json` beside the artifacts (D-186: the stable
   `releases/latest/download/latest.json` URL is what gives self-update zero infrastructure).
   `env: GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`.
   Above this step write a comment naming the env groups added later and by which plan:
   `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` in plan 11-05, and the
   `APPLE_*` set in plan 11-07. Do not add them here — this plan ships the pipeline unsigned on
   purpose (D-185), so that nothing but criterion 1 waits on the Apple account.
9. An asset assertion step: `gh release view "${{ github.ref_name }}" --json assets` and fail unless
   all four expected names are present (one `.dmg`, one `.app.tar.gz`, one `.app.tar.gz.sig`, and
   `latest.json`). A release missing the signature or the manifest is a release no client can update
   from; that must fail at release time, not on a user's machine.

Use no `continue-on-error` anywhere.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| git tag (any pusher with write access) → a published binary | A tag is the sole trigger for producing something users install. |
| `tauri-action` third-party step → `GITHUB_TOKEN` with `contents: write` | The action creates releases on the repository's behalf. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-10 | Spoofing | `on: push: tags` trigger | medium | accept | Only repository collaborators can push tags; a single-maintainer repository has no weaker path. Revisit when the repository takes outside committers — branch protection and tag protection rules are the control then. |
| T-11-11 | Tampering | `tauri-apps/tauri-action` | medium | mitigate | Pinned to a major tag, scoped to `permissions: contents: write`, and given no signing secret in this plan; the asset-assertion step independently verifies what was published rather than trusting the action's own success. |
| T-11-12 | Elevation of Privilege | `apply-tag-version.mjs` running on untrusted input | low | mitigate | The tag is validated against a semantic-version pattern and refused atomically before any file write; the script executes nothing from the tag string. |
| T-11-SC | Tampering | npm/cargo installs | high | accept | This plan adds no package-manager dependency; `tauri-action` is a GitHub Action, not a package install. The package-legitimacy gate applies to plan 11-05. |
</threat_model>
