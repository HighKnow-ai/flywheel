<objective>
Build the reparenting half of the fixed three-level hierarchy that BOARD-01 claims and the UAT proved
unreachable: a task can be moved under an epic and back out, and an issue can be moved under an epic
or under a task and back out — through real, registered Tauri commands, with the same-transaction
event and the same server-side actor resolution every other mutation in this codebase already uses.

Purpose: G-01-EPIC-ASSIGN found three compounding causes. This plan removes the structural one — the
command registry has no `task_set_epic` and no `issue_set_parent`, and `task_update`/`issue_update`
patch only text fields, so nothing in the running application can ever change a parent. Until that
command surface exists, no amount of frontend work can make the hierarchy reachable. The two
frontend causes are closed by plans 01-14 and 01-15, which depend on this one.

Output: two domain functions, two Tauri commands, one shared same-project integrity check applied to
both the new reparenting paths and the two existing creation paths, and the cargo tests that hold
them.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → Tauri command surface | `task_id`, `epic_id`, `issue_id`, `parent_kind` and `parent_id` are renderer-supplied strings; nothing about them is trusted |
| domain function → SQLite | the only code in the workspace permitted to execute a mutating statement (`domain/mod.rs` module doc) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-GC-01 | Tampering | `task_set_epic` / `issue_set_parent` parent arguments | high | mitigate | `assert_parent_in_project` rejects a parent id whose `project_id` differs from the child's, inside the same transaction and before the UPDATE, so a renderer-supplied id cannot graft an item onto another project's tree; the same check is applied to `create_task`/`create_issue`, whose parent parameters plans 01-14 and 01-15 are about to make live |
| T-01-GC-02 | Tampering | a parent id naming no row at all | medium | mitigate | `assert_parent_in_project` returns an error naming the id before the UPDATE runs, and the `epic_id`/`task_id` foreign keys reject it independently (`foreign_keys = ON` is set on every connection by `db::open_and_migrate`) |
| T-01-GC-03 | Repudiation | a reparent leaving no trace | medium | mitigate | Every accepted change appends exactly one `task.epic_changed`/`issue.parent_changed` event carrying before and after, in the same transaction as the UPDATE (DATA-01); the tests assert the count so a silent path cannot be added later |
| T-01-GC-04 | Spoofing | actor attribution on a reparent | high | mitigate | Both commands resolve `actor_id` server-side via `local_human_actor_id` and accept no actor argument from the renderer, matching threat T-01-04's existing rule for every other command |
| T-01-GC-05 | Tampering | an issue holding two parents at once | medium | mitigate | `set_parent` writes both `epic_id` and `task_id` in one UPDATE derived from a single `IssueParent` variant, so a two-parent row is unrepresentable rather than merely unwritten |
| T-01-GC-06 | Denial of Service | oversized id arguments | low | accept | Every id column carries `CHECK (length(id) = 26)`; a longer string fails the parent lookup and is never stored |
| T-01-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs no package — no line is added to any `Cargo.toml` or `package.json`, so the package-legitimacy gate has nothing to audit |
</threat_model>
