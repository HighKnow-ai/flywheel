<objective>
Close UAT gap G-01-1: on macOS the native menu owns ⌘N as an accelerator, the webview never sees
the keydown, and `App.tsx`'s `menu:action` bridge dismantles the very layer the keystroke was
supposed to be blocked by before dispatching the action.

Purpose: the layer guard in `state/keyboard.ts` is correct and must stay untouched — it is being
bypassed, not failing. This plan removes the bypass and makes the native menu bar itself
layer-aware, so both origins of a menu action (keystroke and click) are decided by the one
`bindingAllowedInLayer`/`topLayer` call every other keystroke already goes through.

Output: a bridge that grants the menu no capability the keyboard lacks, a menu bar whose items
grey out under a trapped layer instead of firing behind it, and the first regression test in this
repo that drives the real `menu:action` path rather than stubbing it to a no-op.

<design_decision>
## Route chosen, and why

The planning brief offered two routes: (a) carry the event origin from Rust so only a real click
returns to the board layer, or (b) drop the return-to-board call entirely and let the layer guard
decide for every forwarded id. This plan implements **(a)** — but not as a payload field, because
that is not available, and not by deleting the accelerators, because that would break a binding
contract. It carries the origin by removing the *only* case where the two origins needed to be
told apart.

**Why (a)-as-a-payload-field is not implementable.** `muda 0.19.3`, vendored under `tauri 2.11.5`
(both pinned in `packages/desktop/src-tauri/Cargo.toml`), defines the whole event as
`pub struct MenuEvent { pub id: MenuId }`. `on_menu_event` receives nothing else — no origin, no
modifier state, no originating `NSEvent`. Telling an accelerator from a click at runtime would
need macOS-specific FFI to read `NSEvent` modifier flags at event time: platform-locked, racy (a
user holding ⌘ while clicking a menu item reads as an accelerator), and untestable in a
`src-tauri` crate that today contains zero `#[cfg(test)]` blocks.

**Why the accelerators must stay.** 01-UI-SPEC.md's "App shell & window chrome" section is the
binding design contract for this phase and specifies the menu bar item-by-item *with* its
shortcuts: "**File:** Register Project… (⌘⇧O) · New Task (⌘N) · New Epic (⌘⇧N) · Close Window
(⌘W)" and "**View:** Toggle Command Palette (⌘K)". Stripping the accelerators to force every
keystroke into the webview would satisfy the layer guard by violating that contract and removing
the macOS-native affordance that tells a user the shortcut exists at all.

**Why (b) alone is not shippable.** Dropping the return-to-board call closes the accelerator bug,
but it turns a File-menu *click* over an open detail panel into a silent no-op on an item that
still looks enabled. That is precisely the failure `menu.rs`'s own doc comment condemns ("a menu
entry that goes nowhere is worse than its absence", 01-UI-SPEC.md Open Decisions #8), and it
revisits 01-13-PLAN.md Task 2's deliberate click behavior while trading one defect for another.

**The route this plan takes** is (b)'s bridge simplification plus native menu-item validation:

1. **The bridge stops granting the menu a broader capability than the keyboard** (Task 1). The
   `menu:action` handler calls `dispatchAction(actionId)` and nothing else;
   `bindingAllowedInLayer`/`topLayer` decides, identically for both origins. This restores threat
   T-01-02's own stated invariant — "menu items invoke the same registered commands as the UI; no
   menu item is given a broader capability" — which the pre-emptive layer teardown violated.

2. **The menu bar becomes layer-aware** (Tasks 2 and 3). The renderer pushes the guard's verdict
   for the four forwarded ids to Rust, which calls `MenuItem::set_enabled`. macOS greys a disabled
   item *and* stops firing its key equivalent, so the accelerator never reaches `on_menu_event` in
   the first place while a trapped layer is up. The accelerators themselves are untouched, so the
   UI-SPEC menu-bar contract holds exactly, printed shortcuts and all — and no menu item is left
   standing as an enabled-but-dead control while the layer model refuses it (with the one bounded,
   self-correcting exception the next section names and accepts).

**Layering, and the async window — for both menu origins.** Policy lives in one place
(`bindingAllowedInLayer`); enforcement stays at the guard (`useGlobalBindings`, unchanged and
unweakened by this plan); the menu state is an *affordance*, not the enforcement point. The
enable/disable push is asynchronous, and the two origins land differently inside that window:

- **Keystroke (the reported bug).** A keystroke that beats the round trip still reaches the guard
  through the bridge and is refused, so the accelerator is inert under either ordering — which is
  exactly the truth G-01-1 demands — and it stays inert whether or not macOS forwards a disabled
  item's key equivalent down the responder chain.
- **Click (bounded, and explicitly accepted).** Inside that same window a File-menu *click* is the
  silent no-op this plan rejects route (b) over, so it must be bounded rather than waved away. It
  is bounded to one local IPC round trip: `useMenuLayerSync`'s effect is queued in the same React
  commit as the store write that opened the layer, so `menu_set_action_enabled` is in flight within
  that frame, and it is an in-process Tauri command — no network, no disk, no lock behind it. To
  land in the window a user must open a trapped layer and reach the menu bar within roughly one
  frame of it appearing. **This residual window is accepted, not designed away.** Closing it would
  mean making the menu's enabled state synchronous with the layer change, which is only possible by
  moving the layer model into Rust — far larger than G-01-1 warrants, and it would put policy in
  two places, the exact defect being fixed. Task 3's `<human-check>` step 3 measures the window
  directly (open the panel, go straight to the File menu) so "bounded to about a frame" is
  confirmed on a real build instead of asserted here. Note the asymmetry that makes this acceptable
  at all: the accepted case is *transient* and the item self-corrects on the next menu opening,
  whereas route (b)'s no-op was *permanent* — the item stayed enabled and dead for as long as the
  layer was up.

**Commit ordering: Tasks 1 and 3 must land together.** Task 1 removes the click's layer reset;
Task 3 adds the greying that replaces it. Between them the tree has File items that are enabled but
refused for a click — for the click origin that is strictly worse than HEAD, even though the
keystroke bug is already fixed. The intermediate state is not shippable: do not stop after Task 1,
and if the tasks are committed separately, only the commit that lands Task 3 is a releasable point.
Task 2 is inert on its own (it adds a command nothing calls yet) and may land anywhere before
Task 3.
