<objective>
Give tasks and epics real contracts: discrete acceptance criteria with their own identity, each a
checkable statement plus a verification hint, individually checkable without touching the parent row,
and counted wherever the item appears.

Purpose: this is the phase's core-value requirement. "Every unit of agent work is anchored to a
structured board item with real acceptance criteria — never a chat blob" is the sentence the whole
product rests on, and `BOARD-02` is where it becomes a schema rather than a slogan. Criteria having
their own table with their own ULIDs is what lets Phase 4 add revisioning as a column, Phase 8 check
one criterion off against a diff without rewriting its parent, and a session summary reference an
individual criterion by id.

Output: criteria a user authors, checks and reorders, and a checked/total count visible everywhere.
</objective>

    Write `packages/core/src/domain/acceptance_criterion.rs` exposing `create_criterion`,
    `update_criterion`, `toggle_criterion`, `reorder_criterion`, `delete_criterion` and
    `list_criteria`. A criterion carries a `statement` and a nullable `verification_hint` — how you
    would know the statement is true: a test name, a command, or a manual check. Each mutation opens
    exactly one `conn.transaction()`, writes its row, calls `next_sequence` and `append_event`, and

    criterion's own id in `stream_id` and its parent's id in the denormalised `task_id`/`epic_id`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → Tauri command surface | Criterion statements and verification hints cross here as untrusted strings |
| criterion row → parent item row | A criterion mutation must not become a parent rewrite, and a parent mutation must not become a criterion rewrite |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | SQL in `domain/acceptance_criterion.rs` and the counts aggregate in `query/mod.rs` | high | mitigate | Literal statements with `params![]` bindings only, including the grouped aggregate; no value is formatted into an SQL string |
| T-01-20 | Tampering | `toggle_criterion` UPDATE scope | high | mitigate | The statement names only the `checked` column and a timestamp, asserted both by an acceptance criterion and by `parent_edit_leaves_criteria_untouched`, so a check can never become an edit of the user's authored text |
| T-01-04 | Repudiation | `commands/criterion.rs` | high | mitigate | `actor_id` is resolved in Rust; every criterion event carries it, so who checked a criterion off is always recoverable |
| T-01-05 | Denial of Service | statement and hint length | medium | mitigate | The command layer caps both before the core writes them into an event payload |
| T-01-02 | Elevation of Privilege | `capabilities/default.json` | high | mitigate | The six criterion commands are named explicitly; no blanket grant |
</threat_model>
