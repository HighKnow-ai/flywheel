<design_decision>
## The defect in one sentence

An effect whose dependency array carries the whole `collapsedByStatus` map, and whose body performs a
write whenever a condition holds, is not "do X when Y opens" — it is "Y implies X, forever". Every
render where `effectiveQuickAddOpen && collapsedByStatus.backlog` are both true re-calls
`expandBand`, so the user's own collapse is undone on the very next render. Because
`effectiveQuickAddOpen = quickAddOpen || items.length === 0`, that condition never goes false on an
empty project, and the toggle is inert for that project's entire lifetime.

## Why a project-keyed ref rather than the review's boolean ref

`01-REVIEW.md`'s fix sketch is the right shape — a rising-edge guard — but its `backlogAutoExpandedRef`
is a bare boolean that resets only when `effectiveQuickAddOpen` goes false. `App.tsx` renders
`<Board projectId={project.id} projectName={…} />` with **no `key`** (App.tsx:212), so `BoardView` is
not remounted on a project switch — only its `projectId` prop changes. Switch from one empty project to
another (both keep `effectiveQuickAddOpen` true across the switch) and a boolean ref still reads
"already handled", so the switched-to project's collapsed Backlog is never expanded and G-01-4's
collapsed-band failure path reopens for it. Holding the project id the current episode already handled
costs the same one ref and closes that edge by construction.

## Why the explicit-request path lives in the open funnel, not in the effect

There are two distinct triggers, and only one of them is an event:

- **"Quick-add became reachable"** is a *state* transition (`quickAddOpen` rising, or `items.length`
  falling to zero on load). It has no handler to hang off, so it needs the ref-guarded effect.
- **"The user pressed ⌘N/⌘⇧N/`c`, or picked New Task in the palette or the native menu"** is an
  *event*, and `BoardView.openQuickAdd` (BoardView.tsx:427) is already the single funnel every one of
  those routes reaches — nothing else in the renderer sets `quickAddOpen` to true. Expanding there is
  an action taken at the moment of the user's request, which is structurally incapable of fighting a
  later render.

Splitting them this way also settles the one genuine conflict between CR-01 and G-01-4: the user
collapses Backlog while quick-add is open (their click must stick — CR-01), then presses ⌘N again
(an explicit request for a focused quick-add row — G-01-4). The passive render loses; the explicit
keystroke wins. The alternative — refusing to re-expand — turns ⌘N into a silent no-op that also
leaves `quickAddFocusPending` raised and unconsumed, waiting to steal focus whenever the band is
reopened. That is a second defect, not a fix.

## Why the collapsed-check guard must stay inside the effect

`collapseStore.expand` always builds a fresh `collapsedByProject` object, even when the value it writes
is already `false`. An unconditional call from the effect would therefore hand Zustand a new object
reference on every run, re-render `BoardView`, re-run the effect, and spin. The existing
`collapsedByStatus.backlog` check is what makes the write conditional, and it stays. The new ref guard
sits in front of it; it does not replace it.

## Why StatusBand is not touched

Guarding the header's own `onClick` while quick-add is open would make the affordance inert *by design*
— the same user-visible behavior CR-01 reports, only deliberate. `StatusBand.tsx` stays exactly as it
is; the fix belongs where the over-firing is.

## IN-01: fixed, but not as the review sketched it

`01-REVIEW.md` suggests clamping the stub's `top` to `[0, this.scrollHeight - this.offsetHeight]`.
Verified against this repo's jsdom (a direct probe of `jsdom`'s own DOM): **every element reports
`scrollHeight === 0` and `clientHeight === 0`**, because jsdom implements no layout — which is exactly
why `test/setup.ts` already has to stub `offsetHeight` at 800. Applying the sketch literally would make
every programmatic scroll clamp to `max(0, 0 - 800) = 0`, silently disabling `DEEP_SCROLL_OFFSET` and
turning the entire volume suite's deep-scroll precondition into a no-op — the G-01-4 regression tests
would then pass for the wrong reason, which is the precise failure mode `test/setup.ts`'s own doc
comment says the stub exists to prevent. The clamp is therefore implemented **guarded on the element
actually reporting a scrollable range**, inert while jsdom reports none, and its own test proves both
halves.

## Reversibility

All three decisions are `reversible`: one `useRef` and a guard clause inside an existing effect, one
guarded store call inside an existing event handler, a conditional clamp in a test-only stub, and two
sentences of spec prose. No persisted format, no migration, no IPC surface, no published contract. There
is no `one-way` decision in this gap closure, so no `checkpoint:decision` is inserted.
</design_decision>
