<objective>
Make the fleet real: several local git repositories registered as projects, switchable from the rail,
from ⌘1 through ⌘9 and from the palette — each bound to its repository by a committed identity marker
rather than by a remembered path, and each surfaced honestly when that binding no longer holds.

Purpose: `BOARD-10` is the requirement, but D-15 is the reason the marker exists at all — a project
needs an identity that survives being cloned onto another machine, which is the prerequisite for the
team model D-20 describes. D-16 is the discipline: the marker is the binding and the stored path is
only a cached hint, so a mismatch is surfaced, never silently repaired. That mirrors the rule Phase 3
applies to worktrees, and silent repair is exactly what those requirements forbid.

Output: a fleet-wide board with stable per-project identity and no guessing about the filesystem.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-chosen directory → `projects.repo_path` | A path from the native picker becomes a stored location the app later reads and writes |
| marker file content → application state | A file inside a repository the user (or a teammate, or an agent in a later phase) can edit is read as identity |
| application → the user's git repository | The one place in this phase where Flywheel writes into territory it does not own |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03 | Tampering | marker content used to derive a filesystem path | high | mitigate | Marker content is read *at* a path the database already holds and is never used to construct a path to visit; every filesystem call takes an explicit canonicalized absolute path, and a grep gate fails the build if the core enumerates directories |
| T-01-29 | Spoofing | a hand-edited or hostile marker claiming another project's id | high | mitigate | `relocate_project` verifies the marker at the new path names the *expected* project id and rejects a mismatch rather than adopting it; registration surfaces an existing marker to the user before completing, so an id collision is a visible event |
| T-01-30 | Tampering | writing into the user's repository | high | mitigate | The only file written is the identity marker, holding two fields; the write happens after the database transaction commits so a failure leaves nothing behind; a test asserts the serialized file has no third key |
| T-01-31 | Denial of Service | launch-time reconciliation over many projects | medium | mitigate | Reconciliation reads one marker per known project at a known path — it never walks a directory tree, so its cost is linear in registered projects and independent of repository size |
| T-01-04 | Repudiation | registration and relocation events | high | mitigate | Both are attributed mutations appending events through the same outbox path; a relocation is recorded rather than being an invisible correction |
| T-01-02 | Elevation of Privilege | the Tauri dialog capability | high | mitigate | The folder picker is granted as a scoped dialog permission; no filesystem-read or filesystem-write capability is granted to the renderer, and the path crosses back through a validated command argument |
</threat_model>
