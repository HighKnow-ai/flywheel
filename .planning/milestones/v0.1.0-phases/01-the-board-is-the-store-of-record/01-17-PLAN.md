<objective>
Close UAT gap G-01-2's root cause: the epic lookup every board label reads from is derived from the
currently loaded `board_list` page, which `commands/board.rs` caps at `DEFAULT_LIMIT = 200`. Any task
whose epic sorts outside that window finds no entry and `BoardRow.tsx` renders the epic's raw internal
ULID instead.

Purpose: `packages/core/src/query/mod.rs`'s windowing is correct and stays untouched — the core is
LIMIT-bounded and cursor-resumable by design (D-03). The defect is that a *small, bounded roster* was
being read out of a *large, windowed page*. This plan gives the epic roster its own unwindowed read
path, exactly as the actor roster already has one, and makes the epic pill resolve against it.

Output: an end-to-end epic-roster path from SQLite to the rendered pill, a pill that cannot leak an
internal id even on a lookup miss, a roster that stays live under `board:changed`, and the first test
in this repository that runs at a volume where this defect is reachable at all.
</objective>

## The shape, and why it is the actor-roster triad

`01-PATTERNS.md` recommends replicating the already-shipped **"small unbounded roster"** triad
(`domain::actor::list_actors` -> `commands::actor::actor_list` -> `useActors()`), and reading the code
confirms it: `BoardView.tsx`'s own `actorsById` is already built from `useActors()` rather than from
`items`, while `epicsById` five lines below it is built from `items`. The two lookups are the same
shape and only one of them was given a real source. This plan makes the epic side match the actor side.

The alternative the UAT `missing` list offers — "have `board_list` return the referenced epics alongside
the page" — is rejected: it fixes the pill but not the filter chips, because the chip list must cover
**every epic in the project**, not merely every epic some loaded row happens to reference. One roster
query serves both; a piggybacked referenced-epics payload serves neither completely.

## Two places this plan deviates from 01-PATTERNS.md, deliberately

1. **Ordering.** `01-PATTERNS.md` suggests `ORDER BY rank ASC, id ASC`. That would create a *second*
   definition of board order, which is the exact failure class this phase's own code review already
   flagged twice (WR-03, WR-04: a rule duplicated across sites that can silently drift). Instead this
   plan widens `packages/core/src/query/mod.rs`'s existing `ORDER_BY` constant from private to
   `pub(crate)` and has `list_epics` compose it, aliasing the epics table as `b` so the constant's
   column references resolve. BOARD-05's total order stays defined exactly once.

2. **DTO width.** `01-PATTERNS.md` offers reusing the full `EpicDto`. This plan adds a narrow
   `EpicSummaryDto { id, key, title }` instead: those are the only three fields the pill, the chips and
   the picker options consume, and a narrow payload is what makes "return every epic, unwindowed"
   defensible against T-01-17-03 rather than merely convenient.

## Reversibility

The one decision above `reversible` here is granting `epic_list_all` an exemption from D-03's
"the core never returns the whole board" contract. It is rated `costly`, not `one-way`: undoing it
means re-windowing every consumer and re-deciding where labels come from — a coordinated change across
the command surface, the hook and three components — but it needs no migration, breaks no persisted
format, and publishes no external contract (there is no relay yet). No `checkpoint:decision` is
inserted; the weight is recorded on the task.

## Assumption-delta decision (checkpoint `assumption-delta` fired: pluralization)

<assumption_delta_decision>
**The assumption that broke.** The codebase held "the loaded board window contains every epic a visible
task references." That was invisibly true at 1 epic and is false at 13 — `01-UAT.md`'s own words. The
detector's lexical hit was on a ROADMAP annotation, but the genuine pluralization delta is this one.

**Noun now primary:** *the project's epic roster* — every epic belonging to a project — replacing
*the epics present in the currently loaded board page*.

**Decision: `promote`.** The roster becomes the single source for every epic label, chip and picker
option; the windowed `items.filter(item => item.kind === "epic")` derivation is **removed** from each
site rather than kept alongside it. Plan 01-18 completes the promotion by taking the `items` prop away
from `FilterBar` entirely, so that component can no longer see the window even by accident.

**Rationale:** keeping the windowed derivation alive next to a roster query would leave two answers to
"what are this project's epics" in the tree, which is the same silent-drift failure class as WR-03/WR-04
and directly contradicts the generalized intent.

**One demoted detail, recorded as accepted debt:** the `issue-parent` picker's **Tasks** group
(`BoardView.tsx` ~line 754) still reads the loaded window. Tasks are the unbounded set D-03's windowing
exists for, so a roster is not the right instrument there. What would force a promote: a per-id
parent-resolution command, or a user report that an issue whose parent task sits outside the window
reads as "No parent". Out of scope for G-01-2, not silently dropped.

**Invariant test encoding the generalized intent** (the checkpoint's optional companion, strongly
indicated here by `01-UAT.md`'s own fourth `missing` item): `packages/core/tests/epic_roster.rs`'s
`roster_returns_every_epic_past_the_board_window` and
`packages/desktop/src/board/__tests__/epic-roster.test.tsx`'s window-free render both go red the instant
a future change reintroduces the windowed assumption.
</assumption_delta_decision>
