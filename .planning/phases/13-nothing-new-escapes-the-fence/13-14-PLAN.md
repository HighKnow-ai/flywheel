<deliberate_narrowing>
**The `.sql` half of the FNC-04 finding is NOT implemented here, deliberately. The owner must decide
it; it is surfaced to the orchestrator rather than silently scoped down or silently taken.**

The verifier is right that `.sql` is unscanned and that Phase 14 adds schema, which is where the hole
bites. But scanning `.sql` migrations with the vocabulary gate is a recorded **Deferred Idea** in
`13-CONTEXT.md` ("the spine pin and the table-classification test already cover schema change; a
third gate on the same diff was not worth it"), and a locked deferral is not a planner's to reverse.

The counter-argument the owner should weigh, recorded here so the decision is informed:

- The deferral's stated premise does not hold for this specific hole. The spine pin covers the
  `CREATE TABLE` text of `epics`/`tasks`/`issues` only; table classification covers table NAMES, not
  column names. A Phase 14 `cycles` table with a `sprint_length_days` column passes the spine pin
  (the three pinned tables are unchanged), passes table classification (the table gets an entry), and
  passes the PM vocabulary gate (`.sql` unscanned). Three gates, zero coverage.
- The change is one token: add `"sql"` to the `SCANNED_EXTENSIONS` const this task introduces.
- It fires on nothing today. Every corpus word across all 23 `.sql` files under
  `packages/core/src/db/migrations/` was checked while planning: zero occurrences.

Task 1 therefore makes the reversal cheap and visible (a named const with this reasoning in its doc
comment) without taking it. Cost of reversal if the owner says yes: one token plus one line in the
walker-reach test.
