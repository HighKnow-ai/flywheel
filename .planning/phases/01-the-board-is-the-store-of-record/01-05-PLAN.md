<objective>
Make the store survive the two failures the phase's fifth success criterion names: a force-quit
mid-work, and a version upgrade that migrates the database. Prove both with tests that actually kill
a process and actually run a bad migration, rather than trusting the pragma choice and the happy
path.

Purpose: `DATA-07` and `DATA-08` are the criteria a user cannot verify by looking at the screen. The
only honest evidence is a harness that crashes on purpose and a fixture database one schema version
behind.

Output: a crash-safety suite, a migration-safety suite, and the restore path that makes "reversible
within one version" a file restore rather than a hope.
</objective>

    backups directory and a mode flag. In `--commit-then-hang` it opens through `open_and_migrate`,

    `env!("CARGO_BIN_EXE_crash_harness")` against a `tempfile` scratch directory, reading stdout

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| previous application version → migrated database file | A file written by an older build is read and rewritten by a newer one |
| backups directory → live database file | The restore path copies a file over the store of record |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-10 | Denial of Service | `open_and_migrate` failure path | high | mitigate | A failed `to_latest` restores the pre-migration backup and refuses to open, surfacing the error; a grep gate fails the build if any code path deletes the live database file |
| T-01-17 | Tampering | `restore_from_backup` target path | medium | mitigate | Restore copies only from a path this process itself returned from `backup_database_file` in the same call, never from a caller-supplied or user-supplied filename |
| T-01-18 | Denial of Service | unbounded backups directory | medium | mitigate | `prune_backups` retains 5 and removes the oldest on every successful migration |
| T-01-19 | Information Disclosure | backup copies of the database | low | accept | The backups sit beside the live file in the same OS app-data directory, under the same user's permissions, and carry no secret the live file does not already carry (`01-RESEARCH.md` § Security Domain, V6). Revisit when credentials enter the schema |

## Flagged assumptions

The deterministic edge probe classified three of this phase's requirements as `unclassified`, which
means it could not derive an edge category from the requirement text. Per protocol these stay
`unresolved` and are surfaced rather than auto-resolved. Two belong to this plan:

- **DATA-07 — unclassified edge.** The probe could not categorise "survives an unclean application
  termination". This plan's reading, which the executor should confirm rather than assume: the
  failure modelled is a *process* kill (SIGKILL, force-quit, panic), not an OS power loss, because
  that is what the phase's success criterion names and what `synchronous=NORMAL` covers. If power-loss
  durability is in scope, `synchronous=FULL` is the change and it costs roughly twice the write
  throughput — raise it rather than widening the test silently.
- **DATA-08 — unclassified edge.** The probe could not categorise "reversible within one version".
  This plan's reading: reversibility is delivered as a pre-migration file restore (D-18), not as
  hand-written down-migrations, and "within one version" means the single most recent backup is
  guaranteed restorable while older ones are best-effort within the retention limit.
