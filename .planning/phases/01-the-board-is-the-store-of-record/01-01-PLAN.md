  <behavior>
    - Opening a fresh database file leaves `PRAGMA journal_mode` reading back as `wal`.
    - Opening an existing database a second time reports `synchronous = 1`, `busy_timeout = 5000`
      and `foreign_keys = 1` — these are connection-scoped and must be re-applied every open.
    - `open_and_migrate` against a fresh path leaves `PRAGMA user_version` at `1`.
    - `open_and_migrate` against an already-migrated path leaves `user_version` at `1` and appends

    - A backup file exists in the backups directory after `open_and_migrate`, and its bytes equal
      the pre-migration file's bytes.
    - Backing up a path that does not yet exist is a no-op that returns `Ok` and writes no file.
    - Inserting an actor with `type` outside `human|agent|system` returns an error from SQLite.

  <action>
    Write `packages/core/src/ids.rs` exposing `pub fn new_id() -> String` backed by a process-wide
    `once_cell::sync::Lazy<Mutex<ulid::Generator>>` so same-millisecond calls stay monotonic, and
    `pub fn is_ulid(s: &str) -> bool` checking the 26-character Crockford-base32 shape. Every entity
    id in this project comes from `new_id()` (DATA-02).

    Write `packages/core/src/db/backup.rs` exposing
    `pub fn backup_database_file(db_path: &Path, backups_dir: &Path) -> anyhow::Result<Option<PathBuf>>`.
    It returns `Ok(None)` when `db_path` does not exist. Otherwise it creates `backups_dir`, reads
    the current `user_version` from the file, and copies to
    `backups_dir/pre-migration-{user_version}-{unix_millis}.db`, returning the new path. Copy the
    file with `std::fs::copy` before any connection has run DDL — this is D-18's whole point: the
    restore is the reversibility mechanism, not a down-migration.

    Write `packages/core/src/db/mod.rs` exposing:
    - `pub fn apply_pragmas(conn: &Connection) -> anyhow::Result<()>` setting `journal_mode=WAL`,
      `synchronous=NORMAL`, `busy_timeout=5000` and `foreign_keys=ON`. All four are set on every
      open; only `journal_mode` persists in the file, and the other three silently revert to SQLite
      defaults otherwise (`01-RESEARCH.md` Pitfall 1).
    - `static MIGRATIONS: Lazy<Migrations<'static>>` built from
      `M::up(include_str!("migrations/0001_actors.sql"))`. Later migrations append to this vector.
    - `pub fn open_and_migrate(db_path: &Path, backups_dir: &Path) -> anyhow::Result<Connection>`
      which calls `backup_database_file`, opens the connection, calls `apply_pragmas`, runs
      `MIGRATIONS.to_latest(&mut conn)`, and on a `to_latest` error returns the error without
      leaving a half-migrated file open. Do not issue `PRAGMA foreign_keys` from inside a migration
      body — it is a documented no-op there.
    - `pub fn default_db_path() -> anyhow::Result<PathBuf>` and `pub fn default_backups_dir()`
      resolving one fleet-wide database under the OS app-data directory (D-14: one file for every
      project, never one per repository). Both take no working-directory input and never read the
      process cwd (ARCHITECTURE.md Anti-Pattern 3).
