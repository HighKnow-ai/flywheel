<objective>
Make the whole board drivable from the keyboard: a single binding table, a focus-region model with
one owner at a time, an Escape ladder that closes one layer per press, selection that survives a
pushed delta because it tracks an id rather than a row index, and a ⌘K palette that makes every
action reachable without memorising a letter.

Purpose: `BOARD-07` is a hard product requirement, and `PRODUCT.md` records the reason — this is
expert software used all day at high frequency, where keystroke latency and predictable focus outrank
first-run charm. The subtle half is the focus contract: a list that re-sorts under the user's cursor
without preserving identity is a defect, and Phase 2 onward has agents writing to this board, so
deltas will arrive unprompted.

Output: a board a developer can run for a day without reaching for the mouse.
</objective>

  <action>
    Create `packages/desktop/src/state/keyboard.ts` holding `BINDINGS` — one declarative table whose
    entries carry the key, the focus region it applies in, the action id, and a human label. Model the
    focus regions as an enumeration with exactly one owner at a time: project rail, search field,
    board list, quick-add input, item detail panel, command palette. Tab and Shift+Tab move between
    regions; within a region the table decides.

    Export `resolveBinding(event, region)` returning the action or nothing. It must return nothing for
    a bare letter when the active element is a text input — a single-letter action never fires while
    the user is typing, and this is the ambiguity the binding model has to settle deliberately rather
    than by accident of event ordering.

    Implement the Escape ladder as a fixed order closing exactly one layer per press: command palette,
    then item detail panel, then quick-add, then clear selection. Pressing Escape with nothing open
    and nothing selected is a no-op.

    Implement the board-list bindings from the spec: `j` and down arrow move selection down, `k` and
    up arrow move it up, Home and End jump to the first and last row of the current view, Enter and
    `o` open the detail panel, `c` opens quick-add at the current position, ⌘⌫ deletes with the
    destructive confirmation. The pickers bound to `s`, `p`, `e` and `a` and the ⌘↑/⌘↓ reorder already
    exist from plans 01-04 and 01-07; move their key handling into this table so there is one source
    of truth rather than handlers scattered across components.

    Change selection to be held in `uiStore` as an **item id**, never a row index, and resolve it to a
    position at render time. This is the hard requirement in § "Focus & selection model": when the
    core pushes a delta and the query refetches, selection follows the same id to its new position and
    the viewport scrolls the minimum amount needed to keep it visible — it never resets to the top.
    When the selected id is no longer in the window, move selection to the next-nearest surviving id
    in the previous order. The transition is a plain state change, not an animated re-render.

    With zero items, the navigation keys are no-ops: they must not throw and must not move focus out
    of the list region, so an empty board is still a place the keyboard can rest.

    In `BoardRow.tsx`, give every row an accessible name concatenating key, title, status and
    priority, and set `aria-setsize` and `aria-posinset` from the band's true total and the row's true
    position — not from the mounted window — so a screen reader announces position and total even
    though only a window exists in the DOM. Use the ARIA listbox or grid pattern consistently rather
    than mixing roles.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| keystroke → board mutation | A key press invokes a mutating command, including a destructive one |
| palette command → command surface | A generated command list becomes an invocation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-25 | Tampering | ⌘⌫ delete binding and its palette entry | high | mitigate | Delete always routes through the destructive confirmation that names the item type, key and title; the binding never calls the delete command directly, and the confirmation is keyboard-dismissible with Escape defaulting to cancel |
| T-01-26 | Spoofing | palette command list generation | medium | mitigate | Commands are generated from the static `BINDINGS` table plus typed runtime lists; no command label or action id originates in user-authored item content, so an item titled like a command cannot become one |
| T-01-04 | Repudiation | keyboard-initiated mutations | high | mitigate | Every mutation still goes through the existing command handlers, which resolve `actor_id` in Rust — a keystroke path does not bypass attribution |
| T-01-02 | Elevation of Privilege | `menu.rs` and the menu-triggered actions | high | mitigate | Menu items invoke the same registered commands as the UI; no menu item is given a broader capability, and no item exists whose action is undefined |
</threat_model>
