<objective>
Close UAT gap G-01-4: make opening quick-add land the keyboard cursor in its input from any scroll
position and any band-collapse state, so a task or epic can be created and typed without touching the
mouse.

Purpose: the product's stated invariant is mouse-free operation — 01-UI-SPEC.md's Keyboard Map promises
"⌘N | New task (opens quick-add, **focused**, in the current group)" and every UAT test in this phase
says "with the mouse untouched". Today that promise holds only while the board happens to be scrolled
near the top and the Backlog band happens to be expanded. Two independent mechanisms break it, and both
are planned here.

Output: a focus path that survives virtualization (a request-driven, consume-once focus effect plus a
scroll-into-view that mounts the row before focus is expected), a collapsed-Backlog path that can no
longer swallow the row, and the first test in this repo that renders the board above the virtualizer's
overscan window.
</objective>

<design_decision>
## The defect has two independent halves, and both are planned

`01-UAT.md`'s G-01-4 diagnosis names them. Half one: `<QuickAdd autoFocus>` (BoardView.tsx:590-591)
uses React's `autoFocus`, which fires only on mount, and the row it sits on is virtualized — press ⌘N
while scrolled more than roughly `(1 + 10) x 40 = 440px` down and the virtualizer declines to mount the
row, so nothing ever focuses. Half two: `BoardView.tsx:303`'s `if (collapsedByStatus[status]) continue;`
skips the row's insertion outright while Backlog is collapsed, so there is no row to mount at all.

A plan that fixes only the scroll half still ships a ⌘N that does nothing focusable for any user who
collapsed Backlog. Task 1 fixes the scroll half; Task 2 fixes the collapse half.

## Why a store-held "focus pending" flag rather than a ref handle or a nonce

The gap's `missing[1]` offers two shapes: "an effect keyed on `quickAddOpen`" or "an imperative ref
handle". Both fail one of the owner's two reported behaviors, so this plan uses a third: a
consume-once request flag in `state/uiStore.ts`.

- A **ref handle** (`useImperativeHandle`) cannot work at all in the reported case. At press time the
  row is unmounted, so the ref is `null` — there is nothing to call `focus()` on. The scroll must land
  first, and the row that mounts afterward has to focus itself.
- An **effect keyed on `quickAddOpen`** fixes the late-mount case but not the owner's literal words:
  "not stealing the focus when re-applied". Re-applied means pressing ⌘N while quick-add is *already*
  open. `openQuickAdd` sets `quickAddOpen: true` when it is already `true` — no state change, no
  re-render, no effect re-run, no focus.
- An effect keyed on **plain mount** (`autoFocus`, or an effect with no request state) over-fires: with
  quick-add open, scrolling the row back into view would re-mount it and yank focus out of wherever the
  user put it — and could yank it out of a trapped item-detail panel, which is exactly the class of
  defect G-01-1 was.

A request flag set by `openQuickAdd` and cleared by whoever consumes it satisfies all three: a late
mount consumes it, a re-press re-raises it, and an incidental re-mount finds it already consumed.

## Why the layer guard is structurally upstream of everything this plan adds

`useGlobalBindings` (`state/keyboard.ts:461`) calls `bindingAllowedInLayer(binding.id,
topLayer(currentLayerState()))` **before** it calls the handler. `BoardView`'s `handleContainerKeyDown`
makes the same check at line 406. So a refused ⌘N never reaches `openQuickAdd`, never sets the request
flag, and therefore never reaches either new effect — both of which are guarded on the flag, not on
`quickAddOpen`. That is why this plan's first prohibition is satisfied by construction rather than by a
second guard, and Task 3 asserts it rather than assuming it.

## Why `align: "auto"` and not a fixed alignment

`virtualizer.scrollToIndex(index, { align: "auto" })` scrolls the minimum distance that brings the row
into view, which is literally 01-UI-SPEC.md's "Focus & selection model" wording ("the viewport scrolls
the minimum amount needed to keep it visible — it never resets to the top of the list"). Coming from
below, `auto` resolves to the row's own start offset, so the result is deterministic for the test
without hard-coding an alignment that would need its own justification.

## Why the test harness needs a `scrollTo` stub

`@tanstack/virtual-core`'s `elementScroll` calls `instance.scrollElement?.scrollTo?.({ top, behavior })`
— an *optional* call. jsdom 30.0.1 implements `Element.prototype.scrollTop` (settable, stored) but does
NOT implement `Element.prototype.scrollTo` (verified: `typeof el.scrollTo === "undefined"`). So today
`scrollToIndex` in a test is a silent no-op that throws nothing and moves nothing — a regression test
written without the stub would pass for the wrong reason. `src/test/setup.ts` already exists to fix
exactly this class of jsdom gap (it stubs `ResizeObserver`, `offsetHeight` and `offsetWidth` for the
same virtualizer), so the stub belongs beside them, not in one test file.

## Deliberately NOT touched

- `effectiveQuickAddOpen = quickAddOpen || items.length === 0` (BoardView.tsx:290). Creating the first
  task on an empty board makes `items.length` non-zero, which closes the row — arguably at odds with
  01-UI-SPEC.md's "Enter creates the item and immediately opens a new blank quick-add row below it".
  That is a **different** defect, pre-existing, not reported in G-01-4, and out of scope. Preserve
  today's behavior exactly; do not widen this plan's diff to fix it.
- `epicsById`, `useEpics`, `FilterBar`, both `ParentPicker` option lists and `BoardRow.tsx` — all owned
  by plans 01-17/01-18 (G-01-2). This plan's second prohibition is that none of them are edited.
- `IssuesLane.tsx`'s always-mounted issues quick-add. It supplies no focus props today and must supply
  none afterward.

## Reversibility

All three decisions are `reversible`: a boolean field on a Zustand store, two guarded `useEffect`s, one
idempotent store action, and a jsdom stub in a test setup file. No persisted format, no migration, no
published contract, no IPC surface. There is no `one-way` decision in this gap closure, so no
`checkpoint:decision` is inserted.
</design_decision>
