## What the plan asked for, and what happened

**The four brand-filled buttons (binding decision 1).** `ItemDetailPanel`'s Start Work, Review and Continue Shaping and `RunsSection`'s Watch Live had `--accent-nontext` fills under `--text-primary-rack` text (3.05:1 light, 4.42:1 dark). They now carry `type-body control-edge detail-action`: `control-edge` (plan 14, `App.css`) gives the 3:1 `--border-control` edge, the chrome radius and the ink hover edge; `.detail-action` (`item-detail.css`) sets a transparent ground and ink text. No `--text-on-accent` anywhere. Measured in WebKit in both schemes: each button's ground is transparent, its edge is at least 3:1 against the panel ground and its text at least 4.5:1. The Acknowledge button and the panel's Status control took the same class; the three panel actions now share one row (`.detail-actions`, hidden when empty so an issue leaves no gap).

**The focus-ring defect class (binding decision 2).** `AcceptanceCriteriaList` had it in a new shape: `outline: focused ? "2px solid var(--focus-ring)" : "none"` driven by the cursor state `focusedId`, which a mouse click sets too, so a click left a permanent brand rectangle on the row. A criterion row is not itself focusable (the list is, and the cursor is a virtual one), so `:focus-visible` cannot sit on the row. The row now carries `data-focused` and the rule is `.criteria-list:focus-visible .criterion-row[data-focused="true"]`. A list focused by keyboard with no cursor row yet rings itself (`:not(:has(...))`), so it is never silent. WebKit proves both halves: click a row, `outline-style` is `none`; refocus by keyboard and press `j`, the new cursor row has a solid 2px ring in the focus-ring colour and the previous row has none. The palette's search field had a second instance of the same class (inline `outline: "none"` beat the global `input:focus-visible`, so a keyboard user saw no focus in the field they type in); that is removed and the ring is inset because the panel clips its children.

**Overlay rule (binding decision 3).** The five pickers are popovers (`--border-control` edge, `--shadow-popover`, no scrim). The palette is a sheet (`--scrim`, `--shadow-sheet`, `--border-control` edge). The worktree removal dialog is a dialog (`--scrim`, `--shadow-dialog`). No literal colour, scrim or shadow remains in the group. WebKit resolves the shadow and scrim strings to the per-mode role values (`rgba(31, 35, 40, 0.4)` light, `rgba(0, 0, 0, 0.6)` dark for the scrim) rather than a source grep alone.

**Selection reads the same in the palette and the pickers as on a task row (A-06).** The highlighted command and the chosen picker item are a `--row-surface-selected` surface shift plus the 2px `--selection-rule`, with a transparent 2px border when idle so nothing reflows. Picker items are square, as rows are. To make the shift visible the palette and the pickers now sit on the ground (`--surface-dominant`) rather than `--surface-secondary`: the first draft would have drawn nothing, since `--row-surface-selected` is nearly equal to `--surface-secondary` (the rail's trap in 08.1-14).

**Motion (binding decision 4).** Untouched in timing and easing. `panel-slide-in` is still on the panel (alongside the new `detail-panel` class), `palette-settle` is still on the palette, the palette still returns nothing while closed, and the mount structure is unchanged. The motion browser suite passes in the default and reduced-motion arms.

**The activity trail** stays fully populated on open and animates nothing; its entries became one hairline-separated row each (sentence first, actor and time pushed to the trailing edge when they fit, wrapping beneath when they do not).

### Auto-fixed Issues

**1. [Rule 1 - Bug / T-08.1-40] The destructive Remove button failed AA text in both modes**
- **Found during:** Task 1 (the plan said to keep the dialog's destructive roles at their asserted contrast)
- **Issue:** `destructiveButtonStyle` painted `--text-primary-rack` on a `--destructive-strip` fill. Measured: 2.95:1 light (`#1f2328` on `#cf222e`), 2.86:1 dark (`#ededed` on `#f85149`). The code comment claiming "6.3:1" is the retired palette's figure. Nothing asserted the pair, so the plan's premise ("already pinned AA by the per-mode contrast test") held for the destructive TEXT role but not for this fill.
- **Fix:** drawn as destructive text and edge on the dialog's own surface, no fill. That pair (`--destructive-text-rack` on `--surface-secondary`) is 5.03 light and 5.72 dark and is asserted in `contrast.test.ts`.
- **Files modified:** `item-detail/WorktreeRemovalDialog.tsx`, `item-detail/WorktreeSummary.tsx` (a comment that named the old fill)
- **Verification:** `finish.test.tsx`; the arithmetic was run, not assumed
- **Committed in:** `af1a072`

**2. [Rule 1 - Bug] The criteria list ringed a clicked row**
- Reported above under "The focus-ring defect class". **Committed in:** `af1a072`

**3. [Rule 1 - Bug] The palette's search field had no keyboard focus ring**
- Reported above. Inline `outline: "none"` beat the global rule. **Committed in:** `628deba`

**4. [Rule 3 - Blocking] Mixing `border` and `borderLeft` in React inline styles**
- **Issue:** giving picker items a 2px selected rule as `borderLeft` while they set `border: "none"` is a shorthand-and-longhand mix; React warns when the longhand changes on a re-render.
- **Fix:** the items set `borderTop/Right/Bottom: "none"` per side. Commented in each file.
- **Committed in:** `628deba`

**5. [Rule 3 - Test config] `vitest.config.ts` lets `item-detail.css` through as real CSS**
- Same reason as 08.1-14's `App.css`: an empty `?raw` would make the `:focus-visible` assertion vacuous. All 991 tests pass with it.
- **Committed in:** `af1a072`
