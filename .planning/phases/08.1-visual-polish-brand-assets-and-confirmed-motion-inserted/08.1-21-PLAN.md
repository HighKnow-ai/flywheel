Implements **A-08(a)** (`08.1-AMENDMENTS.md`, owner, 2026-10-08): the review surface gets a decline path,
in this phase, as its own plan with its own tests — a Request-changes action that returns the task to the
agent with its unchecked criteria as the reason. It also folds in the placement finding the same reviewer
raised, because it is the same change: the surface's only action is an 11px button in the title bar's far
corner, while the approved comp (`comps/review.html`, `.action-row`) puts **Request changes** and **Merge**
together at the foot of the criteria column, where the attestation actually completes.

**The finding.** "Request changes" is drawn in the approved comp and has never existed in the source
(`git log -S "Request changes"` returns zero commits). On the surface where this product's core value
(every unit of agent work anchored to a board item with real acceptance criteria) becomes a daily act,
work can be merged and never sent back. Plan 16 was a finish pass and correctly did not invent a feature;
its SUMMARY records the hold ("the review surface's missing Request changes decline path... Nothing here
adds it"). A-08(a) lifts that hold. This plan does not edit the 08.1-16 SUMMARY.

**Facts verified read-only against the real board on 2026-10-08 (nothing was written):**
- THRE-33, THRE-38, THRE-43, THRE-53 and THRE-58 are the only five tasks with a worktree. All five are
  `in_progress`. Each has three current criteria, all three unchecked: 15 current task criteria, 15
  unchecked.
- 181 tasks are `in_review`. None has a worktree and none has a criterion.
- 0 `task.changes_requested` events exist.

Consequence for the design: gating the action on `in_review` alone would offer it on **zero** real
tasks. The brief's edge is `in_review -> in_progress`; the real reviewable tasks are already `in_progress`.
So a decline is offered on `in_progress` and `in_review`. On `in_review` the status moves; on
`in_progress` the shared status writer's documented redundant-transition guarantee (`Ok`, no event, no
`updated_at` change; `domain/task.rs` lines 436-438) means the status does not move, and the decline is
still recorded and still reaches the agent. This is stated plainly so a later reader does not mistake the
no-op for a bug. No test in this plan writes to, or seeds, the real database.

**Decision 1 — where the reason lives (researched against the code; nothing new is stored).**
- An issue (`domain/issue.rs`, `create_issue_in_tx`) is the wrong object: it allocates a project key with
  `UPDATE projects SET key_counter = key_counter + 1` (line 109), mints a triage-lane row per click, and
  `context_packet.rs` never reads `issues` — its SQL constants (`TASK_ROW_SQL`, `EPIC_ROW_SQL`,
  `CRITERIA_SQL`, `SUMMARIES_SQL`, `WORKTREE_ROW_SQL`, lines 167-187) name tasks, epics, criteria,
  summaries and worktrees only, so the agent would never see it.
- There is no comments table: none of the 18 migrations defines one.
- `session_summaries.next_session_must_know` is the agent's own closing statement keyed to an agent run
  (`context_packet.rs` line 81); a human decline written there would forge a session, and the drift
  detectors read the latest summary.
- The **drift** channel (`PacketExtras.drift`) looks right and is a trap: `record_drift_warnings`
  (`domain/agent_run.rs` line 326) appends a `drift.detected` event for every warning at run start, and
  `query/recovery.rs` (lines 14, 73, 93) treats "most recent run has a `drift.detected` event" as an
  outstanding recovery item, which raises the Needs Decision pill and the rail count (D-46, "money burning
  and waiting on me"). Every relaunch after a decline would flag the task. The decline does NOT travel
  as drift, and a test pins that.
- **What fits:** the `events` log. `event_type` is unconstrained text (`0002_board_schema.sql` line 124),
  so no migration is needed. The precedent is exact: `forge/transitions.rs` appends
  `task.done_with_unmet_criteria` (line 49, appended at lines 206-240) in the same transaction as a
  status write, with the unmet predicate (current revisions, `checked = 0`) and a human `label` that
  `render_description` shows in the activity trail with no UI change. The event is the **marker and the
  audit snapshot** (count and criterion ids, never statement text); the **reason itself is derived live
  from the criteria** at read time, so it is never stale and is never a second copy of board text. No new
  table, no new column, no migration.
- **How the agent reads it:** one new data field on the context packet, `review_feedback`, and one new
  `## Review Feedback` section in `render_prompt` (omitted entirely when absent, per that file's
  omit-the-heading rule). It is populated inside `assemble_context_packet`, so both the preview and the
  run start get it from the one assembler. The launch sheet renders structured fields, not the prompt
  string, and T-02-21 forbids the sheet differing from what the agent is told; so the DTO and the sheet
  gain the same section from the same Rust sentence.

**Decision 2 — the standing decision this runs into (D-122), and how it is honoured.** D-122 (Phase 7)
allows only two forge-driven status moves, forward only, and rejected backward moves because they "read
as the board second-guessing the user". Three review test headers (`merge-sheet`, `epic-request` and
`keyboard-activation`) and the two sheet sources cite D-122 for a structural guarantee: the adapter mocks
list no status setter and `invokeCommand` rejects unknown commands. A-08(a) is the
owner's decision and the move here is a human act on the board, which is the opposite of the board
second-guessing the user; it does not contradict D-122's rule about what the forge may move. It does end
the claim that the review tree writes no status at all. So the guarantee is narrowed, not dropped: the
review tree may call exactly one status-moving command, `review_request_changes`, which takes a task id
and can only ever do the one edge; no generic status setter is reachable from it, asserted by grep on
non-test sources and by a strict-mock test. D-145 (a merge moves no status) is untouched. Forge baselines
are edge-triggered (`forge/transitions.rs` moves a task to `in_review` only from a `None` baseline), so a
decline on a task with an open request is not flipped back by the next poll. The orchestrator should record
this reading in A-08(a), as it did for A-08(b)'s D-46 note; this plan's executor does not edit the
amendments file.

**Decision 3 — which action leads.** Merge keeps the lead (the 2px `--selection-rule` ink edge, A-07's
device) whenever it is offered. Request changes is a secondary on the hairline: `control-edge`, 1px
`--border-control`, transparent ground, ink text, weight 400. The comp draws Merge as the primary; plan 16's
closure gave Merge the lead edge after a reviewer found it indistinguishable from the scope toggles, and
reversing that now would undo a reviewer-driven fix. When Merge is not offered, Request changes does **not**
inherit the lead: absence does not promote a decline, and the foot simply has no lead. No fill, no brand
and no destructive colour on either (owner, 2026-10-08; D-11, D-12): a decline is reversible, not
destructive.

**No confirm sheet.** A decline writes nothing outside the board, spends nothing and is undone by moving
the card to In Review or by checking the criteria; a sheet would add friction to the daily act. The cost
is shown instead of confirmed: a muted line states "sends N unchecked criteria back" before the click, and
the button's accessible description is that line.
