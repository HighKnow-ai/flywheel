## What the plan asked for, and what happened

**The legend (binding decision 4), Task 1.** The plan's premise was that five registry entries describe "per-status paper tints" the UI no longer draws. They do not: those five entries are the **status** marks (Backlog, Todo, In Progress, In Review, Done), which `BoardRow`, the pickers and `statusMarkId` all read, and the plan's own verify (`grep -c 'strip-' marks.ts` = 0) was unsatisfiable only because the ids kept the name of the retired strip stock. So the entries stay, and what was actually stale is gone: the ids are `status-*`; `Legend.tsx` no longer paints a status swatch in a `--strip-*` tint or its glyph in strip ink (the swatch is the same neutral one the priority glyphs sit on); two meanings that called an outline glyph "filled" ("a half-filled circle", "a filled circle with a check mark") now say what is drawn. I verified every other entry against what the product draws:

| What changed in 08.1 | What the legend said | Now |
|---|---|---|
| `change-ahead` is `Triangle`, `change-dirty` is `Dot` (A-05) | already right in the registry, and the glyph test pinned it | also asserted that **no other mark** uses either glyph: `project-current` used `Dot`, the exact collision A-05 was meant to remove. It is `PanelLeft` now |
| The current project is marked neutrally (D-12) | `project-current` said "one of the few places the accent role marks the current position" | it says the rail entry lifts to the page ground and no colour is on it |
| The 2px selection rule (A-06) | the selected swatches differed from the ground by 1.07 and 1.04: invisible in a 20px swatch | both selected swatches draw the 2px rule, in `--selection-rule` and `--selection-rule-unfocused`, measured in WebKit |
| The focus ring | "the element reachable by Tab" | says it is the brand ring, and that a field that takes focus on open wears the ink rule instead |
| The epic roster's progress bar and task-distribution strip (A-01, D-06) | undefined: marks the product draws that the legend did not define | `epic-progress` and `epic-distribution` added to the `epic` channel |
| Per-tier edges | not a mark | not added; they are not marks |

The registry is pinned by exact per-channel count (`row-state 4, focus 1, status 5, priority 5, epic 4, criteria 7, estimate 3, assignee 4, project 3, agent 17`, 53 in all), so a removal or an addition is one change with its count.

**Overlay (binding decision 3).** The legend's dialog drew `rgba(0,0,0,0.45)` and `0 12px 32px rgba(0,0,0,0.45)` inline. It is `.legend-scrim` (`--scrim`) over `.legend-dialog` (`--shadow-dialog`, a `--border-dialog` edge, `--radius-chrome`), asserted from the stylesheet and measured in WebKit in both schemes (scrim `rgba(31, 35, 40, 0.4)` light and `rgba(0, 0, 0, 0.4)` dark; the dark edge is `#909090`, the light is `#7a828c`; frame one is at full opacity with no animation). `DoneWarning`'s literal `0 8px 24px rgba(0,0,0,0.35)` and divider edge are `--shadow-popover` and `--border-popover`.

**No brand fills (binding decision 1).** `ProposalRow`'s Accept and `ProposalAmendEditor`'s Save were `--accent-nontext` with ink on top (3.05 / 4.42:1). Both are redrawn; so is `SettingsSurface`'s chosen segment, which group four handed over: an ink edge, a 2px ink foot rule, no fill, no weight change (a segment that grows pushes its neighbour along). The triage surface's Pending/Deferred toggle painted `--surface-secondary` on the pressed one, which is invisible on the page ground; it takes the same device. Save is the one lead in the editor. Nothing is a destructive fill in this group. `--text-on-accent` was not used and, after this plan, **nothing under `src/` consumes it or `--destructive-strip`** (grepped), so plan 20 can retire the first.

**The focus-ring-on-prop defect (binding decision 2).** Found, and it was the same defect: `ProposalRow` set `outline: selected ? "2px solid var(--focus-ring)" : "none"`. `selected` is true after a mouse click, so a click left a permanent brand rectangle. It is not `:focus-visible` that fixes it here, because the row is a `div` with no `tabindex`: `selected` is the j/k cursor, the board's "current position", which the spec marks neutrally. The row now reserves a 2px edge and sets it to `--selection-rule` on `--row-surface-selected` when selected (`data-selected`, and `aria-current`). WebKit clicks a different row, asserts the rule moved, and asserts `outline-style: none` on every row. The checked components: `SettingsSurface`, `PermissionRulesTable`, `TriageSurface`, `ProposalTray`, `ProposalAmendEditor`, `Legend`, `DoneWarning` have no other inline `outline`; a test fails if one appears (`DoneWarning`'s `outline: "none"` on a non-interactive container is excepted by name).

**The text-input leftover (binding decision 5).** I closed it for this group and said so rather than rewriting `App.css`: every field here (the API key, the two open-command templates, the reject-reason field, the amend editor's fields) is `control-edge admin-field`, a 3:1 boundary with a 2px ink `:focus-visible` ring. The amend editor's first field is `autoFocus`, which is where a brand ring would have stood as a permanent box. The triage checkbox took the system accent; it is ink now (`accent-color`). `App.css`'s `input:focus-visible` is still the brand for `QuickAdd`, `FilterBar`, the criteria composer and the title field: logged in `deferred-items.md` with the choice that needs the owner.

**One dialect with the board's challenge row.** `board/ChallengeRow.tsx` shows the same proposal inline. It uses the idle row surface, a hairline underneath, the target type as a muted uppercase label and drawn Accept and Reject. `ProposalRow` had a `--surface-secondary` card with a 6px radius, a **brand** uppercase type label and a brand Accept. It now matches: square, `--row-surface`, a hairline, muted type label, drawn actions. I changed this surface to match; I did not touch the challenge row (group one's file). One difference is deliberate: the challenge row has no `--row-surface-selected` state because it is not on the j/k cursor, the tray and the triage rows are.

**The permission rules table (T-08.1-49).** Flex rows with a `maxWidth: 140` project cell and a flexible tool cell did not line up row to row. It is one CSS grid shared by a heading row and the data rows (`140px 1fr 72px 88px 80px`), a hairline under each, no fill, no stripe. WebKit asserts each data row's four columns start where the heading's do, that every row is transparent with a 1px divider underneath, that Revoke stays inside its row, and that every Revoke is drawn (3:1 edge, 4.5:1 text). Revoke is the ink text role on a control edge, not an icon-paired destructive role: revoking withdraws authority, which is the safe direction, and it is not a destructive action in the sense `DeleteConfirm` is. The one destructive affordance in the group is the error text, which stays on `--destructive-text-rack` (pinned AA per mode).

**Fields and sections.** Settings sections are told apart by a hairline and a heavier section label (13px 600), not cards. The per-project rows and the forge rows are hairline rows at the board's 32px; the last row's own rule is dropped so the section's hairline is not doubled.
