## The decision, as asked and as answered

SC4 asks that the durations in the product be ones someone actually looked at. This is the first time
any of them were.

**Question asked (Task 3, verbatim from the plan):** "Confirm the four motion durations, or name a
different number for any of them."

**Options offered:** `confirm-all` (confirm all four as built) or `change-some` (name a different
number for one or more of the four). The answer could be per-motion.

**What was put in front of the owner:** all four durations with the contract's reasons (a peer surface
arriving, not a modal; nothing travels on a collapse; a palette that must feel instant; a selection that
signals "you moved"), a playable page at
`.planning/phases/08.1-visual-polish-brand-assets-and-confirmed-motion-inserted/comps/motion.html`
that inlines the shipped `motion.css` and `tokens.css` so the keyframes he watched are the shipped
keyframes, and the following caveats:

- **The easing is front-loaded, so each label overstates the felt duration.** With
  `cubic-bezier(0.16, 1, 0.3, 1)`, 90% of the travel is done at about **73 / 59 / 46 / 40 ms** for the
  220 / 180 / 140 / 120 ms motions respectively.
- **Two figures are the implementer's judgement, not derived:** the palette's **8px settle distance**
  (plan 09's cap, itself flagged as judgement) and **reading "selection move" as the row's background
  wash** (the contract says the surface and the rule transition; the wash is what carries it).

**Decision 1, durations: CONFIRM ALL FOUR, unchanged.**

| Motion | Value | Confirmed |
|---|---|---|
| Panel slide-in | 220ms | 2026-10-08 |
| Group collapse and expand | 180ms | 2026-10-08 |
| Palette open | 140ms | 2026-10-08 |
| Selection move | 120ms | 2026-10-08 |
| Easing (all four) | `cubic-bezier(0.16, 1, 0.3, 1)` | 2026-10-08 |

No duration value changed, so `motion.css` and `tokens.ts` took no duration edits for this half.

**Decision 2, row reorder: it FOLLOWS COLLAPSE at 180ms, and the dead token is RETIRED.** A single row
reordering travels at the collapse duration. That left `--duration-displace` (220ms) declared and
referenced by nothing. The owner's reason, recorded as he gave it: a declared-but-unreferenced constant
is the kind of dead value someone later "fixes" by wiring it back up. So it is removed from
`styles/motion.css`, `theme/tokens.ts` and the drift test. I did not capture the second question's
exact wording, only the answer; this section paraphrases it.

**SC4 now cites an observation, not an assertion.** The owner opened `comps/motion.html` and watched
the motions before answering, and he is the decider. What was observed was the shipped CSS running in
that page, not the packaged Tauri app. The values he confirmed are the values in `motion.css`, and the
drift test now fails if they move.

One honest limit: `--duration-settle` (180ms, the colour wash on a settling control) is not one of the
four and was not shown to him separately. It still ships, and it is still an unreviewed assertion.
`08.1-UI-SPEC.md` § Motion says so.

## Accomplishments

- **Four named durations**, one per motion the contract names, zeroed (with the existing settle) in the
  `prefers-reduced-motion` block, with the blanket `!important` rule and the running-session pulse
  exception untouched.
- **Detail panel** slides in from the trailing edge by `transform`, never width (board rows declare a
  container query type).
- **Palette** arrives at full opacity on its first frame and settles 8px down by `transform` only. It
  still unmounts while closed. This follows the UI-SPEC's resolved "never a fade" decision.
- **Groups** expand with a staggered top-down wipe and the rows below travel on the collapse duration.
  Removed rows disappear immediately (no exit animation, as the contract says).
- **Drift guard:** `motion.test.ts` is block-aware (normal block against reduced-motion block) and fails
  on a duration missing from the stylesheet, one zeroed but never declared, a value that drifted either
  way, and a retired token coming back.
- **Reduced motion measured in a real engine.** `test:browser:motion` runs the same browser test file
  with the Playwright context emulating `prefers-reduced-motion: reduce`. A first test asserts which
  world the engine actually landed in, so a config that silently failed to switch cannot make both runs
  measure the same case and pass twice.
- **No scripted animation.** A negative grep inside the browser test fails if the three touched
  components use WAAPI or `requestAnimationFrame`, so the blanket rule remains the only thing that matters.

## Deviations from Plan

### Owner-directed

**1. [Owner decision, Rule 4 authority] Removed `--duration-displace`, which the plan said to keep**
- **Found during:** Task 3
- **Plan text:** Task 1 said to keep both pre-existing duration properties, and the drift test pinned `durationDisplace`.
- **Why it changed:** once row travel moved to `--duration-collapse`, nothing referenced `--duration-displace`. The owner chose to retire it. His reason: a declared-but-unreferenced constant is the kind of dead value someone later "fixes" by wiring it back up.
- **Fix:** removed from `motion.css` and `tokens.ts`; `motion.test.ts` no longer pins it, still asserts the four live durations plus settle and the reduced-motion zeroing, and gains a test that fails if the token returns. The `BoardView.tsx` comment that named it now names `--duration-collapse`.
- **Verification:** drift test 10/10; full jsdom suite 932; both browser arms 34/34; `npm run build` exit 0.
- **Authority:** the owner. The deviation is deliberate and directed, not discovered.
- **Committed in:** `71df3d2`

### Made by the prior executor, carried forward

**2. [Rule 1 - Bug] Group expansion is a staggered top-down wipe, not the plan's literal enter keyframe**
- **Found during:** Task 2, in WebKit
- **Issue:** the plan's technique (stable keys so rows below slide, plus a short enter keyframe on new rows) drove the row below through the new rows, and their text overprinted for about 2 frames at 40-80ms.
- **Fix:** each new row takes `180ms / n` of the collapse duration and starts at `i * 180ms / n`, so the wipe front stays behind the travelling rows. Both the share and the delay derive from `--duration-collapse`, which the reduce block zeroes, so no delay survives reduced motion.
- **Files modified:** `motion.css`, `BoardView.tsx`
- **Committed in:** `44aa448`

**3. [Rule 3 - Blocking] `vitest.config.ts` `css.include` extended to `styles/motion.css`**
- **Found during:** Task 1 RED
- **Issue:** Vitest stubs `.css` imports to an empty module, so a `?raw` import of `motion.css` was empty and every "declared with this value" assertion was vacuous. The same reason `tokens.css` was already opted in.
- **Fix:** `include: [/styles\/tokens\.css/, /styles\/motion\.css/]`, plus a test that fails if the raw source is the empty stub.
- **Committed in:** `b00fe96`

**4. [Premise correction] Row displacement is proven by observing the transition, not by reading styles**
- **Found during:** Task 2
- **Issue:** the plan's premise was that, with rows keyed by identity (plan 10), the displacement utility finally has something to move. A computed-style read cannot show that a row actually travelled, so it would have passed even if nothing moved.
- **Fix:** the browser test polls `getAnimations()` on the row below an expanding group and requires a real `CSSTransition` on `transform` (and none under reduced motion).
- **Committed in:** `1c570b8`

**5. [Rule 2 - Missing critical] A branch assertion so the two browser runs cannot measure the same case**
- **Found during:** Task 1 and Task 2
- **Issue:** if the Playwright context failed to apply reduced motion, the default and reduced arms would both run in the default world and both pass.
- **Fix:** the first browser test asserts `matchMedia("(prefers-reduced-motion: reduce)").matches` and the resolved `--duration-panel` equal what the arm claims (`VITE_EXPECT_MOTION`).
- **Committed in:** `1c570b8`

**6. [Rule 3 - Blocking] RED evidence needed converting to the gate's record format**
- **Found during:** Task 1 and Task 2 RED
- **Issue:** `gsd_run check tdd-red-evidence` takes a JSON record (command, exit code, failing test, expected, actual), not raw Vitest output. `08.1-13-RED-EVIDENCE-task{1,2}.json` hold those records, both with verdict `RED_EVIDENCE_OK`.
- **Committed in:** `b00fe96`, `1c570b8`

## Known simplification

- **Off-screen new row:** a new row that is off-screen when its group opens plays its wipe when it first scrolls into view, until the rows array next changes. This is marked in `BoardView.tsx` with a `ponytail:` comment: the new-row set is derived from the rows array, not from what the virtualizer has mounted, because scrolling mounts rows that already existed and must not animate. It is harmless, and fixing it needs a timer. Upgrade path: clear the entering set on a timer sized to the collapse duration.
