## Task 3: The decision

**Question asked (verbatim from the plan):** "Adopt the comped visual direction wholesale, or send it back naming what is wrong."

**Options offered:**
1. **adopt**: "Adopt wholesale and proceed to tokens and the new contract." Plans 07 and 09 unblock; the palette is re-derived once; the finish passes get a target. Con: one-way, the old measured ratios cannot be restored without restoring the old ground.
2. **send-back**: "Send it back, naming what is wrong." Costs a comp rather than eleven surfaces. Con: plans 07 and 09 stay blocked until a revised comp is adopted.

**Answer:** "adopt". The owner looked at all six rendered PNGs (mission-control, item-detail and review, each light and dark) before answering. He was told beforehand that the comps are code-rendered static HTML, not image-generated (RESEARCH Correction 11); that the agent-challenge, running-agent and commits-ahead values are labelled FIXTURE because the real board has none today; and that adoption is one-way and voids the measured palette in `01-UI-SPEC.md` (D-19). The adoption line is at the top of `08.1-DIRECTION.md`: "Adopted 2026-10-07 by the owner".

**Three caveats the owner was shown and accepted when adopting:**

- **(a) The craft detector had not actually run when the comps were presented.** Its parser modules were missing, so it ran degraded on regex fallback and its zero findings were an undercount, not a clean bill. (It has since run for real; see below.)
- **(b) The epic roster's visual rhythm is untested.** The seed data is uniform (nearly every epic reads 15/60), so the row design has not been judged against real variance in progress.
- **(c) The roster's lead row is the junk epic `test · 0/1`, and the "No epic" bucket holds all 181 in-review tasks, which is the entire review queue.** Neither is the direction's fault, but the roster's strongest position currently holds junk. The owner adopted knowing this.

**Register candidate for plan 20 (not written here):** caveat (c) should be appended to `.planning/DEFERRED-REVIEW.md` by plan 20. The junk `test` epic and the 181-task no-epic bucket are a data defect that plan 11's roster will otherwise inherit. This plan did not write to the register.

## Code-rendered disclosure and FIXTURE labelling

The comps are static HTML and CSS, not image-generated, because no image generation exists in this environment (RESEARCH Correction 11). This is a disclosed substitution. Values the real board cannot supply (agent challenge, running agent, commits-ahead) are rendered and tagged FIXTURE, including one deliberately labelled row carrying a non-zero commits-ahead count. The FIXTURE tag is comp-only scaffolding and does not ship.

## Craft detector: the real result

After the owner authorised installing the detector's parsers, `htmlparser2`, `css-select`, `css-tree` and `domutils` went into `~/.claude/plugins/marketplaces/impeccable` (`npm install --omit=optional`), and `detect.mjs` was re-run on the three comps and `comp.css`. Result, replacing the earlier degraded undercount: **135 findings, all severity `warning`, zero errors**.

| Finding | Count |
|---|---|
| `cramped-padding` | 115 |
| `tiny-text` | 14 |
| `undersized-ui-text` | 5 |
| `flat-type-hierarchy` | 1 (sizes 11/12/13/14/15/20px, ratio 1.8:1) |

Full output: `comps/detector-report.json`. The `cramped-padding` mass sits on `.row`, `.nav-item`, `.lens` and `.field`, the deliberately dense row grammar that D-13 fixes at 32px/28px. The detector has no knowledge of that density contract, so these need judgement, not blind compliance. The 9px FIXTURE tag is comp-only.

**The selection-rule question is still undecided, and the install did not settle it.** `skill-ban-side-stripe-borders` is prose in `craft-floor.md` ("a *colored* `border-left` or `border-right` above 1px on cards, list items, callouts, or alerts"), not a `detect.mjs` antipattern. The detector emits no finding for it and never can. The contract's treatment is `border-left: 2px solid var(--text-primary-rack)`: 2px and on a list item, but ink rather than an accent colour, which is exactly the ambiguity the ban's word "colored" leaves open. **Plan 09 still owns this decision**, to be made by judgement against the four alternatives rendered in `mission-control.html`. Plan 09 must NOT record the detector as having cleared the 2px rule. The detector is silent on it by construction, not by approval.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Comps are generated static HTML (`comps/build-comps.mjs`), not HTML that fetches the JSON**
- **Found during:** Task 2
- **Issue:** The plan's own checks require `data-epic-row` markup to be present in the file source, and the craft detector needs real markup to evaluate. HTML that fetches `comp-data.json` at load time satisfies neither.
- **Fix:** `build-comps.mjs` (not in the plan's `files_modified`) reads `comp-data.json` and writes the three HTML files with the rows in the markup. Every value is HTML-escaped (T-08.1-11).
- **Files modified:** `comps/build-comps.mjs` (new), `comps/mission-control.html`, `comps/item-detail.html`, `comps/review.html`
- **Verification:** 14 `data-epic-row` elements in `mission-control.html`; plan acceptance checks passed at the Task 2 commit.
- **Committed in:** `a170b6b`

**2. [Process] Craft detector ran degraded, then was re-run for real**
- **Found during:** Task 2
- **Issue:** The detector's parser modules had never been installed, so its empty result was an undercount. A package install is not auto-fixable, so it was logged (`7c18fa1`) rather than worked around.
- **Fix:** The owner authorised the install; the orchestrator installed the four parsers and re-ran the detector (`493dda8`). Result above.
- **Committed in:** `7c18fa1`, `493dda8`
