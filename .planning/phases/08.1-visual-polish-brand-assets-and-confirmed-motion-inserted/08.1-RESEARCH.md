**The home surface — "Mission Control"**

- **D-05:** **The epic roster leads.** Each epic row carries: title and key, a progress bar, a task-distribution strip by status, a count of agents running on it, and a count of proposals waiting on the owner. Expanding an epic reveals its content in place. — **Reversibility:** costly — `BoardView`'s row model, the virtualizer's size function and the board query's grouping all change together.
- **D-06:** **Progress is tasks done/total, with criteria as a finer second number where present.** The database holds **four** `acceptance_criteria` rows across a 907-task board, so a criteria-driven bar would read 0% on every epic. An epic whose tasks carry no criteria prints **"no criteria yet"** — never a 0% that lies.
- **D-07:** **The status-band rack becomes a lens, not a second surface.** ONE board, ONE virtualized rack, ONE keyboard map, ONE query — a grouping toggle switches the grouping key between **epic** and **status**. - **D-08:** **An agent's challenge renders inline, above the epic's tasks.** Expanding an epic shows its open proposals first, then its tasks. **Accepting one creates a task in place**, so the roadmap grows itself.
- **D-09:** **The "what this says" summary line is computed from board state by a fixed rule set** (~6 clauses: decisions pending, items reviewable, agents blocked and for how long, epics with no criteria). Zero cost, zero latency, cannot hallucinate. An agent-written version is deferred.

## Summary

This phase is mostly *not* the phase CONTEXT.md describes. Reading the code and replaying the owner's real database against it overturned four load-bearing premises, and the planner needs to start from the corrected picture. **First, `logo.svg` exists** — untracked, in the main checkout at `/Users/cymarechal/cymarechal/HighKnow-harness/logo.svg` (14,257 bytes, sha1 `c4b6b770baeb9476aa95258ebc1422c9e6cec572`, byte-identical to four copies in the sibling `HighKnow-mvp` repo). The worktree `find` that concluded it did not exist could not see an untracked file in another checkout. Criterion 2 is "copy, commit, reference", and criterion 1 is one ~1 second `tauri icon` run once the full-bleed square is wrapped with an inset margin. `PRODUCT.md` and `DESIGN.md` also exist (tracked, repo root); PRE-CONTEXT finding 2 is wrong, and `PRODUCT.md` still says the mark decision is open.

**Second, and most important: the board the owner judged never showed real data.** `board_list` returns at most 200 rows (`DEFAULT_LIMIT: i64 = 200`), the renderer never pages, and the order is backlog → todo → in_progress → in_review → done. Replaying that ORDER BY over a copy of the real database: 920 rows total, window = 180 backlog + 20 todo + 0 in_progress; the five tasks that have worktrees sit at positions 551–555 and have **never been loaded by the renderer**. That — not the absence of a cue — is why finding the reviewable task took a hand-written SQL query. D-05 (epic roster with progress), D-07 (status lens preserving the "all in review" sweep) and D-17 cannot work on the current data path, so a scoped-fetch data layer is the first thing to build, and it does not depend on the visual direction.

**Third**, three of D-15/D-16/D-18's assumptions do not hold as written: `git_facts_for_task`'s target ref (`origin/<integration>`) resolves for only 1 of the 5 real worktrees, so `▲N` computed that way would be absent almost everywhere (Phase 8's `review.rs` already solved this with local refs); `board_forge_flags` is an events-table read that "never shells out", so `board_change_flags` is not its "exact structural twin" — it spawns git; and `useEpicTaskRollup` is a per-epic, criteria-count query in `review/`, not a task-status rollup. **Fourth**, none of the three motions in criterion 3 exists in code today (panel, palette and band mount/unmount with no animation), and height-animating a group inside a flat fixed-height virtualizer needs a deliberate technique. On the plus side the toolchain is in better shape than assumed: a real WebKit browser-test arm already exists, `paint.ts` already measures rendered contrast, and the existing `* { transition-duration: 0s !important }` reduce rule will collapse any new CSS motion without further work.

**Primary recommendation:** Run three independent tracks in parallel from day one — (A) asset track: copy `logo.svg`, wrap for inset, `tauri icon`, assert; (B) data track: scoped board fetch + `board_epic_progress` + `board_change_flags` (local refs, git outside the DB lock) + `has_worktree`, plus D-23 seeding; (C) direction track: contract → static-HTML comps at real density → `checkpoint:decision` → `08.1-UI-SPEC.md` → tokens. Keep every existing custom-property *name* and change only values, so the re-theme lands in `tokens.css` instead of touching 53 files.

### Pattern 1: Re-theme by value, not by name
**What:** Leave every existing custom property name (`--surface-dominant`, `--text-primary-rack`, `--divider`, `--accent-text-rack`, `--accent-text-strip`, `--destructive-strip`, `--blocked-text-strip`, `--row-surface*`, `--radius-*`) in place and re-point values; add a `@media (prefers-color-scheme: dark)` block for the dark values and keep light as `:root`. The strip-tint family (`--strip-backlog` … `--strip-done`) becomes five aliases of one ground (or is deleted where the 4 consuming files are rewritten for the new row).
**Why:** The token files are the only place hex literals may live (`tokens.css` header: "No component may declare a literal hex colour outside this file and theme/tokens.ts"). Usage today, counted by `grep -rl` over `src/` excluding tests: `surface-dominant` 23 files, `surface-secondary` 29, `divider` 41, `text-primary-rack` 41, `text-muted-rack` 38, `accent-text-rack` 22, `accent-nontext` 14, `destructive-text-rack` 18, `radius-chrome` 36, but `strip-` only 4, `text-primary-strip` 6, `accent-text-strip` 2. ### Pattern 2: Re-derive contrast per mode and let the test own the numbers
**What:** Replace the single `RACK`/`STRIP`/`INK` objects with `LIGHT` and `DARK` typed mirrors, and have `contrast.test.ts` (a) assert every role pair per mode and (b) parse `tokens.css` by block (`:root { … }` vs the `prefers-color-scheme: dark` block) and assert the TS mirror equals the shipped CSS in each. The existing drift check is a single regex over the whole file — with two declarations of each property it would pass if *either* matches, so it must become block-aware or it silently stops protecting the dark values.
**Measured this session** (script replicating `theme/contrast.ts`'s WCAG formula, run in node):

| Pair | Ratio | Reading |
|---|---|---|
| light text `#1f2328` on ground `#ffffff` / surface `#f6f8fa` | 15.80 / 14.84 | AA body, large margin |
| light muted `#59636e` on `#ffffff` / `#f6f8fa` | 6.11 / 5.74 | AA body |
| dark text `#ededed` on `#0a0a0a` / `#0f0f0f` | 16.91 / 16.37 | AA body |

**Painted proof:** `src/review/__tests__/browser/paint.ts` already exports `paintedContrast` / `effectiveBackground`, built on the same `relativeLuminance`, and `legibility.browser.test.tsx` shows the pattern. Add one browser test per mode that mounts a real `BoardRow` and asserts `paintedContrast` for key/title/muted/progress — this is what makes "the table is not the proof" literal. It needs `colorScheme` emulation (see Pattern 5).

### Pattern 4: Confirmed motion = four named tokens + a recorded decision + a drift test
**What "confirmed" can mean mechanically** (criterion 4 must cite an observation): (a) the contract table in `08.1-UI-SPEC.md` lists each duration with its stated reason; (b) the build uses four **named** custom properties in `motion.css`; (c) a `checkpoint:decision` presents the four live and records the owner's accepted-or-changed number with date in the same table; (d) a vitest test `?raw`-imports `motion.css` and asserts each declared value equals the confirmed value in `MOTION` (`theme/tokens.ts`) — the same drift-guard shape `contrast.test.ts` already uses for `AGENT`. Without (c) the numbers are still assertions; without (d) they can drift back.
**Today:** `motion.css` has `--duration-settle: 180ms;` and `--duration-displace: 220ms;`, both zeroed under `prefers-reduced-motion`. D-21's four (`panel` ~220, `collapse` ~180, `palette` ~140, `selection` ~120) map to new properties; the old two stay only if still referenced (`App.css:54-56`, `:97` use `--duration-settle`; `BoardView` uses `.displace-transition`).
**Reduced motion is already structurally safe for CSS motion:** the block is `:root { --duration-settle: 0s; --duration-displace: 0s; }` plus `* { animation-duration: 0s !important; transition-duration: 0s !important; }`. An `!important` author declaration beats an inline `style="transition: …"`, so inline transitions collapse too. **Do not use the Web Animations API or JS-driven animation** — the blanket rule does not touch it. A keyframe `animation` with duration `0s` jumps straight to its end state, which is exactly "instant state change".

### Pattern 5: Testing reduced motion and colour scheme in WebKit
The browser arm is `vitest.browser.config.ts` (`provider: playwright()`, `instances: [{ browser: "webkit" }]`). The vitest docs list `contextOptions` on the provider (`playwright({ contextOptions: { reducedMotion: 'reduce', colorScheme: 'dark' } })`) [CITED: vitest.dev/config/browser/playwright]; the `instances` page lists no per-instance context options [CITED: vitest.dev/config/browser/instances — silent, so treat per-instance as unavailable; ASSUMED]. So the practical route is **separate config files** (or an env switch read by one config): `vitest.browser.config.ts` (default), plus reduced-motion and dark variants, each selected with `--config`. Assert with `getComputedStyle(el).transitionDuration === '0s'` / `animationDuration === '0s'` under reduce and a nonzero value without it. A jsdom-only fallback that always works: `?raw`-import `motion.css` and assert the reduce block's literal contents.

### Pattern 6: The change cue — read board half under the lock, git half after
**What:** mirror `review::review_target_inputs` / `finish_review_target` (documented as the lock-safe split: "Safe under the database lock; hand the result to `finish_review_target` once the lock is released"). `board_change_flags` should: (1) under `state.db.lock()`, `SELECT w.task_id, w.path, w.branch, t.epic_id, e.integration_branch, p.default_branch FROM worktrees w JOIN tasks t … WHERE w.project_id = ?1 AND w.status = 'active'`; (2) drop the lock; (3) per row, base = the epic's local `integration_branch` else the project's `default_branch` (never `origin/…`), `ahead = git rev-list --count <base>..<branch>`, `dirty = !crate::domain::worktree::porcelain_entries(path)?.is_empty()`.
**Constraints found:** `porcelain_entries` is "the sole caller of `git::git_status_porcelain` (WORK-03's one-porcelain-read-site contract)" — use it, do not add a second status call. Every git read must go through `crate::git` (`supervisor_cwd.rs` asserts one `Command::new("git")` site). The scheduler's hot and cold ticks hold `AppState.db` *across* `git_facts_for_task` (`scheduler.rs:run_hot_tick`/`run_cold_tick`: `let Ok(mut conn) = state.db.lock()` then the loop), so a command that also holds the mutex across git would queue behind them.
**Measured cost:** 10 × (`git rev-list --count … ` + `git status --porcelain`) in `THRE-58` took 0.481 s ≈ 48 ms per worktree on this machine (small repo). Five worktrees ≈ 0.24 s per sweep, serial. `board:changed` fires on every board mutation *and* on each scheduler digest change, so naively invalidating on every event spawns ~10 git processes per edit. **Mitigate:** run the sweep via `spawn_blocking`/off the IPC thread, set a `staleTime` of several seconds on the hook, and (optionally) parallelise the per-worktree reads. Do not add a cache of the verdict (D-75).
**Merged tasks:** after an integrated merge the three-dot range is empty (`review.rs` comment in `finish_review_target`), so `ahead = 0` for a merged task is correct and the D-17 `status = 'active'` restriction already excludes it.
**Real data reality:** all five active worktrees are 0 commits ahead of their local integration branch and exactly one (`THRE-58`, `README.md` modified) is dirty. The cue will be nearly invisible on today's data — the comp and the tests need a fixture with commits ahead and dirty trees (use `FLYWHEEL_APP_DATA_DIR` against a scratch DB, as `tests/bin/uat_seed_ui.rs` does, which "refuses to run without it").

### Pattern 8: Animating a group inside a flat fixed-height virtualizer
**Constraint:** the board is one flat `rows` array rendered as absolutely positioned `translateY(start)` divs keyed by `virtualRow.key`, which defaults to the **index**. Collapsing removes rows from the array; the element at each index stays and its *content* swaps, so no position changes and nothing animates today. The existing `.displace-transition` (`transform 220ms`) never fires for a collapse.
**Recommended technique (keeps D-13):** (1) pass `getItemKey` returning the item id so a row keeps its DOM node across a collapse/expand and the existing `.displace-transition` slides rows below into place; (2) give newly mounted rows a short CSS `@keyframes` enter (opacity/translateY), so an expanding group reads as growing without measuring; (3) removed rows disappear immediately (no exit animation). This reads as a height animation without `measureElement`, `grid-template-rows` or per-row measuring. [ASSUMED] visual result — prototype it in the WebKit arm before promising it.
**Item detail panel:** `transform: translateX(100%) → 0` on the `<aside>` via a CSS `animation` on mount. Do **not** animate width: rows are `container-type: inline-size` and their `@container` ladder re-evaluates on every width frame.
**Palette:** it mounts only while open (`return null` otherwise), so a mount-time `@keyframes` fade/scale works; an exit animation is not possible without keeping it mounted and is not required by SC3.
**Note:** `01-UI-SPEC.md § Motion` and `§ Motion grammar` ("Never a fade") contradict each other on the palette; D-20 voids § Motion, so the new contract resolves it.

### Anti-Patterns to Avoid
- **Deriving epic progress from the loaded window.** It is 200 of 920 rows, ordered by status; progress would be wrong and look plausible.
- **Using `git_facts_for_task` (or its `target_ref`) for `▲N`.** Four of five target refs do not resolve; it also does a `git log`, `rev-parse` and `FETCH_HEAD` stat the cue does not need.
- **Holding `AppState.db` across git in the new command.**
- **A per-row `useQuery` for any signal** (D-16's own rule) — including per-epic progress.
- **Folding a structural change into a visual task** (D-03): the epic-first IA, the grouping lens, the `has_worktree` epic semantics and each Keyboard Map / Row Anatomy amendment are separate `checkpoint:decision`s.
- **Literal hex or `rgba()` in components.** Today these slip through: `ProjectRail.tsx:81` hard-codes `rgba(60, 100, 221, 0.14)` (the brand at 14%); scrims `rgba(0,0,0,0.45)` and shadows appear in `CommandPalette`, `DeleteConfirm`, `LaunchSheet`, `OrphanRecoveryModal`, `WorktreeRemovalDialog`, `MergeConfirmSheet`, `Legend`, five pickers and `DoneWarning`. Under D-10's "no fills / hairline" recipe, shadows and scrims need a token decision per mode (a black scrim at 45% is wrong on a white ground).
- **JS-driven animation** (WAAPI, `requestAnimationFrame` tweens) — bypasses the reduce rule.

## Common Pitfalls

### Pitfall 1: Building the roster on a 200-row window
**What goes wrong:** epic rows show wrong progress; expanding an epic shows a fraction of its tasks; the status lens' "everything in review" sweep is empty (in_review rows start past row ~560).
**Why:** `DEFAULT_LIMIT = 200`, no paging, ordering puts backlog first (verified by SQL replay).
**How to avoid:** Pattern 3 — aggregate for progress, scoped `board_list` for content. Make a Wave-0 test that fails if any epic's displayed total differs from `COUNT(*)`.
**Warning signs:** an in-progress or in-review band that is empty while its header count is non-zero (this is the state of the live board today).

### Pitfall 2: Passing contrast numbers copied from the old spec
**What goes wrong:** the new light ground makes `#3c64dd` text AA by itself while the dark ground still fails it; applying the old two-lift model gives a light-mode text colour that is *less* accessible than the brand itself (`#7d99ff` on white is 2.67:1).
**How to avoid:** pair every accent role with a per-mode ground in the test; never reuse a token across modes without asserting both. Add a `--border-control` role. Re-measure the `AGENT` set (`success/destructive/blocked-text-rack`, `blocked-text-strip`) on both new grounds — their current values were chosen against `#171b22`/`#1e232b` and `#e6e1d6…#dde9dc`.
**Warning signs:** `contrast.test.ts` still importing `RACK`/`STRIP` after the palette changes.

### Pitfall 3: The drift-check regex passing on one mode only
**What goes wrong:** `contrast.test.ts` asserts `--agent-key: value;` appears *anywhere* in `tokens.css`. With a second declaration inside the dark media block, a wrong dark value passes if the light value matches.
**How to avoid:** parse by block; assert per-mode equality between `tokens.ts` and the corresponding CSS block.

### Pitfall 4: `ahead` is `None` almost everywhere
**What goes wrong:** the cue reads "nothing" for 4 of 5 real tasks and nobody notices because 4 of 5 are also 0 ahead.
**How to avoid:** local refs (Pattern 6); a Rust test with a real scratch repo (commits ahead, dirty tree, base branch only local); distinguish "0 ahead" from "cannot measure" in the return type (`Option<u32>`), as `git::ahead_behind` already does.

### Pitfall 5: Hairline rules used as control borders
See Pattern 2 consequence (2). `#1f1f1f` on `#0a0a0a` is 1.20:1.

### Pitfall 6: Tests that mirror layout constants
**What goes wrong:** `board/__tests__/volume.ts` re-declares `ROW_HEIGHT = 40`, `OVERSCAN = 10`, `BAND_HEADER_COUNT = 5`, `QUICK_ADD_ROW_COUNT = 1` and the jsdom viewport 800, and `quick-add-focus.test.tsx`'s `the_volume_fixture_exceeds_what_the_harness_can_mount` is designed to fail when its margin disappears. D-13's four heights and the nested model change every one of these assumptions at once, and `ROW_HEIGHT` is currently one shared constant exported from `BoardRow.tsx` (`export const ROW_HEIGHT = 40;`).
**How to avoid:** replace the shared constant with a `ROW_HEIGHT_BY_KIND` export and have `volume.ts` import it rather than mirror it. Update G-01-4's quick-add row-index logic (`quickAddRowIndex`) — its comment already says the index "is only `1` while Backlog is first in `BAND_ORDER`".

### Pitfall 7: Wrapping the icon wrongly
**What goes wrong:** `tauri icon logo.svg` works but produces the full-bleed rounded square (verified: the rounded square touches the canvas edges, `rx=200` of 1024). A full-bleed icon looks oversized next to other macOS icons in the Dock.
**How to avoid:** author an `app-icon.svg` that places the existing 1024 mark scaled to ~824/1024 and centred on a transparent 1024 canvas (a test run with an 824-wide rounded square at offset 100 produced a correctly transparent-margined `icon.png` with alpha). The 824 figure is the commonly cited macOS grid [ASSUMED — not confirmed against Apple's template in this session]. Keep the committed `logo.svg` untouched for in-app use.
**Also:** `tauri icon` writes `android/` and `ios/` directories and a `64x64.png` into the output; the project is macOS desktop only, so delete `android/`/`ios/` before committing (they would be dead files), and keep `64x64.png` only if wanted (`tauri.conf.json` does not list it).

### Pitfall 8: Verifying the icon by eye, or by file mtime
**How to avoid:** the scaffold blobs are known — at commit `286a403`, `icons/32x32.png`=`9c0ad672…`, `128x128.png`=`24045aa1…`, `128x128@2x.png`=`4a537e15…`, `icon.icns`=`12a5bcee…`, `icon.ico`=`06c23c82…` (the working tree matches them today). A test that reads `tauri.conf.json` `bundle.icon`, asserts each file exists, its magic bytes/dimensions match, and `git hash-object` differs from the scaffold blob is a runnable SC1 proof; add a pixel assertion (centre-region is white mark, corner is transparent) to rule out "different but still wrong".

### Pitfall 9: Impeccable mechanical gate vs D-12
`detect.mjs` and `craft-floor.md:35` ban a >1px coloured side border on list items. Run the detector on the *first* comp-derived row, before building eleven surfaces on a selection treatment it flags. If it flags a neutral 2px rule, the alternatives are a 1px rule, an inset `::before` bar, or a background-only shift — and that is a D-03 decision, not an executor's quiet workaround.

### Pitfall 10: Keyed rows and selection/focus restore
Switching `getItemKey` from index to item id changes which DOM node holds focus/selection across a collapse. `BoardView` keeps `rowElRefs` by `item.id` and the Escape/focus-return behaviour relies on Radix scope restore; re-run `keyboard-nav.test.tsx`, `layer-guard.test.tsx` and `quick-add-focus.test.tsx` after the change.
