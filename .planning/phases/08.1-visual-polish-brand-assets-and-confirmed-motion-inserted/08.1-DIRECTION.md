# Phase 8.1 Direction Contract: Mission Control

**Status:** ADOPTED.
**Adoption:** Adopted 2026-10-07 by the owner (Cyril Marechal), wholesale (D-03), after viewing all six rendered comps (mission-control, item-detail, review, each in light and dark). Adoption voids the measured palette in `01-UI-SPEC.md` (D-19).

This is one direction, not a menu. It is written from decisions already taken in the 2026-10-07
discussion (`08.1-CONTEXT.md` D-01 through D-14 and D-21), and its only job is to be rendered
(D-04). The comps in `comps/` are this document drawn, not a second taste. If a comp and this
document disagree, the document is wrong or the comp is, and either way the owner is not asked to
reconcile them.

**How the comps are made, said plainly.** They are static HTML and CSS, rendered through this
project's own WebKit engine at 1440x900, in light and in dark, from data exported out of a copy of
the real board. They are **code-rendered, not image-generated**. Impeccable's comp pipeline needs an
image generator, and this environment has none (the image tools present are converters only and no
generation key is set; `08.1-RESEARCH.md` Correction 11). That is a disclosed substitution, not a
skipped step. Code-rendered comps have one real advantage here: they run at the board's true
density instead of a painter's idea of it.

## 1. The world (D-10)

Near-neutral ground. One surface family. One-pixel hairline rules. No fills. Type and spacing carry
all hierarchy. Authored for light and for dark from **one** token set, so dark is not a recolour of
light and light is not an afterthought.

The Flight Progress Strips material split (a cream light plane on a dark rack, five paper tints) is
retired. It was a hardcoded material story, not a theme, and it structurally cannot do light and
dark.

### Starting values (the owner's)

| Role | Token (name unchanged) | Light | Dark |
|---|---|---|---|
| ground | `--surface-dominant` | `#ffffff` | `#0a0a0a` |
| surface | `--surface-secondary` | `#f6f8fa` | `#0f0f0f` |
| rule | `--divider` | `#d1d9e0` | `#1f1f1f` |
| text | `--text-primary-rack` | `#1f2328` | `#ededed` |
| muted | `--text-muted-rack` | `#59636e` | `#8b8b8b` |

Token names stay exactly as they are today; only values change. That keeps the re-theme a two-file
value change (`tokens.css`, `theme/tokens.ts`) instead of a rename across 53 files. The `rack` and
`strip` suffixes become semantic debt to clean up after the owner is using the app.

### Measured ratios (WCAG 2.x relative luminance, the formula `theme/contrast.ts` uses)

| Pair | Light | Dark | Reading |
|---|---|---|---|
| text on ground / on surface | 15.80 / 14.84 | 16.91 / 16.37 | AA body, large margin |
| muted on ground / on surface | 6.11 / 5.74 | 5.81 / 5.63 | AA body |
| rule on ground / on surface | 1.43 / 1.34 | 1.20 / 1.16 | decorative hairline only |
| brand `#3c64dd` on ground / on surface | 5.17 / 4.86 | 3.83 / 3.71 | light: AA for text unlifted. Dark: clears 3:1 non-text, **fails 4.5:1 text** |

**The table is not the proof.** It is a starting position measured at the point of decision. The
proof is plan 07's runnable assertion in `theme/__tests__/contrast.test.ts`, which asserts every
pair in both modes and parses `tokens.css` per colour-scheme block so a wrong dark value cannot hide
behind a right light one. The 08.1 comps use the values below; if the assertion later disagrees
with this table, the assertion wins and this table is corrected.

### Two consequences of the measurements, carried into the comps

1. **A dark-mode brand lift is still required; a light-mode one is not.** The old `#2d4fb8` strip
   lift is retired. For brand-coloured text on dark, the comps start at `#5275e0` (same hue, 225
   degrees, lightness 60%): 4.55 on `#0f0f0f`, the worst dark surface. Plan 07 derives the final step
   by search and pins it.
2. **A hairline rule cannot be a control's border.** WCAG 1.4.11 wants 3:1 for the edge of an input
   or button, and `#1f1f1f` on `#0a0a0a` is 1.20. So the contract adds one role,
   `--border-control` (the border-control role), for inputs, pickers and buttons:

   | Role | Light | Dark | On ground / on surface |
   |---|---|---|---|
   | `--border-control` | `#7a828c` | `#707070` | 3.89 / 3.65 light, 4.00 / 3.87 dark |

   Without it the filter inputs and quick-add lose their visible edge the moment the rule goes
   hairline.

## 2. The colour rule (D-11)

Colour appears **only as a data channel**. The list of things that may be coloured is exhaustive:

| Channel | Meaning | Light | Dark |
|---|---|---|---|
| progress fill | tasks done over total (the brand, see section 3) | `#3c64dd` | `#3c64dd` |
| done | a finished state | `#1a7f37` | `#3fb950` |
| blocked | an agent is waiting on the owner | `#9a6700` | `#d29922` |
| failed | a run or check failed | `#cf222e` | `#f85149` |
| commits ahead | the `ahead` annotation (section 6) | brand text, lifted per mode | brand text, lifted per mode |

Measured on ground / surface: done 5.08 / 4.77 light, 7.79 / 7.55 dark; blocked 4.87 / 4.57 light,
7.84 / 7.59 dark; failed 5.36 / 5.03 light, 5.91 / 5.72 dark. All clear AA body text on both
surfaces. These are starting values for plan 07's assertion to confirm per mode.

Nothing else is coloured. **No tinted rows. No status fills. No pills with backgrounds.** The five
paper tints of the old world (`--strip-backlog`, `--strip-todo`, `--strip-in-progress`,
`--strip-in-review`, `--strip-done`) are **removed**, not re-pointed. Status keeps its shape glyph
and its printed word; colour was only ever the redundant third channel and now it is not even that.

## 3. The brand rule (D-12)

The progress fill carries the pinned hue `#3c64dd`. Selection is a **2px left rule plus a background
shift**, and it is **not** a brand colour. The rule is ink (text colour), the shift is the surface
role.

The reason, in the owner's terms: a brand that appears forty times down a page as a progress bar
reads as identity, a rhythm the eye learns. A brand that appears once as a highlight reads as a
cursor. Mission Control has a progress bar on every epic row, so the brand belongs to progress and
the current position gets a different, quieter mark.

**This supersedes `01-UI-SPEC.md`'s rule** that accent is reserved strictly for the current
position ("the brand blue marks exactly one thing"). That rule is voided here, by name, and plan 09
carries it in the `08.1-UI-SPEC.md` SUPERSEDES table. The old file is not edited in place; the
history of why the first world lost is preserved.

**The selection rule has one open conflict, recorded now rather than at the finish pass.** Impeccable's
`craft-floor.md` line 35 bans "a colored `border-left` or `border-right` above 1px on cards, list
items, callouts, or alerts". The contract's selection treatment is a 2px left rule on a list item.
The comp carries this on its selected rows. **The mechanical detector could not judge it:** `detect.mjs` ran in its regex fallback because its HTML and CSS parser modules are not installed here, and it states that its findings are an undercount, so zero findings is not a clean bill. The ban's wording is "a colored border-left"; whether a neutral-ink 2px rule trips it is unverified until the parsers are present (`deferred-items.md`) and the
Mission Control comp renders the alternatives the detector would accept side by side: a 1px rule,
an inset bar drawn as a pseudo-element, and a background-only shift. Choosing among them is plan
09's selection-rule decision gate under D-03. It is not an executor's quiet workaround.

## 4. The row ladder (D-13)

Four fixed row heights, by row kind. Never measured.

| Row kind | Height | Carries |
|---|---|---|
| epic header | ~64px | title and key, muted sub-label, progress bar, value, change delta, distribution strip, agents running, proposals waiting |
| challenge | ~48px | one open agent challenge or proposal, above the epic's tasks |
| task | ~32px | status glyph, key, title, criteria count, annotations |
| band header | ~28px | a status band's name and count, in the status lens |

**The virtualizer's `estimateSize` stays an O(1) lookup on row kind.** There is no `measureElement`,
no per-row measurement, no second pass over the array. That is the Performance Contract
(`01-UI-SPEC.md` § Performance Contract, BOARD-08), and it survives the move to a nested model
intact. The shared `ROW_HEIGHT = 40` constant becomes a `ROW_HEIGHT_BY_KIND` export that the test
volume fixture imports instead of mirroring.

## 5. The compare-row anatomy (D-05, D-06)

Adopted from the owner's reference. An epic row reads, left to right: **title**, a **muted
sub-label** (the epic key and its integration branch state), a **progress bar**, the **value**
(`done/total`), and a **change delta** (tasks moved to done in the recent window, or the commits-ahead
roll-up where worktrees exist). Beside the bar sits the task-distribution strip by status, the
agents-running count and the proposals-waiting count.

**The honesty rule (D-06).** Progress is tasks done over total, because the real board has only fifteen
criteria across 907 tasks (all on the five active-worktree tasks) and a criteria-driven bar would read
zero on almost every epic.
Where criteria exist they appear as a finer second number. **An epic whose tasks carry no criteria
prints the phrase `no criteria yet`** in the muted role, never a `0%` that lies.

The fixed ordering of the roster follows the board's own order. The "what this says" block (D-09)
sits above it, computed from board state by a fixed rule set, with zero cost and no ability to
hallucinate.

## 6. The change cue (D-15, D-18)

`▲N` is commits ahead of the integration branch and `●` is uncommitted changes. Both are notation
here; the shipped marks are Lucide glyphs registered in `legend/marks.ts` (a mark the legend does
not define may not exist). A task with no worktree shows nothing at all. On an epic row the cue
rolls up from its child tasks and occupies a slot that is **not** the one holding the
proposals-waiting count.

**What the comps can honestly show.** On the real board all five active worktrees are zero commits
ahead of their local integration branch and exactly one (THRE-58) is dirty. The cue is nearly
invisible on real data, so the Mission Control comp includes **one clearly labelled fixture row**
with a non-zero count, so the owner can see the cue at all. It is marked `FIXTURE` on the row. Two
other things the real board lacks are fixtures too and are labelled the same way: no agent is
running right now, and no proposal is pending, so the expanded epic's challenge rows and the
agents-running counts come from labelled fixtures, not from the export.

## 7. The typeface (D-14)

**Archivo holds.** It already satisfies every carried-over constraint, and this was checked by
running a font inspection, not assumed:

- licence: SIL OFL, self-hosted from `public/fonts/Archivo-Variable.ttf` beside `OFL.txt`
- tabular and lining figures: the `tnum` and `lnum` GSUB features are both present
- variable, 659 KB, axes `wght 100-900` and `wdth 62-125`, so the **width axis** gives the
  condensed cut for stamped keys and band headers without a second file
- not one of Impeccable's banned training-data defaults

If a later review argues for a replacement, that replacement cannot be adopted until the same
feature check has been run against it, and swapping a typeface is a **structural amendment plan 09
gates**, not a comp detail. The comps use Archivo.

## 8. The motion table (D-21, contract half)

Four named durations, each with the reason for that number. One easing curve across the product
(the existing `cubic-bezier(0.16, 1, 0.3, 1)`).

| Name | Duration | Reason | Confirmed value | Confirmed on |
|---|---|---|---|---|
| panel slide-in | ~220ms | A peer surface is arriving anchored to the list, not a modal takeover. It travels the furthest, so it earns the longest time. | | |
| group collapse | ~180ms | Nothing travels. Rows settle into place; a longer collapse reads as lag. | | |
| palette open | ~140ms | It must feel instant. The owner pressed a key and is already typing. | | |
| selection move | ~120ms | Signals "you moved". Faster than that is a snap, slower makes arrow-key travel feel sticky. | | |

The last two columns are **empty on purpose**. Plan 13's decision gate fills them after the owner
has watched all four once. **The two durations in the product today (`--duration-settle: 180ms`,
`--duration-displace: 220ms`) were never reviewed by anyone**; they were asserted in `motion.css`
and never confirmed, which is exactly the gap success criterion 4 closes.

Reduced motion is already structurally safe for CSS motion: `prefers-reduced-motion: reduce`
zeroes the durations and a blanket `!important` rule collapses every transition and animation. New
motion must stay in CSS so that rule keeps catching it.

## 9. What this document does not decide

It decides the visual world, the colour and brand rules, the row ladder, the row anatomy, the
typeface and the motion contract. It does not decide the structural amendments, which are separate
`checkpoint:decision` gates under D-03: the epic-first IA and the grouping lens (plan 06), the
`has_worktree` semantics for epic rows, the selection-rule treatment (plan 09), and the confirmed
motion numbers (plan 13). Adoption of this direction is wholesale (D-03) and voids the measured
palette in `01-UI-SPEC.md` (D-19). Nothing in the product's CSS has changed yet.
