# Phase 08.1 Plan 05: Epic Progress Data and Scoped Group Fetches Summary

**One grouped aggregate over every task (status, agent runs, criteria) behind a read-only command and a board-wide hook, plus a scoped group fetch that passes an explicit row limit so a 186-row bucket is complete instead of cut at 200**

## Performance

- **Duration:** 34 min
- **Started:** 2026-10-07T12:12:47Z
- **Completed:** 2026-10-07T12:46:59Z
- **Tasks:** 3
- **Files modified:** 10

## Accomplishments

- `board_epic_progress` reads status counts, running/blocked agent runs and current-revision criteria in three `GROUP BY` queries over all of a project's tasks. There is no row window and no ordering in it; a test with more tasks than the board's default window compares every epic's total with a direct `COUNT(*)`.
- `criteria` is an `Option` all the way from core to the TypeScript DTO. An epic with no criteria is `null`, which is a different fact from `{checked: 0, total: n}`, so D-06's "no criteria yet" can be printed truthfully. Neither the junk epic titled `test` (0/1) nor the 181-task No-epic review queue is hidden or smoothed: both come out as ordinary entries with their real numbers.
- `useEpicProgress` is one board-wide query refreshed on `board:changed`, with no polling and no per-epic query. `useEpicTaskRollup` from the review module was not reused (RESEARCH Correction 6).
- `useGroupItems` reuses `board_list` with the existing `epicIds` / `statuses` dimensions and passes a limit sized from the group's own total, clamped to the core's 500 maximum. It returns exactly what the core returned and reports `truncated` when a group is bigger than one call can hold.

## Window fixed, not routed around (RESEARCH Open Question 1)

This plan fixes the window instead of routing around it. The unscoped board list is a 200-row page over the board's rows and the renderer never pages, so any figure read from it is plausible and wrong. The roster's numbers now come from an aggregate with no window, and group content comes from the existing list command with an explicit limit. The unfiltered flat list used by search and filters still goes through the core's own bounded read, unchanged: its default of 200 and its clamp of 500 were not touched, so nothing else in the product gained an unbounded query. The only un-`LIMIT`'d SQL added is the aggregate, and it is allowlisted by name in the repo's unbounded-read gate with its real bound (epics times five statuses, plus the truncation error).

### Interpretations the plan left open

**2. Truncation is an `Err`, not a flag.** The plan fixes `board_epic_progress` to return `Vec<EpicProgress>` yet asks that more epics than the ceiling be reported as truncation. A `Vec` has no room for a flag, so exceeding the cap returns an error naming truncation (`failed:board_epic_progress:read` at the IPC boundary). The cap is `EPIC_ROSTER_CEILING` (5000), so this is a safety valve, not a path the current board can reach. If a softer degrade is wanted later, the return type is the thing to change.

**3. The Task 2 hook tests live in Task 3's file.** The plan lists no test file for Task 2, so its `<behavior>` cases (one board-wide query, re-run on board change, null criteria preserved) were written into `epic-roster.test.tsx` with Task 3's. Task 2 has no separate RED commit; the hook was written to the plan's sibling-copy instruction and its tests passed on first run.

**4. The core's no-epic bucket includes epic rows.** `board_list`'s epic filter matches on `COALESCE(epic_id, '')`, and an epic row's own `epic_id` is null, so filtering to the no-epic bucket returns the orphan tasks plus every epic row (186 + 13 = 199 on the real board). That is existing core behaviour and was not changed. `useGroupItems` therefore documents that its `total` for the no-epic bucket is tasks plus epic rows, and its test checks that all 250 orphan tasks are present rather than the row count. The consumer (plan 11) must treat `kind: "epic"` rows in that list as epics, not tasks.
