# Phase 08.1 Plan 01: Board change annotation Summary

**One board-wide `board_change_flags` sweep (SQLite read, then git, with the db lock released between) feeds a graded commits-ahead / uncommitted-changes annotation on each board row, registered in the legend and named for screen readers.**

## Performance

- **Duration:** 42 min
- **Started:** 2026-10-07T10:17:00Z (approximate; start time was not captured at spawn)
- **Completed:** 2026-10-07T10:59:00Z
- **Tasks:** 3
- **Files modified:** 14 (4 created, 10 modified)

## Accomplishments

- Core pair `change_flag_inputs` / `finish_change_flags`: the board half takes only a `&Connection` and spawns nothing; the git half takes no connection and goes through `crate::git` only. `ahead` stays `Option<u32>` from git to the DOM so cannot-measure never turns into zero.
- `board_change_flags` Tauri command accepts a project id and nothing else, caps the sweep at 200, drops the db mutex before git, runs git on the blocking pool, and is registered at `generate_handler!` and in the capability roster.
- `useChangeFlags` is the only new query key and is board-scoped; `BoardView` turns it into one id-keyed map and hands each row its flag.
- The row annotation renders a count (commits ahead) and a mark (uncommitted changes) beside the status glyph, appends to the row's accessible name, and is not a button or an alert pill.
- Tests run against real `git init` scratch repositories with no remote at all (8 Rust cases) and through `BoardView` with a stubbed adapter (14 TS cases). Full `cargo test --workspace` and the full desktop vitest suite (784 tests) pass.

## Decisions Made

- Base ref is the epic's local integration branch, else the project default branch, resolved in the board half. It never routes through `git_facts_for_task`, whose own base resolution was measured to resolve for one of five real worktrees.
- Zero ahead and cannot-measure both render nothing. A printed zero would read as a measurement; a missing figure must not read as "level".
- A worktree directory that vanished between the two halves is skipped rather than failing the sweep (the `missing` status exists for that race).
- The two marks went in the existing `agent` channel beside `ci-failed` and `proposal-pending`, which are the precedent for row signals.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's `staleTime: 5000` does not bound the sweep rate**
- **Found during:** Task 2
- **Issue:** The plan asks for a 5s `staleTime` so a burst of `board:changed` events does not spawn a git sweep per event. But the hook refreshes via `invalidateQueries`, which refetches an active query regardless of `staleTime`, so threat T-08.1-02's mitigation would have been a no-op.
- **Fix:** Kept `staleTime: 5000` (it still dedupes remounts) and coalesced the invalidation inside `useChangeFlags`: the first event in a 1s window arms one timer, later events in that window are dropped, the timer fires one invalidation. No `refetchInterval` was added. A test asserts a burst of five events yields no refetch inside the window and exactly one after it.
- **Files modified:** packages/desktop/src/board/useBoardQuery.ts, packages/desktop/src/board/__tests__/change-cue.test.tsx
- **Verification:** `change-cue.test.tsx` "coalesces a burst of board:changed events into one refresh"
- **Committed in:** a13c109, 073471e
