## What the plan asked for, and what happened

**The A-06 focus clause (assigned to this plan, built).** `--selection-rule` (`#1f2328` / `#ededed`) and `--selection-rule-unfocused` (`#7a828c` / `#707070`) are declared in both blocks of `tokens.css`, mirrored in `tokens.ts`, and wired into `BoardRow`'s existing `selectionOverlay` branch as a 2px left border (transparent when idle, so a row changing state never reflows). The proof is three layers, none of them a hex-inequality check: `contrast.test.ts` asserts each rule is at least 3:1 against every row surface in each mode and the focused rule is at least 3:1 against the unfocused one (4.06 light, 4.23 dark); `selection-rule.test.tsx` asserts the branch; `legibility.browser.test.tsx` paints a real `BoardRow` in WebKit under both schemes and asserts the resolved border colours, the 2px width, and the ratios between the painted values. A fourth assertion pins why the roles exist: the two selected surfaces are still under 1.05 apart.

**The commits-ahead colour (assigned, done).** The count takes `--accent-text-rack` on the task row and, for the same reason, on the epic row's rolled-up cue. The glyph and the accessible name stay, and the dirty dot stays neutral, as the UI-SPEC hand-off says.

**Overlay scrims and shadows (assigned, none were mine).** The UI-SPEC's table assigns plan 14 no component: the 14 literals belong to plans 15 to 19. I confirmed by grep that none of this group's ten components or `App.css` declares a literal colour, scrim or shadow. Nothing to fix, and I touched none of the other 14.

**The detector, and what it can and cannot see.** Run on the source files exactly as the plan's verify line states, `detect.mjs --json` returns `[]` for all of them. That is not evidence: it returns `[]` on `comp.css` too, and it cannot read JSX inline styles at all. So I rendered the real components in WebKit and had the capture test write the DOM plus the real stylesheets to a self-contained HTML per scheme, then ran the detector on that. Result on the built surface: 36 warnings, 0 errors, identical in both schemes.

| Finding | Count | Disposition |
|---|---|---|
| `cramped-padding` | 34 | Not fixed, on purpose. All on `.board-row`, `.epic-header-row`, `.status-band` and the rack wrapper: the fixed-height row grammar A-03 sets at 64/48/32/28px. The prompt said not to loosen heights to satisfy it. |
| `undersized-ui-text` | 1 (was 3) | Fixed the two real ones: the Blocked, Needs Decision, CI-failed pills, the ahead count and the estimate badge went from 10px to 11px. The remaining one is the `FIXTURE` tag in the capture page, comp scaffolding that does not ship. |
| `flat-type-hierarchy` | 1 | Not fixed. Sizes 10/11/13/15/16: the 11/13/15 steps are the locked Archivo scale (`01-UI-SPEC.md` § Typography, unamended). The 10px is the same FIXTURE tag. I did not trace the 16px (almost certainly an unclassed element inheriting the root size). |

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] Accept on a challenge row failed AA text**
- **Found during:** Task 1 (reading ChallengeRow against the new tokens)
- **Issue:** `--text-primary-rack` on the `--accent-nontext` fill is 3.05:1 in light and 4.42:1 in dark, both under 4.5.
- **Fix:** new `--text-on-accent` role (`#ffffff`, 5.17:1 in both modes), asserted in `contrast.test.ts`, used on Accept.
- **Files modified:** `tokens.css`, `tokens.ts`, `contrast.test.ts`, `ChallengeRow.tsx`
- **Committed in:** `13de21e`

**2. [Rule 1 - Bug] The focus ring would have covered the selection rule**
- **Found during:** Task 1 (reasoning about the hand-off's "the ring stays")
- **Issue:** an inset 2px outline at offset -2 occupies exactly the outermost 2px, which is where the 2px left rule is. The focused row would have shown the blue ring, not the full-ink rule A-06 specifies.
- **Fix:** offset -4, so the rule and the ring sit side by side. Confirmed in the WebKit capture (both visible on the focused row), and pinned by a jsdom assertion.
- **Committed in:** `13de21e`

**3. [Rule 1 - Bug] The epic roster header collapsed its title to nothing at narrow widths**
- **Found during:** Task 1 (the plan's own container-ladder trap)
- **Issue:** a fixed grid of 538px of columns left the title about 66px at the minimum window and 0 with the detail panel open. The header had no `.field-*` classes, so the ladder never reached it.
- **Fix:** the header's wrapper is a container; the template moved to `App.css`; the distribution strip drops at 900px and the progress column narrows at 640px. The signals (agents, proposals, the change cue) never drop.
- **Committed in:** `13de21e`

**4. [Rule 1 - Bug] Quick-add's input had no focus ring**
- **Found during:** Task 2
- **Issue:** the input carried inline `outline: none`, which beat the global `input:focus-visible` rule, so keyboard focus was invisible.
- **Fix:** the inline suppression is gone; the input also has a 3:1 boundary now, since the row's old hairline was its only edge.
- **Committed in:** `e4f38cd`

**5. [Rule 2 - Missing critical] The project rail marked the current project with the brand**
- **Found during:** Task 2
- **Issue:** the rail used `--accent-nontext` and `--accent-text-rack` for the current project, which D-12 voids. A first neutral attempt, a shift to `--row-surface-selected`, drew nothing, because that colour equals the rail's own ground.
- **Fix:** the current entry lifts to the page ground with a hairline edge and semibold. Seen in the dark capture; in light it is subtler.
- **Committed in:** `e4f38cd`

**6. [Rule 1 - Bug, test follow-through] Three existing tests asserted what the redesign removed**
- `menu-bridge.test.tsx` and `project-rail.test.tsx` looked up the project name with `findByText`, which now matches the rail row as well as the board's heading; switched to `findAllByText` and, for the ⌘3 case, to `aria-current` on the rail button.
- `needs-decision.test.tsx` asserted the two rail badges had different background colours. D-11 removed the fills, so it now asserts different text colours.
- **Committed in:** `e4f38cd`

**7. [Plan wording, not a defect] The plan's detector verify line is vacuous on this surface**
- Reported above. The checks that actually bite are the greps, the rendered-HTML detector run and the painted assertions.

## Reviewer record (Task 3)

**The shipped `impeccable-finish-reviewer` was not run. This must not be read as a reviewed group.** The executor's tools are Read, Write, Edit, Bash and Skill, with no subagent tool, so it cannot spawn one. The independent pass D-24 asks for is therefore **open**, registered as D-REV-11 in `.planning/DEFERRED-REVIEW.md` with `automatable: YES`: the orchestrator can spawn the reviewer against the paths below with no human involved.

**What I did instead, and it is not the same thing.** I captured the surface and reviewed it myself against the reviewer's own check list (fidelity, floor, truth). A builder reviewing its own build is exactly the attention gravity the reviewer exists to escape, so treat this as a first pass, not a verdict. Everything in it was found by looking at the screenshots and fixed or recorded.
