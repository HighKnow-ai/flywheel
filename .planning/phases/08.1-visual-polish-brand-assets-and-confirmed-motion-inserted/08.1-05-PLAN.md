<objective>
Build the data the epic roster needs, and fix the reason the roster could not have worked.

Implements **D-05**'s data half (each epic row carries a progress bar, a task-distribution strip by
status, a count of agents running on it) and **D-06** (progress is tasks done over total, with
criteria as a finer second number where present; an epic with no criteria prints a true statement
rather than a lying zero).

**The premise this plan corrects is the biggest one in the phase.** The ROADMAP's own notes say the
owner judged a board "rendering ~1,000 real items". `08.1-RESEARCH.md` Correction 3 replayed the
real query over a copy of the real database: the unfiltered window is **200 of 920 rows**, the
renderer never pages, and the ordering puts backlog first — so the window holds 180 backlog rows, 20
todo rows and **zero in-progress rows**, and the five tasks that have worktrees sit at positions 551
to 555 and have never been loaded. That, not the absence of a cue, is why finding the one reviewable
task needed a hand-written SQL query. An epic roster fed from that window would show wrong progress
and look plausible, which is the worst available outcome.

So this plan answers `08.1-RESEARCH.md` Open Question 1 the way research recommended, and says so
openly: **the window is fixed inside this plan rather than routed around.** Aggregates come from one
grouped query over all 907 tasks, and group content on expand comes from the existing list command
with an explicit row limit — reusing `BoardFilter`'s existing epic and status dimensions, so there is
no second filtering implementation anywhere (D-03's standing rule).

**Also corrected:** CONTEXT's code notes say `useEpicTaskRollup` "already answers D-05's progress
bar". `08.1-RESEARCH.md` Correction 6 found it lives in the review module, takes one epic id, and
returns per-task *criteria* counts rather than status counts — so calling it for thirteen epics would
be thirteen queries, which D-16's own rule forbids. It is not reused here.

Probe fallback: skipped — this phase has no REQ-IDs to probe (visible skip). `must_haves` derive
from SC0–SC4, the CONTEXT decisions and `08.1-VALIDATION.md`'s requirement-to-test map.

Purpose: make the roster's numbers true before anyone renders them.
Output: one core aggregate, one registered command, one board-wide hook, scoped group fetches, and a
test that fails if any epic's displayed total ever diverges from the real count.
</objective>
