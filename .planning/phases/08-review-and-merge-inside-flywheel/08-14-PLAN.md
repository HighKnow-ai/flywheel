<objective>
Close G-08-5 (review finding WR-08, decided in UAT: the guard IS required before this ships).
`forge_open_epic_request` takes an epic id and nothing else and re-reads the board at confirm time
(`epic_request_inputs` + `request_body::epic_draft_inputs`), while the preview the user read came
from a separate earlier `forge_epic_request_draft` call. There is no hash parameter in the IPC
signature, so "what you previewed is what gets published" cannot be enforced by construction.
`useEpicRequestDraft`'s `board:changed` subscription narrows the window but its refetch is async,
so a confirm can still fire against a stale render — and the whole product thesis is agents
mutating the board while a human reviews, which makes that window routine rather than theoretical.

Purpose: this is the one action in the phase that publishes board content outside the machine, to
a possibly public forge (D-118/D-120). A body the user did not read is a trust failure, not a
cosmetic one.

Output: `RequestDraft` grows a `content_hash()`; the preview carries it; the confirm requires it
and refuses with the bare category `draftChanged` before anything is pushed; the sheet answers a
refusal by re-fetching and re-rendering. `EpicRequestSheet`'s existing "previews verbatim"
property is preserved — the hash is computed over the SAME `title` and `body` the sheet rendered,
because both sides call the same core function on the same struct.
</objective>

<design_decision>
## Why a hash and not the text itself

The lazier-looking fix — send the previewed title and body back and compare them for equality —
is the wrong shape here and would undo a property the design already has. `forge_open_epic_request`
and `forge_open_request` both document it: "Accepts an epic id and nothing else ... so a caller
cannot influence the text beyond choosing which epic to preview" (T-07-09-01). Putting body text
in the IPC signature re-opens exactly that hole. A digest keeps "the renderer cannot influence the
published text" and adds "and it must match what was shown". That is why WR-08 named a hash.

## Why SHA-256 and why no new package enters the tree

`sha2` is already resolved in this workspace's `Cargo.lock` at `0.10.9` (pulled in via
`tauri-codegen` and `wry`), with its registry checksum recorded. Declaring `sha2 = "0.10"` as a
direct dependency of `packages/core` therefore adds **zero new packages** to the resolved tree —
nothing is downloaded, nothing new is compiled, and the supply-chain risk the package-legitimacy
gate exists to catch is structurally absent. Task 1 proves that rather than asserting it: the
`[[package]]` count in `Cargo.lock` must not change. `sha2` is RustCrypto's own crate, the same
one Tauri's toolchain already trusts in this build. `08-RESEARCH.md`'s Package Legitimacy Audit
records no `[SLOP]` and no `[SUS]` package for this phase.

A stdlib `DefaultHasher` was considered and rejected: it would work for same-process change
detection, but WR-08 and the UAT decision both name SHA-256, and the cost of honouring that is
zero given the crate is already in the tree.

## Scope: the epic path only

`forge_open_request` (the TASK request, Phase 7, `item-detail/ForgeSection.tsx`) has the same
structural exposure and is NOT fixed here — G-08-5's truth is scoped to the epic request sheet and
REVW-05. `content_hash()` lands on `RequestDraft`, which both drafts share, and
`RequestDraftDto.contentHash` is therefore already on the task preview too, so adopting the guard
there later is a signature change and a two-line comparison. Recorded here deliberately so it is
not lost: **follow-up — apply the same `draftChanged` guard to `forge_open_request`.**
</design_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → Tauri IPC (`forge_open_epic_request`) | Untrusted-by-design: the command must not accept text the renderer supplies |
| Flywheel → the forge (`gh` / `glab`) | The one outward publish in this phase; content may become public |
| concurrent writers → the board | Agents mutate epics and criteria while a human reads the preview; this is the designed-for case, not an edge case |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-14-01 | Tampering (published content differs from reviewed content) | `forge_open_epic_request` | high | mitigate | `RequestDraft::content_hash()` is compared against the caller's echoed hash and the command returns the `draftChanged` category BEFORE `open_epic_request_at`, so a mismatch pushes nothing and creates nothing |
| T-08-14-02 | Spoofing (renderer dictates the published text) | IPC signature | high | mitigate | The signature still accepts no title, body, branch or target — only an epic id and an opaque digest. The core re-assembles the text itself; the digest can only cause a refusal, never a substitution |
| T-08-14-03 | Information disclosure (diagnostics leak over IPC) | `forge.rs` error mapping | medium | mitigate | The refusal is the bare category name with no detail; both digests and the epic id go to the host `eprintln!` log only, preserving plan 08-12's category-only contract |
| T-08-14-04 | Denial of service (confirm loops forever on a busy board) | `EpicRequestSheet` | low | accept | A refusal re-renders and leaves the button live; the user re-reads and re-confirms. An agent writing faster than a human reads is a livelock the user can exit with Cancel, and a retry-suppressing guard would be the D-144 anti-pattern applied to the wrong failure |
| T-08-14-05 | Repudiation (a weak digest misses a change) | `content_hash` | low | mitigate | SHA-256 over title, a separator byte and body; the boundary case is asserted by a dedicated test, and the criterion-check test proves it notices a one-character body change |

Task 1's criteria require `git diff -- Cargo.lock` to introduce no `+name = ` line and the `[[package]]` count to be unchanged — stronger evidence than a registry eyeball. RustCrypto crate, no build script of our own |
