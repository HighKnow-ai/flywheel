<objective>
The merge, in the core: a dry run that cannot touch anything, a real merge in a worktree that
belongs to the epic rather than to a task, an abort that is a safety net rather than a hope, one
event, and no status write.

This is the half of phase success criterion 3 that decides whether the product is trustworthy —
"any conflict is surfaced clearly rather than failing silently or half-merging", read literally.
Three mechanisms make that true and each one is verified: `git merge-tree --write-tree` returns
exit 1 with the conflicted paths on stdout and mutates no ref, index or working tree, so conflicts
are known before anything is written; a real merge that fails leaves `MERGE_HEAD` behind, which
`git merge --abort` clears and a porcelain re-read confirms; and `--no-ff` always creates a merge
commit, giving every integration a durable sha to record and to diff later.

Purpose: `git_at` converts a non-zero exit into an error and discards stdout, which is exactly
how merge and merge-tree signal a conflict — so every merge call in this plan goes through the
raw-output wrapper plan 08-01 added. And `git_retry`'s spawn floor only spaces spawns 400 ms
apart; it does not exclude, so two merges into one integration worktree need a real lock. Both
are composition mistakes rather than missing algorithms, which is why this plan is tests-first
against real repositories.

Output: six git primitives, `merge.rs`, and one test file carrying the whole REVW-04 register.
</objective>

<decisions_resolved>
- **The per-epic exclusion lock lives in the core, not in `AppState`.** Research proposed a
  `Mutex<HashSet<String>>` on `AppState`; putting it in `merge.rs` behind
  `try_lock_epic(epic_id) -> Option<EpicMergeGuard>` is strictly less code (no edit to the single
  `AppState { … }` literal, no hunt for other constructions of it in tests) and makes the
  behaviour testable with `cargo test -p core`, which is where the validation map already points
  it. The ceiling is stated in the doc comment: the set is process-global, which is correct while
  one process owns the fleet, and would be shared by a second `AppState` in the same process.
- **Three separable halves, as research Code Example 6 sketches.** `plan_merge(&Connection)`
  resolves everything, `run_merge(&MergePlan)` takes no connection and does all the git, and
  `record_merge_event(&mut Connection, …)` writes the event. The command layer therefore never
  holds the database lock across a subprocess, which is this workspace's standing rule.
- **The epic worktree has no table row.** Its path is derived as the worktree root joined with the
  project key prefix and the epic key, its existence is a filesystem check, and a stale entry
  self-heals through prune-then-add. Research assumption A6: if per-epic worktree status or removal
  UI is ever wanted, a table can be added then at no cost to this shape.
- **Merge commit style:** `--no-ff --no-stat` with the message `Merge {task_key} {task_title}
  into {integration_branch}`. The commit hooks are deliberately left to run.
- **No push after a merge** (orchestrator-resolved decision 3). The merge stays local and
  reversible; the only push in this phase is the first step of the confirmed epic-request action
  in plan 08-05.
- **Epic-less tasks get review but no in-app merge** (orchestrator-resolved decision 1, research
  assumption A7). REVW-04 names the epic integration branch as the target, and merging into the
  trunk would touch the user's main checkout, which may be dirty or on another branch. `plan_merge`
  therefore returns a named refusal for a task with no epic, and epic-less tasks keep the
  task-level open-request path Phase 7 shipped.
- **The integrated marker is event plus ancestry, never ancestry alone** (Pitfall 5). A branch
  with zero commits of its own is trivially an ancestor of the branch it was cut from, so an
  ancestry-only test lights the marker on brand-new tasks.
- **`push_branch` lands in this plan even though nothing here calls it.** It is a git write and it
  belongs with the other git writes in one review of `git.rs`; plan 08-05 is its only caller.
</decisions_resolved>

    `pub enum MergePrecheck { Clean, Conflicts(Vec<String>) }` and `pub fn merge_tree_check(repo_path:
    &Path, target: &str, source: &str) -> anyhow::Result<MergePrecheck>`. It calls `git_output_at`
    with `["merge-tree", "--write-tree", "--name-only", "-z", "--no-messages", target, source]`
    and branches on the exit code: 0 is clean, 1 is a conflict, anything else is a real error
    carrying stderr. On the conflict branch, split stdout on NUL, discard the first field (the
    written tree oid), take fields until the first empty one, then sort and dedupe. The doc comment
    records three verified facts: this command writes objects only and mutates no ref, index or
    working tree; without the quiet flag its informational text also lands on stdout after a blank
    line, which is why that flag is present; and it needs git 2.38, which the crate's minimum
    already clears.

    `pub fn merge_no_ff(worktree: &Path, source: &str, message: &str) -> anyhow::Result<bool>`,
    returning whether a commit was created. It calls `git_output_at` with `["merge", "--no-ff",
    "--no-stat", "-m", message, source]`. On any non-success outcome — including a transport error
    from the wrapper itself — it runs the abort helper below and then returns an error stating
    that the merge failed and was rolled back, including the porcelain re-check result. On success
    it returns false when stdout reports the target was already up to date and true otherwise. The

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Rust core → `git` subprocess (write) | branch names and a task title derived from the board reach a merge argv and a commit message |
| Rust core → filesystem | a worktree directory is created, derived from the configured worktree root |
| Rust core → remote | `push_branch` moves a ref on a remote the user configured |
| concurrent callers → one integration worktree | two merges can arrive at the same index |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-03-01 | Tampering | `merge_no_ff`'s commit message | medium | mitigate | The task title is passed as one argv element to the message flag; there is no shell in this path and no interpolation into a command string. Titles are single-line board data. |
| T-08-03-02 | Tampering | `push_branch` argv | high | mitigate | A plain push only: no history-rewriting, ref-deleting or mirror flag appears anywhere in `git.rs`, asserted by a negative grep in Task 1. A rejected non-fast-forward surfaces git's own refusal and is never retried with force. |
| T-08-03-03 | Tampering | hooks bypassed on the merge commit | medium | mitigate | No hook-skipping flag appears in `git.rs`, asserted by a negative grep. The repository's own commit-message hook runs and, by its own branch pattern, stamps no trailer on the epic namespace. |
| T-08-03-04 | Destruction of work | a merge left half-applied | high | mitigate | Three layers: the dry run means conflicts never reach the worktree; any non-success of the real merge aborts and re-reads porcelain; a worktree still dirty after the abort is a loud named error, never a reported success and never a reported no-op. A pre-existing in-progress merge is recovered before a new one starts, and a worktree dirty for any other reason is refused. |
| T-08-03-05 | Destruction of work | a merge into an agent's live worktree | high | mitigate | D-143: the merge runs in a worktree that belongs to the epic, derived from the epic key. | T-08-03-06 | Denial of Service | two merges racing on one index | medium | mitigate | A per-epic try-lock guard; the second caller is told a merge into that epic is already running rather than contending on the index lock. The retry module's spawn floor is explicitly not a substitute. |

| T-08-03-08 | Repudiation | a landed merge with no record | medium | mitigate | One event per outcome, written through the shared sequence allocator in one transaction, carrying the merge commit and both branch names — so the activity trail can answer what landed and when without reading git. |
| T-08-03-09 | Information Disclosure | git stderr crossing a boundary | low | mitigate | Conflicted file paths are returned as values (research permits this); raw git stderr is mapped to a named error category and logged rather than returned. |
