<objective>
**As a** developer supervising many agents, **I want to** have every finished agent session leave a
structured summary on the board that the next session reads back verbatim, **so that** throwing away
a live context costs me nothing.

This is the phase's tracer: the thinnest path that proves the product thesis end-to-end inside the
Rust core — a summary is written to the board, and the very next context packet assembled for that
task carries it. Everything later in the phase (the agent's own write tool, the fallback synthesizer,
compaction, the diff, drift detection, the launch-sheet render) expands out from this proven slice.

Purpose: land D-65's four-field summary row and prove, with a real test, that a written summary
reaches the next briefing unchanged. If this slice does not hold, nothing else in Phase 4 is worth
building.

Output: migration `0008`, the `session_summary` domain module, `ContextPacket.summaries`, a
`## Prior Sessions` section in `render_prompt`, and two test files proving write-then-read-back,
append-only storage and determinism.

<assumption_delta_decision>
**Noun now primary:** the **session summary** row, keyed by `agent_run_id`, ordered within a
**task**.

**Decision: `promote`.** This phase makes sessions plural over one task and one worktree. The
identity model that already exists — `tasks` (durable) → `worktrees` (durable, one per task,
`task_id` UNIQUE, `0003_agent_runtime.sql:49`) → `agent_runs` (many per worktree,
`idx_agent_runs_task_started ON agent_runs (task_id, started_at DESC)`) — **already** anchors on the
durable noun and already treats the run as the plural detail. Nothing needs renaming.

What *is* promoted is the read axis: continuity is queried **per task**, not per run. The new
`session_summaries` table therefore carries `task_id` as a first-class denormalised column with its
own index (`idx_session_summaries_task_created ON session_summaries (task_id, created_at, id)`), and
`list_summaries_for_task` is the primary read — `latest_summary_for_run` exists only for the
fallback's "did this run already produce one" check. `agent_runs.exit_summary_id` is the *detail of
one variant* (one run's own closing summary), not the continuity axis.

This is a promote, not an add-alongside: there is no second per-run continuity store that the packet
also has to read. The packet reads exactly one list, keyed by task.

**Companion invariant (authored as a real task in plan 04-14):** for every session cycle, the task's
acceptance-criteria statements round-trip unchanged.
</assumption_delta_decision>
