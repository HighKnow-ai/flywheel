<objective>
**As a** developer whose agent knows things a diff cannot show, **I want to** have the agent write its
own closing summary onto the board, **so that** the next session inherits the approach it rejected and
the half-finished idea, not just the files that changed.

D-64 introduces the first agent→board *write* seam. CONTEXT.md leaves its home to the planner;
04-RESEARCH.md's assumption A1 resolves it by reading the code: `mcp-permission-server.ts` already
opens a per-run Unix socket and already registers its tool list from a `tools: []` array, so
`report_summary` becomes a **second tool on the same server, relayed as a second message kind over the
same per-run socket** — the precedent D-53 already set for the PATH shim's git-retry notice. Zero new
`--mcp-config` entry, zero new spawned process, zero new socket lifecycle.

Purpose: build the agent-facing write surface, and only that. The Rust-core half — the reader-loop
branch and the transactional row write — is plan 04-06. This plan's tests prove the tool's contract
against the socket, with no database involved.

**Planner call, resolving 04-RESEARCH.md Open Question 1 (the ack shape).** The call resolves on a
**receipt acknowledgement from the supervisor**, not on the database commit. The sidecar-side handler
emits the `summary_reported` event upstream, writes `{"received": true}` back on the same connection
and closes it; the standalone server resolves the tool call with that. Rationale: a commit-level ack
would need a third socket protocol shape, a new sidecar stdio op and a new relay path, and the
failure it would catch is already covered — if the core write never lands, D-64's fallback
synthesizer (plan 04-02) writes an `auto_generated` row when the run closes, so CTX-01 holds either
way. The tool's own `description` states that the acknowledgement means the supervisor received the
summary, so the agent is never told something untrue. The wire payload carries `version: 1`, which is
what makes upgrading to a commit-level ack additive rather than breaking.

**Reversibility note (no checkpoint inserted).** Task 2 carries a `one-way` rating — the tool's
fully-qualified name becomes part of what every future session is prompted to call, and Phase 5/6
extend this seam. No `checkpoint:decision` is inserted: `04-CONTEXT.md` is explicit that the planner
resolves this item against the canonical references and does not re-ask the developer, and the
irreversibility is *removed* rather than gated — the tool sits behind `AdapterCapabilities`, and the
wire payload is versioned, so a later shape change is an additive `version: 2` branch rather than a
migration.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model → MCP tool arguments | Every field of a tool call is chosen by a model; nothing in it may be trusted to identify who is calling. |
| standalone MCP server process → sidecar socket | A separate OS process connects to a filesystem socket; anything that can reach the path can write to it. |
