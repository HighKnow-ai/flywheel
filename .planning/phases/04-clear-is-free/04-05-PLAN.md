<objective>
**As a** developer whose task has run twenty sessions, **I want to** see exactly which summaries are
being carried word-for-word and exactly where folding begins, **so that** I can tell at a glance
whether the briefing is still carrying what matters.

D-68 and D-69 together are the phase's answer to `PITFALLS.md` pitfall 3's sharpest line — *resist the
temptation to save tokens by summarizing summaries*. Compaction is a pure Rust fold with no model
anywhere: past the verbatim window, `changed` prose and `remains` are dropped, and every `decisions`
entry and every file path is kept. The details research says collapse first — rejected alternatives,
specific names — are the ones structurally preserved. The window is a fixed count of 5, not
configurable, because the boundary has to be arithmetic the developer can state out loud.

Purpose: build the fold and prove it against the threshold from both sides. This plan touches no
database at all — `compact_summaries` is a pure function over the packet's own summary values, which
makes it the fastest test in the phase and the easiest one to keep honest. The packet field and the
rendered boundary marker are plan 04-07; the launch-sheet render is plan 04-08.

Output: `packages/core/src/compaction.rs` and a test file with no `Connection` in it.

**The phrase to hold on to:** compaction is **lossless for decisions and total for narrative**.

**Reversibility:** `costly`. D-69 fixes the window at 5; a later change to that number changes what
every existing task's briefing contains, and CTX-07's five-cycle assertions are written against it.
Not `one-way` — no stored data changes shape, because the fold is computed at read time and nothing
about it is persisted.
</objective>

a value or caps a size, because a size ceiling would move the boundary for reasons the developer

Declare `pub const VERBATIM_WINDOW: usize = 5;` with a comment recording D-69: fixed, not

Declare `pub struct CompactedSummary` deriving `Debug, Clone, PartialEq, Serialize`, carrying exactly
what survives the fold: `agent_run_id: String`, `created_at: String`, `auto_generated: bool`,
`changed_files: Vec<String>`, `decisions: Vec<DecisionEntry>`. The narrative fields are **absent from
the type**, not present-and-empty — that is what makes "total for narrative" checkable by reading the
struct rather than by reading a test.

Declare `pub struct CompactionBoundary` deriving the same traits, carrying `total: usize`,
`folded_count: usize`, `verbatim_count: usize`, `folded_range: Option<(usize, usize)>` and
`verbatim_range: Option<(usize, usize)>` — both ranges as **1-based inclusive ordinals** over the
oldest-first list, so the sentence is arithmetic rather than an index calculation at the call site.

and otherwise a sentence naming both ranges, of the shape *Summaries 1-4 are folded; 5-9 are carried
verbatim.* Use an ASCII hyphen, not an en dash — this string is compared byte-for-byte by CTX-04's
determinism assertions and is rendered into a prompt.

Declare `pub struct CompactedHistory` deriving the same traits, carrying `folded: Vec<CompactedSummary>`,
`verbatim: Vec<SummaryEntry>` and `boundary: CompactionBoundary`.

packet's own `SummaryEntry` values so no conversion layer sits between the assembler and the fold. The
input is assumed oldest-first — the order `list_summaries_for_task` already guarantees. Split at
`summaries.len().saturating_sub(VERBATIM_WINDOW)`: everything before that index folds, everything from
it on is carried verbatim by clone. Build the boundary's ordinals from the same split index. There is
no branch on content anywhere in this function — only on position.

Add a `#[cfg(test)] mod tests` block at the bottom for two smoke cases (empty input and the six-summary
threshold), following `git.rs`'s own in-file pure-function test style; the exhaustive cases live in
the integration test file Task 2 creates.
