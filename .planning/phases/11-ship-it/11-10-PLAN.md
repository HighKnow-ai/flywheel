  <behavior>
    - A merge that fails on every attempt appends one event for the first failure and appends nothing on subsequent ticks; the task's state does not oscillate.
    - A task whose live run was started manually by the user is not relaunched by the dispatcher.
    - A task whose run was started by the dispatcher is still retried under the existing rules.

  <action>
For the flap: make a repeated identical merge failure idempotent — record the failure once and leave
the task in its failed state until something changes, rather than re-entering and re-appending every
5 seconds. The cheapest correct shape is a duplicate-write guard comparing against the last recorded
failure for that task and plan. Do not add a timer, a backoff table or a retry-count column.

For the double-start: `is_startable` must distinguish a run the dispatcher owns from one the user
started. Use the run row's actor attribution (Task 2 makes that attribution correct) rather than
inferring from timing.

Two tests in `dispatch_auto_merge.rs`: one driving a merge that fails on three consecutive ticks and
asserting exactly one appended event, one asserting a manually launched task is not relaunched while
its run is live, with a companion asserting a dispatcher-launched task still is.
  </action>
