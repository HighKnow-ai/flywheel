<task type="checkpoint:human-action" gate="blocking-human">
  <name>Task 2: The updater keypair — generate it, store it, and back it up</name>
  <action>Back up the updater signing key off this machine, and confirm the repository slug the endpoint will carry.</action>
  <instructions>
The updater's trust root is an ed25519 keypair. Its public half is compiled into every shipped
binary; its private half signs every release. **If the private key is lost, every already-installed
Flywheel becomes permanently un-updatable** — not broken, but frozen, with no path forward except
asking the user to download a fresh build signed by a new key.

Steps:
1. Generate it: `npm --prefix packages/desktop exec -- tauri signer generate -w ~/.flywheel/updater.key`.
   Choose and record a password for the key.
2. Store the private half and its password as repository secrets:
   `gh secret set TAURI_SIGNING_PRIVATE_KEY --body "$(cat ~/.flywheel/updater.key)"` and
   `gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.
3. **Back up the private key and its password somewhere that is not this machine and not this
   repository** — a password manager entry is enough. This is the step only you can do, and it is
   why this is a checkpoint rather than a command: a key that exists in exactly two places, both of
   them one laptop, is a key you are going to lose.
4. Paste the public key (the `.pub` file's contents) into the answer. Task 3 writes it into
   `tauri.conf.json`.

Confirm also the `owner/repo` slug recorded in 11-02 Task 1, because it is the other half of the
endpoint about to be compiled in.

Never commit `~/.flywheel/updater.key`, never paste the private key into a plan, a SUMMARY or a
commit message, and never echo it in a CI log.
  </instructions>
  <verification>`gh secret list` shows `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; `git ls-files` matches nothing named `updater.key`; the public key pasted in the answer is a valid ed25519 Tauri public key that `tauri signer` accepts.</verification>
  <resume-signal>Reply with the public key verbatim, the confirmed `owner/repo` slug, and "backed up" once an off-machine copy of the private key and its password exists.</resume-signal>
  <acceptance_criteria>
    - `gh secret list` shows `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.
    - The SUMMARY records the public key verbatim and the confirmed `owner/repo` slug, and records that an off-machine backup of the private key exists — without recording the key or its password.
    - `git ls-files` matches nothing named `updater.key` and `git check-ignore` confirms any in-repo key path would be ignored.
  </acceptance_criteria>
  <done>A keypair exists, CI can sign with it, the owner holds an off-machine copy, and the public half is written down.</done>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| github.com release assets → the installed application's code | The updater downloads and stages an executable the application will run as the user. |
| renderer → `update_install` | A renderer-reachable command that replaces the application binary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-13 | Tampering | updater download path | critical | mitigate | ed25519 signature verification against the compiled `pubkey` is the plugin's own gate; exactly one `https://github.com/...` endpoint, no fallback, no plaintext scheme; an unverifiable manifest surfaces as an error, never as "no update". |
| T-11-14 | Elevation of Privilege | `update_install` | high | mitigate | Takes no arguments: endpoint, current version and key all come from compiled config, so the renderer cannot name an update source. The window is granted no `updater:` permission; the command is reachable only through `generate_handler!`. |
| T-11-15 | Denial of Service | update applied under live runs | high | mitigate | The live-run count is read in Rust before any download (D-188); a non-zero count refuses and stages nothing, so an ADE cannot restart itself out from under running sessions. |
| T-11-16 | Information Disclosure | signing secrets in CI | medium | mitigate | Both key variables come from `secrets.*` and are referenced only in the `tauri-action` env; no step echoes them, and the key file is never added to the repository. |
| T-11-SC | Tampering | cargo install of `tauri-plugin-updater` | high | mitigate | Task 1's blocking human checkpoint (crates.io owner, repository, typosquat check, exact version) before `cargo add`, per the `[ASSUMED]` fallback policy that applies when no RESEARCH.md audit table exists. Not auto-approvable. |
</threat_model>
