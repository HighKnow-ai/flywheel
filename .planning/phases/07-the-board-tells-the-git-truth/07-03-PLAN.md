<decisions_resolved>
- **RESEARCH.md open question 3 — two typed error variants, not one stringified error.**
  `ForgeError::CliNotInstalled` and `ForgeError::CliNotAuthenticated` are distinct, because
  D-120's "the forge section is absent entirely" belongs to *no forge configured* and must never
  swallow *forge configured but the CLI is broken*, which needs a visible error. Detection is
  cheap: a spawn failing with `ErrorKind::NotFound` is not-installed; otherwise a non-zero
  `<cli> auth status` is not-authenticated.
- **Normalisation mapping (discretion), stated once here and implemented in two independent
  modules** (Pitfall 1 — the two CLIs' shapes are structurally unrelated and a normaliser written
  against one will silently misclassify the other):
  - `ForgeState`: GitHub `MERGED` → `Merged` **regardless of `closedAt`**; `CLOSED` →
    `ClosedUnmerged`; `OPEN` with `reviewDecision == "CHANGES_REQUESTED"` → `ChangesRequested`;
    `OPEN` otherwise → `Open`; no request → `None`. GitLab `merged` → `Merged`; `closed` →
    `ClosedUnmerged`; `opened` → `Open` (GitLab exposes no single review-decision field, so
    `ChangesRequested` is unreachable on the GitLab arm and that is recorded in the module's doc
    comment rather than faked).
  - `CiResult`: GitHub — empty rollup → `None`; any `conclusion == "FAILURE"` or `"TIMED_OUT"` or
    `"CANCELLED"` → `Failed`; else any `status != "COMPLETED"` → `Pending`; else → `Passed` (so
    an all-`SKIPPED` rollup is `Passed`). GitLab — `head_pipeline` null → `None`; `status` in
    `failed`/`canceled` → `Failed`; `running`/`pending`/`created` → `Pending`;
    `success`/`skipped` → `Passed`; anything else → `None`. Both folds are written as a
    reduction over the collection with no reliance on element order.
- **Defensive parsing, not typed `Deserialize`.** Every field is read as
  `value.get("k").and_then(Value::as_str)` against a `serde_json::Value`, following
  `query/events.rs`'s own precedent — a future `gh`/`glab` version changing a field's type must
  degrade to `None`/`Pending`, never panic and never silently default to a *wrong* definite value.
- **The live arm is a command, not a walkthrough.** `tests/bin/forge_probe.rs` takes a repository
  path and a branch and prints the detected forge plus the normalised `ForgeRequest`, so plan
  07-08's human check is one copy-pasteable invocation per forge rather than a manual procedure.
- **GitLab needs two subprocesses** (`mr list` to find the iid, `mr view` for `head_pipeline`),
  GitHub needs one. The asymmetry is real and recorded in `gitlab.rs`'s doc comment; it is
  affordable because D-116's "network cost is decoupled from the tick rate" puts every forge read
  on its own slow cadence.
</decisions_resolved>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Rust core → `gh` / `glab` subprocess | an external binary resolved from the supervisor's `PATH`, holding its own credentials |
| forge CLI JSON → the normalised model | third-party output of a tool that can change field types between versions |
| `projects.forge` → the dispatch decision | a stored value that selects which binary is spawned |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-03-01 | Tampering | `github::normalize` / `gitlab::normalize` against a future CLI version | medium | mitigate | Every field is read as `Value::get(…).and_then(as_str/as_i64/as_bool)` with a defined fallback — never a typed `Deserialize` struct that panics or silently defaults. A wrong-typed field degrades to `None`/`Pending`, asserted by a test on both arms. |
| T-07-03-02 | Information Disclosure | a forge token reaching this process | high | mitigate | D-117: no token is minted, stored or read by Flywheel. `gh`/`glab` hold their own credentials; nothing crosses argv or env. Asserted structurally by the grep that no HTTP client dependency exists. |
| T-07-03-03 | Spoofing | `gh`/`glab` resolved from the supervisor's `PATH` | medium | accept | These are the developer's own installed CLIs on the developer's own machine, resolved the same way the already-shipped `shim::resolve_real_git` resolves git. Local-first execution is a stated project constraint; a compromised `PATH` on the developer's own machine is outside this boundary. |
| T-07-03-04 | Tampering | the `branch` argument reaching `gh pr list --head` | medium | mitigate | `branch` is never renderer-supplied: it is read from the `worktrees` row that `branch::task_branch_name` wrote.
