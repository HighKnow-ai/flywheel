<decisions_resolved>
- **D-128 applied literally: no index, in the schema or in memory.** Resolution asks git, every
  time, across the registered repositories. This plan adds no table, no column, and no cache —
  asserted by a grep that the module holds no `HashMap`/`OnceCell`/`Lazy` keyed by sha.
- **Ambiguity is answered by git, not by the loop.** For an input shorter than 40 hex characters,
  `git rev-parse --disambiguate=<prefix>` lists every matching full object name in a repository;
  more than one match in any single repository is an ambiguous outcome, reported as such. This is
  cheaper and more correct than inferring ambiguity from `git show`'s error text.
- **Trailer extraction is git's own.** `git show -s --format=%(trailers:key=Flywheel-Task,valueonly)`
  — with the key interpolated from `TRAILER_TASK_KEY`, not retyped — rather than fetching the full
  message and parsing trailers in Rust. The hook writes trailers with
  `git interpret-trailers`; the reader reads them with git's own trailer formatter, so the two
  cannot disagree about what a trailer block is.
- **Validation happens before any git invocation (T-07-05-01).** `classify` is a pure function
  returning `Option<GitIdentifier>`; the Tauri command calls it first and returns no result for
  `None`, so a string such as `--upload-pack=…` never reaches `git_at`. The sha is additionally
  passed with a trailing `--` so git cannot reinterpret it as a pathspec.
- **A branch resolves without touching git at all.** `worktrees.branch` is a stored column, so a
  task branch is a single indexed read; an epic integration branch is matched by re-deriving
  `epic_integration_branch_name` for the project's epics. Only a sha needs git.
- **Repository iteration order is the project registration order** (`projects` ordered by `id`,
  which is a ULID and therefore chronological), and the loop stops at the first repository that
  resolves — so the outcome is deterministic across two reads. A sha that resolves in two
  different registered repositories is reported as a repository-ambiguous outcome rather than
  resolved to whichever came first.
</decisions_resolved>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → `git_identifier_resolve` | a free-text string the user pasted, arriving unvalidated |
| the pasted string → a `git` argument | an untrusted token reaching a subprocess argument vector |
| every registered repository → one answer | the resolver reads across repositories the user registered |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-05-01 | Tampering | the pasted identifier reaching `git_at` | high | mitigate | `classify` is a pure allow-list gate — 7-to-64 ASCII hexadecimal characters, or a literal `flywheel/` prefix — called as the command's first statement, before the database is locked and before any subprocess. A string such as `--upload-pack=…` classifies as `None` and never reaches git. The sha is additionally passed as a positional revision followed by `--`, so git cannot reinterpret it as a pathspec, and `git_at` already places `-C <repo_path>` before any subcommand token (PROC-02 ordering). |
| T-07-05-02 | Information Disclosure | resolving across every registered repository | medium | mitigate | The resolver reads only repositories the user themselves registered as projects, with `status = 'active'`, and returns only the board item's own identifiers — never a path, a commit message body, or a diff. |
| T-07-05-03 | Spoofing | a `Flywheel-Task:` trailer naming a task the commit did not belong to | medium | mitigate | A trailer is self-asserted data in a commit message and can be hand-written by anyone able to commit. The resolver therefore treats it as a lookup key only: the key is resolved against the `tasks` table of the repository's own project, so a trailer naming a key that does not exist in that project resolves to nothing. No authority is granted on the basis of a trailer. |
| T-07-05-04 | Tampering | silently resolving an ambiguous prefix | medium | mitigate | Both ambiguity kinds — two objects sharing a prefix in one repository, and one sha present in two repositories — are distinct reported outcomes that resolve nothing, and the palette renders the count rather than navigating. Guessing would send the user to the wrong board item with full confidence. |
| T-07-05-05 | Denial of Service | one resolve call per keystroke | low | mitigate | `useGitIdentifier` is `enabled` only when the input could plausibly classify, so ordinary text search spends no IPC call — asserted as a mock call-count test. |
| T-07-05-06 | Information Disclosure | a stale cached resolution | low | mitigate | `staleTime: 0` and no index anywhere: every answer is derived from git at read time (D-128), so a resolution can never outlive the history it describes. |

**Canon referral:** argument injection is canon — owned by `/gsd-secure-phase` — and its bespoke
half here is T-07-05-01's pre-git allow-list, asserted by a core test on `classify`.
