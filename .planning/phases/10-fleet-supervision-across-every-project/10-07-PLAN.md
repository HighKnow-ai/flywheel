<objective>
FLEET-05 and ROADMAP criterion 4: **the user receives an operating-system notification when an agent
becomes blocked or completes, without watching the window.** Phase 2's D-37 held OS notifications back
explicitly for this phase; this plan delivers them.

**Locked scope (D-181, owner decision 2026-10-12):** stay on the pinned `tauri = "=2.11.5"` and take
`tauri-plugin-notification` **2.4.0**, not 2.6.0. FLEET-05 and criterion 4 require only that the banner
*fire*; click-through is in no requirement. Every part of RESEARCH that depends on the Tauri minor bump —
Findings 4 and 4b, Open Question 0, Pattern 3's click-routing paragraph and its `on_action` example — is
**superseded**. This plan contains no Tauri version bump, no `on_action`, no `.extra()` payloads and no
`fleet:navigate` click path. Notification click-to-jump is deferred to a board issue.

Purpose: eight projects produce one visible row, so the fleet surface alone does not solve "what needs me?"
when the window is not in front. Research measured four traps: the emit site is two desktop-crate
functions, not the core domain, because `packages/core` has no `AppHandle` (Finding 5); a run already
blocked must not re-notify when a second request arrives (Finding 5, Pitfall 3); the core cannot know which
surface is visible, so the renderer must report it through an in-memory field (Finding 6); and Phase 9's
fan-out of up to 8 makes a simultaneous wave the normal case, so a per-transition banner would stack eight
deep (D-175).

Output: `notify.rs` with a pure coalescer and a pure suppression predicate, the plugin registered on the
core only, the two transition hooks, the `watched_run` report, and one global switch in Settings.
</objective>

**1. `packages/desktop/src-tauri/src/commands/agent_run.rs` — the permission site.** Finding 5 established
that the two notifiable transitions are written here and in the session-closed handler, not in
`packages/core`, because the core has no `AppHandle`.

Read the run's status **before** calling `process_inbound_permission_request` — the connection is dropped
right after it, and the status is needed to detect the edge. In the `PermissionRequestOutcome::Pending`
arm, after the existing register-and-emit sequence, push a transition **only if the prior status was
`running`**. A run already `blocked` receiving a second concurrent request must not re-notify (Finding 5's
first trap, Pitfall 3). Gather the project name and the subject label in the same pre-drop read, so the
banner's text needs no second lock.

**2. The session-closed site.** After the existing `drop(conn)`, in the branch that already treats the
outcome as changed, match `SessionClosedOutcome::Closed(status)` for `Completed` and `Failed` **only**.
`Interrupted` never notifies because it is user-initiated; already-terminal and backfilled-terminal never
notify because nothing transitioned. Note in a comment that both D-174 exclusions fall out for free —
the Stop path writes `interrupted` first so the later outcome is already-terminal, and `mark_abandoned`
runs at launch before a window exists — so no extra guard is needed and none should be added.

Both functions carry a documented must-never-panic contract. `notify::push` is infallible by signature from
Task 1, so these call sites add no `unwrap`, no `expect` and no `?`.

**3. `packages/desktop/src-tauri/src/commands/fleet.rs`.** Add `fleet_watch_run(task_id: Option<String>)`

`state.watched_run` mutex, assign, return. Nothing else. Register it in `main.rs`'s `generate_handler!`
roster and add it to the audited roster in `capabilities/default.json`, stating that it writes one
in-memory field used solely to suppress a notification for the session the user is already looking at.

**4. The suppression read at fire time.** In the notify shell, read the window's focus state from

source of truth, no race with the report (the Don't-Hand-Roll table names this). Read the switch from
`settings` at the same moment, so toggling it takes effect without a restart. Then call `should_suppress`.

open. One effect, keyed on the precedence inputs, reporting the value or clearing it.
