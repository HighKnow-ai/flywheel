This plan is the decidable core of "does not collide": the overlap algebra over the two declared forms, the

PLAN-02, downgrades the *whole wave* to sequential on any collision; D-158 downgrades only the colliding
pair, which is strictly more useful and strictly harder — it needs per-pair edges, a stable orientation,
and a frozen record of what was acted on.

Output: `overlaps`/`collisions` in the single matcher, `dispatch.rs`'s pure wave and edge computation with
the `why` read, and the plan tables' CRUD with the approval transaction.

The deterministic edge probe classified one row for **PLAN-07** as `unclassified`. Per the probe's own
rules an unclassified row is never auto-resolved and never auto-dismissed, so it is carried here as an
explicit assumption rather than silently turned into an acceptance criterion:

> **A-09-03-01 (unresolved).** PLAN-07 says the user can *ask* why two tasks were sequenced. The probe
> could not classify the edge axis for a question-answering requirement. The assumption this plan proceeds
> on is that "can ask" means **both** at approval time (inline on the wave plan) and after the fact (from
> the recorded event and the frozen edge row) — which is what D-157 states. If the owner meant only one of
> those, the `why` read is still correct but one of its two call sites is unnecessary. No behaviour here is
> guessed from the unclassified row.

`pub fn overlaps(a: &FileSetEntry, b: &FileSetEntry, fold_case: bool) -> bool` covers exactly three cases
and nothing else: two `File` variants overlap iff their strings compare equal; a `File` and a `Dir` overlap
iff `covers` says the directory covers the file; two `Dir` variants overlap iff either string is a prefix
of the other, which because both end with a separator is the correct containment test in both directions.
Equality is a collision in every case — two tasks declaring the same path are the clearest collision there
is, not a merge.

`pub fn collisions<'a>(a: &'a [FileSetEntry], b: &'a [FileSetEntry], fold_case: bool) -> Vec<Collision<'a>>`
is a nested loop returning every colliding pair, in the declared order of the first slice then the second,
so the same two sets always yield a byte-identical answer and the `why` text is reproducible. `Collision`
carries references to both entries, which is what lets the caller name the colliding paths rather than only
report that a collision exists. Add a `ponytail:` comment on the nested loop naming the ceiling: it is
quadratic in entries per pair, which is fine for hundreds of tasks on one machine, and the upgrade path is
an interval structure if a repository ever makes that false.

`fold_case` is a parameter, never a global: it is read from the repository's `core.ignorecase` at the point
a set is compared or a marker is written, and carried alongside the entries, because the same declared
strings mean different things on a case-insensitive volume. Two tasks declaring `src/Foo.ts` and
`src/foo.ts` look disjoint as strings and are one file on this project's own development filesystem; a
planning-prompt instruction to use the repository's existing casing is not a control.

**1. `packages/core/src/dispatch.rs` (new), declared in `packages/core/src/lib.rs`.** Pure and
database-reading only: no git, no subprocess, no sleep. `now` is always a parameter so tests need no clock.

- `pub const DISPATCH_TASK_STATES` and `pub const DISPATCH_PLAN_STATES` — the single Rust declarations the
  migration's CHECK lists mirror, in the `WORKFLOW_STATES` discipline. Task states: planned, waiting,
  running, finished, merging, merged, conflict, needs_attention, failed, stopped, held_by_limit, skipped.
  Plan states: draft, approved, running, paused, completed, aborted.
- `normalise_waves(tasks: &mut [PlannedTask])` — collapse user-supplied wave integers to a contiguous
  sequence starting at one, preserving relative order, so "move this task to wave 5" in the review sheet
  cannot leave a hole the cursor would stall on.
- `edges_for_plan(tasks: &[PlannedTask], fold_case: bool) -> Vec<DispatchEdge>` — for each wave, enumerate
  every unordered pair and call `file_set::collisions`; for each pair with a non-empty result emit one edge
  oriented by board rank with task id ascending as the tie-break, carrying the colliding pairs. Because
  rank-then-id is a total order, cycles are impossible by construction rather than by a check. A pair in
  different waves is never enumerated. This is the one difference from the GSD-core model this phase is
  built on: that model downgrades the whole wave, this one touches only the pair.
- `why(conn, plan_id, task_a, task_b) -> SequencingReason` — read `dispatch_edges` **first**, because that
  row is what was acted on; return its colliding paths and its cause. With no edge, answer "different
  waves" or "file-sets disjoint" from the plan rows. Never recompute over current entries when a frozen
  row exists: after a live widen the recomputed answer and the acted-on answer are different answers, and
  the user asked about the one that happened.
- `occupied_slots(conn) -> u32` — `COUNT(*)` of agent runs whose status is running or blocked, across every
  project, as a parameterised query. Database truth, not an in-memory counter, so it is correct after a
  restart and counts authoring and planning runs on the same account. Plan 09-04 consumes it.
- `in_flight_declared_sets(conn, project_id) -> Vec<(String, Vec<FileSetEntry>)>` — the declared entries of
  every task with a currently running armed run. Plans 09-06 and 09-07 both consume this: the widen
  re-check and the cross-plan readiness guard are the same question asked twice.
