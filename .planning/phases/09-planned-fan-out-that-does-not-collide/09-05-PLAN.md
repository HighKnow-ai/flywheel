Fan-out makes the account's limits the binding constraint. This plan consumes the limit signal the adapter
already parses and turns it into a gate: new dispatch stops, the reason is readable, running work is
untouched, and dispatch resumes at the reset time the wire actually reported — never at a time this
application guessed, and never after a probe.

Purpose: AGNT-05 and ROADMAP success criterion 5. The detection half already ships — the wire's limit line
is parsed and emitted as a normalised event. What is missing is a consumer. Criterion 5 also exists partly
for compliance optics: visible backoff is what keeps this application from looking like abuse to the
backend, which is precisely why a probe is forbidden.

Output: `limit_gate.rs`, the normalised hard-limit signal at the adapter seam, the inbound consumer, and
the warning tier that holds the wave cursor.

## Recorded decision (left to the planner by CONTEXT.md, not re-asked)

**When `resetsAt` is absent or malformed:** the gate pauses with no resume time, the reason reads that the
reset time is unknown, and only a manual resume clears it. D-162 forbids a probe, and guessing a wait is a
quieter version of the same mistake. This matches the fail-closed discipline every other gate in this
codebase follows: a precondition that cannot be established is never concluded to be permissive.

## Honest statement of what is unobserved

The hard-limit wire shape is **built from the documented shape and has never been observed live** in this
project. The observed sample is an *allowed* event, and it carries an overage status reading `rejected`
while its top-level status reads `allowed` — which is exactly the trap a substring match would fall into.
Every assertion in this plan about the hard tier runs against a constructed fixture. That residual is
already queued in `.planning/DEFERRED-REVIEW.md`; this plan must not describe it as verified, and the
plan SUMMARY must repeat it.

**1. The seam, in `packages/sidecar/src/claude-code-adapter.ts` and `packages/sidecar/src/adapter.ts`.**
Keep emitting the existing rate-limit event unchanged, and add one normalised interpretation field — a
tier of `open`, `warning` or `rejected` — computed by a new exported `rateLimitTier` helper. The tier is
derived from the **top-level** status field and from nothing else on that object. Do not key on the overage
status: the one real sample this project holds carries an overage status of rejected while its top-level
status is allowed, so a substring match on that word would pause dispatch on every single response for any
account that merely has overage disabled. Also map an assistant message whose error code names a rate limit
onto the rejected tier, because the documented error enum carries that value and a hard limit may arrive
there instead. Add the tier to the event's exported type.

**2. `packages/core/src/limit_gate.rs` (new), declared in `packages/core/src/lib.rs`.** The gate is three
states: open; warning, carrying the limit window and its reset time; and paused, carrying a reason string
and an optional resume instant. Persist it as a single global `settings` row through the existing
`upsert_setting` / `read_setting` helpers — a global value, so no `events` row, exactly as the credential
mode and the parallel cap already do.

- `normalise_resets_at(raw) -> Option<i64>`: a number above 1e11 is milliseconds and is divided by a
  thousand; a number at or below that is already seconds; anything that is not a positive number is
  `None`. The one live sample is seconds and the community documentation describes milliseconds, so the
  magnitude test is the guard rather than a choice between the two.
- `apply_rate_limit_signal(conn, &LimitSignal, now_epoch_secs) -> anyhow::Result<GateChange>`: computes the
  next state and **writes only when the state actually changes**. The backend emits a limit line per API
  response, so a write per event is a write storm against the store of record.
- Rejected tier with a usable reset time in the future: paused until that instant, reason naming the limit
  window. Rejected with no usable reset time: paused with no resume instant and a reason saying the reset
  time is unknown — only a manual resume clears it. No probe is ever sent, because a probe is a retry and
  AGNT-05 rules retries out.
- Rejected with a reset time already in the past: pause with a resume instant equal to now, so the next
  tick resumes once. Guard the loop with `DISPATCH_REJECT_FLOOR_SECS`: a second rejection arriving within
  that floor of a time-driven resume pauses for **manual** resume and says so. Without that floor, resume
  → spawn → immediate rejection → resume is a blind retry wearing a timestamp.
- The gate pauses **new dispatch only**. This module writes no agent-run status, sends no interrupt and
  touches no process. A session mid-task holds uncommitted work and spent tokens; killing it loses both,
  and stopping in-flight work is not what the limit is asking for.
