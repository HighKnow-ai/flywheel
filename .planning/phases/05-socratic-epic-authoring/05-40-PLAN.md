<measured_diagnosis>
Measured during planning, against the source and against the live run's own preserved artefacts.
The executor states this finding in Task 1 before changing any production code; it is reproduced
here so Task 1 is a confirmation with a named target rather than an open-ended search.

**The WRITE side is wrong. The read side is correct and must not be touched.**

1. `packages/core/src/domain/authoring_session.rs::start_authoring_run` inserts the `agent_runs`
   row with `authoring_stage = 'challenge'` and **never calls
   `runtime_protocol::write_authoring_stage`**. The only production caller of
   `write_authoring_stage` in the entire workspace is `transition_stage`, the shared body behind
   `advance_stage` and `return_to_stage`. So `<runtimeDir>/stage/<runId>.json` does not exist from
   session start until the first stage transition.
2. `packages/sidecar/src/stage-gate-hook.ts` reads that exact file fresh per matched call and, when
   the read throws, calls its own `failClosed` with the reason `no authoring stage marker could be
   read for this run`. That is the string the live run saw. **The gap report named
   `packages/sidecar/src/mcp-permission-server.ts` as the artifact; that is wrong — the refusal is
   emitted by `stage-gate-hook.ts`, a `PreToolUse` hook, not by the MCP tool handler.**
3. Nothing is misconfigured. The hook got past its own `FLYWHEEL_RUN_ID`/`FLYWHEEL_RUNTIME_DIR`
   guards (it reported the marker read, not an unset variable), and the live transcript's turn 6
   records the agent observing *"Gate's open now"* immediately after the driver advanced the stage —
   the single moment `transition_stage` first wrote the marker. Both directions confirm the write
   path and the read path resolve the same directory: `runtime_dir()` on the Rust side and the
   `FLYWHEEL_RUNTIME_DIR` that `uat_session_env` derives from that same function on the harness
   side.
4. **Why nine rounds of green tests did not catch it.**
   `packages/core/tests/authoring_stage.rs::a_fresh_run_starts_at_challenge` asserts
   `current_stage(...)` — the **database row**. `packages/sidecar/test/authoring-stage-gate.test.mjs`
   asserts the hook's decision against a marker file its own `scratchRuntimeDirWithStage` helper
   **hand-writes**. One side tested the row, the other side tested the file, each one fabricating
   the other side's state, and nothing anywhere asserted that the product makes them agree. This is
   the same shape `scripts/uat/README.md` Item 8 already records: an offline arm only proves a
   property if it exercises the same code path, with the same inputs, the live arm will hit.
5. **What the wrong message cost.** During the challenge stage a propose call *should* be denied —
   that is D-88 working. But it must be denied by `denyForChallengeStage`, whose reason tells the
   agent to keep challenging and that only the developer can advance. Instead it was denied by
   `failClosed`, whose reason reads as an infrastructure defect. The transcript shows the model
   drawing exactly that conclusion — *"it needs a session started in the authoring stage"*,
   *"re-running the same calls won't help"* — and dumping a six-task epic with acceptance criteria
   into prose. The gate's correctness was accidental; its message was the damage.
</measured_diagnosis>
