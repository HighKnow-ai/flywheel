<objective>
Make `propose_criterion` reachable in a fresh-epic session, so the drafted acceptance criteria
SHAPE-03 is about can exist at all.

Today they cannot. Three measurements close the loop, and they are the first thing this plan writes
down, before any production code moves:

1. `stageAuthoringProposal` (`packages/sidecar/src/mcp-permission-server.ts:960`) resolves EVERY
   `propose_*` tool call with exactly `{"staged": true}`. No id is ever returned, for any verb.
2. `proposeCriterionToolDefinition` (`:577-599`) declares `required: ["statement",
   "parent_proposal_id"]` with `parent_proposal_id` at `minLength: 1`.
3. The agent's only read tools are `board_search`, `epic_get`, `task_list`
   (`AUTHORING_READ_TOOL_NAMES`, `:145`); `authoring_proposals` is read by no agent-visible tool.

So a proposal can never become the parent of another proposal inside its own session.
`Drafted criteria: 0` is not one live run's bad luck — it is the only value the current design can
produce. Live run `01M3ENQMC3E4M2HP7014MA84PX` is the first run in this phase ever to get far
enough to expose it, and the agent diagnosed it correctly and unprompted in turn 8 of
`05-LIVE-CHALLENGE-TRANSCRIPT.md`.

This plan also carries a correction to the gap's own framing, measured during planning — the third
consecutive round in which that has been necessary. The gap asks whether D-07's rule ("a drafted
criterion has no canonical parent until its own parent proposal is accepted") and SHAPE-03's wording
can both stand. They can. `accept_proposal_in_tx` (`authoring_proposal.rs:679`) already accepts a
still-pending `parent_proposal_id` FIRST, in the same transaction, before the criterion materialises
— D-96's implied-parent rule, bounded to depth one by construction. A criterion drafted against an
unaccepted parent therefore never reaches `acceptance_criteria` with a dangling parent. The
invariant was never the blocker; the missing id was.

Purpose: SHAPE-03 ("the agent drafts acceptance criteria for each generated task") is currently
unsatisfiable live, by construction, which makes this the project's Core Value failing structurally
rather than intermittently.
Output: the fork put to the developer, then one thin end-to-end slice that proves a fresh-epic
session can stage an epic, read its id back, hang a criterion off it, and land a real
`acceptance_criteria` row — offline, in one command.
</objective>

Every claim below was read out of the shipped source during planning, not inferred from the gap
report. The gap report's own `correction` field already retracted one wrong root cause; this block
exists so a third one does not get implemented.

- `stageAuthoringProposal` (`mcp-permission-server.ts:938-963`) opens a socket, writes the payload,
  waits for one line, checks `parsed.received === true`, and resolves
  `{ content: [{ type: "text", text: JSON.stringify({ staged: true }) }] }`. That literal is the
  agent's entire answer for all six write verbs.
- The `{ received: true }` ack is written by `startPermissionServer`'s connection handler
  (`:398-402`), which calls `onProposal(parsed)` and `socket.end(...)` IMMEDIATELY. The proposal is
  NOT held in `pending`. The row does not exist yet at ack time.
- The row's id is minted Rust-side, in `create_proposal_in_tx` (`authoring_proposal.rs:250`,
  `let id = new_id();`), reached from `apply_proposal_created` — strictly after the ack.
- `resolve_board_read` (`query/authoring.rs:508`) takes `run_id` as its own parameter and resolves
  `project_id` from the `agent_runs` row INSIDE its body, then dispatches on `event`'s `readKind` to
  `search` / `get_epic` / `list_tasks`, with `other => anyhow::bail!(...)`. A fourth arm is a
  single, bounded change in exactly one place.
- `pending_proposals_for_run` (`authoring_proposal.rs:1041`) already exists, already takes
  `agent_run_id`, and already applies the `DEFAULT_LIMIT`/`MAX_LIMIT` clamp Pitfall 4 requires.
- `accept_subtree` (`authoring_proposal.rs:975`) accepts a root then every proposal whose
  `parent_proposal_id` is that root (`:1007`), each through `accept_proposal_in_tx`, which
  re-fetches the parent (already accepted -> returns the existing `materialised_id`) and passes it
  to `materialise_proposal` as `parent_outcome`. The criterion path is already written for exactly
  this.
- `--board-read-check` (`uat-08-socratic-authoring.mjs:4706`) already registers a project, starts a
  run, applies a synthetic `proposal_created` event, lists pending, accepts a proposal, and drives
  the REAL `drainInboundCoreRequests` against the REAL bridge binary. It is the one offline arm in
  this repository that crosses the Node/Rust boundary the live arm crosses.

What was NOT the cause, recorded so it is not chased: the single-shot proposal drain at
`uat-08-socratic-authoring.mjs:6429`. The gap's own `superseded_root_cause` retracts it. The
comment/code divergence there is real and is handled by plan 05-46, not here.

  <context>
    Read `<measured_diagnosis>` above first. It corrects the framing this gap was filed with.

    **The gap asked whether D-07 and SHAPE-03 can both stand. Measurement says yes.**
    `proposeCriterionToolDefinition`'s doc comment states the rule — "a drafted criterion has no
    canonical parent until its own parent proposal is accepted, so this is the schema-layer
    rejection point for a criterion with nowhere to hang." That rule is about the CANONICAL parent,
    and it is already honoured by `accept_proposal_in_tx`'s D-96 implied-parent walk: accepting a
    criterion accepts its still-pending parent proposal first, in the same transaction, and
    `materialise_proposal` only ever writes the criterion against a parent that has just
    materialised. So a criterion pointing at an unaccepted PROPOSAL is exactly what the accept path
    was built for. Nothing about D-07 needs weakening and SHAPE-03's wording does not need to
    change. The only thing missing is that the agent is never told the proposal id.

    That leaves the real fork: by what mechanism does the id reach the agent?

    **Option A (RECOMMENDED) — a fourth capped read tool, `proposal_list`.**
    The agent reads its own session's pending proposals back through the `board_read` channel D-87's
    three read tools already use. One new tool name, one new `readKind`, one new match arm in
    `resolve_board_read`.
    - Costs one extra agent round trip per batch of proposals.
    - Adds no held inbound kind, so `HELD_INBOUND_REQUEST_TYPES` is unchanged and no harness can
      starve on it — the desktop app's `handle_inbound_board_read_request` and the UAT harness's
      `answer-board-read` BOTH already route every `board_read_request` through the same
      `resolve_board_read` dispatch, so the new kind is answered by both for free.
    - Leaves the propose ack, the id-minting authority, D-07, D-88 and SHAPE-03's wording all
      untouched.
    - Reversibility: reversible. Additive tool, additive read kind.

    **Option B — hold the propose socket and return the core-minted id.**
    `authoring_proposal` becomes a HELD inbound kind like `board_read`: the sidecar keeps the socket
    open until the core answers with the id `create_proposal_in_tx` minted.
    - Exact, and no extra round trip.
    - Requires a new answer op, a `SidecarHandle` relay, a desktop inbound change, a third entry in
      `HELD_INBOUND_REQUEST_TYPES` and a new harness handler. Any harness that does not answer it
      STARVES rather than fails fast — the precise failure this live arm hit twice already
      (`scripts/uat/README.md` Item 8, findings 1 and 2).
    - Also re-opens D-46's question: staging a proposal would now block on the supervisor. (`board_read`
      already does, so this is a precedent question, not a prohibition.)
    - Reversibility: costly.

    **Option C — mint the id in the MCP server process and echo it immediately.**
    The sidecar generates a ULID, carries it on the `authoring_proposal` payload, and
    `create_proposal_in_tx` uses it instead of `new_id()`.
    - No extra round trip, no held kind.
    - Makes the `authoring_proposals` primary key a value supplied across a process boundary by the
      process the model talks to. `mcp-permission-server.ts` states three times, in its own header
      comments, that identity is derived from the socket the call arrives on and never accepted as a
      caller-supplied argument (T-05-02-01). The discipline's wording does not split "attribution"
      from "primary key". Needs core-side well-formedness and collision handling that does not exist.
    - Reversibility: one-way.

    **Option D — accept the deadlock and reword SHAPE-03.**
    Criteria are drafted only in a later session, after the parent is accepted — the two-session
    shape `authoring_acceptance.rs::criterion_4_*` already exercises.
    - Cheapest in code: nothing ships.
    - But D-88's stage machine is `challenge -> decompose -> criteria` and a fresh-epic session
      reaches the `criteria` stage; under D that stage has nothing to do in the very case SHAPE-01
      is about. And `stage-gate-hook.ts:111` already allows `propose_criterion` in both `decompose`
      and `criteria`, so the product's own gate expects it to be callable there.
    - Reversibility: one-way — it rewrites a shipped requirement.

    A fifth shape not listed here is legitimate if you see one; name it and the executor implements
