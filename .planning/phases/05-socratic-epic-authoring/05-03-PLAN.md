<objective>
**As a** solo developer running a fleet of agents, **I want to** be challenged before anything is
planned, **so that** the epic I end up with is one I have actually thought about.

D-88's whole point is that "ask before you plan" is enforced by **structure**, not by instruction:
during the challenge stage the agent has no way to write a proposal. `05-RESEARCH.md` established
that the literal mechanism — a tool set that changes mid-session — does not work against the
installed CLI (`anthropics/claude-code#77314`), and that the one proven mechanism in this codebase
that can deterministically deny a tool call based on live mutable state is the `PreToolUse` hook
Phase 3 already ships for the destructive-command gate.

So this plan implements the *tested behaviour* of D-88 — "assert that no proposal row exists before
the stage advanced", which is `05-CONTEXT.md`'s own named test — through a hook-mediated refusal
rather than literal tool absence. That substitution is deliberate, evidence-driven and recorded
here; it is not a silent downgrade, and `05-RESEARCH.md` Pattern 1's caveat says so in as many
words.

Purpose: make the differentiator structural. A prompt asking the agent to challenge first is a
paragraph anyone copies in an afternoon; a gate that can be asserted is not.
Output: the per-run stage marker, the stage-gate hook and its second `PreToolUse` matcher entry, the
human-only advance/return commands, the stage indicator, and a visible failure when the gate cannot
be installed.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model → `PreToolUse` hook payload | The hook payload is assembled around model-authored tool arguments |
| hook process → runtime stage file | A per-tool-call subprocess reads authoritative application state off disk |
| renderer → advance/return commands | The one gate the whole mechanism depends on is exposed as an IPC command |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-03-01 | Tampering (bypassed control) | `writeHookSettings` failure | high | mitigate | The authoring path no longer fails open silently: `startAuthoringSession` emits a `system_notice` and Task 3 renders it as a banner; the task-run path's existing posture is left unchanged so the destructive gate's reasoning is not disturbed |
| T-05-03-02 | Spoofing | the hook's run-id source | high | mitigate | The hook resolves the run id from its own `FLYWHEEL_RUN_ID` environment only; a grep gate asserts it never reads a run id from the hook payload, so one session cannot read another's stage marker |
| T-05-03-03 | Tampering | arbitrary run id → file path | high | mitigate | `write_authoring_stage`/`read_authoring_stage` route through the shared `is_ulid` predicate at the one join site, the same fix `03-15` applied to `session_log_path`; a non-ULID id is rejected before any path is built |
| T-05-03-04 | Elevation of Privilege | agent-initiated stage advance | high | mitigate | `advance_stage` takes a human actor id, and a source-scanning test asserts no file under `packages/sidecar/src` names it — the gate is a property of the code, not a prompt |
| T-05-03-05 | Tampering | stage row and marker disagreeing | medium | mitigate | The marker write happens inside the transaction's success path and a marker failure rolls the row back; a committed stage the hook cannot see would be a silently-open gate |
| T-05-03-06 | Denial of Service | fail-closed denial loop | medium | accept | A permanently-unreadable marker denies every proposal call for that run, which is loud and recoverable (the developer sees the banner and the refusals) — the alternative, failing open, is the bypass this gate exists to prevent |
</threat_model>
