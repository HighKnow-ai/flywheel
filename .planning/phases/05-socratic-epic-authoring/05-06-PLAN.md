<objective>
**As a** solo developer running a fleet of agents, **I want to** accept, reject or amend each thing
the session proposes on its own, **so that** what lands on my board is what I agreed to rather than
what I could not be bothered to read.

SHAPE-04 forbids wholesale acceptance being the only option; SHAPE-03 requires a drafted criterion be
editable *before* accepting. D-92 makes the granularity per-row down to the individual criterion,
D-94 makes amendment mean editing the staged row and accepting the developer's own version, and D-95
allows exactly one bulk path — a proposed task together with its drafted criteria — and no tray-wide
accept-all.

That last refusal is the one worth restating, because it will look like a missing feature to whoever
reads this next. `05-CONTEXT.md`'s own reasoning: once accept-all is the reflex, SHAPE-03's
criterion-editing requirement is decorative — **the phase would pass its tests while the behaviour it
exists to create stops happening.** A tray-wide accept is a Deferred Idea, purely additive later, and
deliberately not shipped first so the per-subtree habit forms.

Purpose: make the write-gate real at the granularity the requirements ask for.
Output: the full accept/reject/amend path across every verb and target type, the implied-parent rule,
the subtree bulk accept, and the structural gate that no accept-all exists.
</objective>

form of that rule.

**The locked-criterion branch does not get a new mechanism.** An accepted `amend` against a criterion
already locked by D-76 calls `domain::acceptance_criterion::revise_criterion` directly, which already
detects the lock through `criteria_locked_for_task` and already appends a successor with
`revision_of` pointing at the chain root. D-81's words are that this "materialises as a D-77 revision
row, never an `UPDATE`" — the immutability Phase 4 shipped is not something this phase routes around.
If `revise_criterion` needs a visibility widening to be callable from here, widen it; do not copy it.

**Implied-parent accept (D-96).** Accepting a child whose parent proposal is still `pending` accepts
the parent first, in the same transaction, so the materialised tree can never reference a row that
does not exist. Implement it as a walk up `parent_proposal_id` collecting undecided ancestors, then
materialising root-first. Accepting an ancestor that is already `accepted` must be a no-op that
reuses its `materialised_id` — that is the whole reason a second accept returns the existing id
rather than writing a second row.

**Key allocation timing, recorded rather than left implicit.** D-96 materialises on accept, so
per-project keys are allocated in acceptance order, not proposal order. That is correct and is the
only option that does not burn keys on rejection (the reason D-80 chose staging at all), but it has
one visible consequence: a staged proposal has no key, so nothing may render one for it. Assert in
this module's doc comment and in the test that `Proposal` carries no key field at all, so the
surfaces physically cannot display one.

`target_id` no longer exists — because D-44's task deletion cascade ran underneath it — returns a
typed `ProposalUndecidable` error naming the missing row and its type. It is never auto-rejected and
never silently dropped: D-16's rule, applied three times in this project already, is to surface a
mismatch rather than repair it, and a proposal the developer never decided is exactly the invisible
state D-45 and D-74 were written against. Plan 05-07 renders it; this task defines it.

Every mutation appends its event in the same transaction as the row write, with a human-renderable
payload (D-19) — the activity trail gets the whole proposal and decision history free if the payloads
are written for it. The **human** actor is the decider on every accept; `created_by` stays the agent.

**Rejection is a turn in the conversation (D-93), not a verdict.** After the write commits, the
command sends one `authoring_turn` naming the proposal, the fact it was rejected and the reason if
one was given. The wording is an invitation to propose something better — `05-CONTEXT.md`'s reasoning
is that silence buys nothing, because the developer ends up typing the objection into the
conversation anyway. The looping risk is covered elsewhere and deliberately: D-83's persisted rejected
set is primed into every later session for the epic, and a structural bar on re-proposing is a
Deferred Idea because near-duplicate matching is the hard problem and a false match silently
swallows a genuinely better second attempt.

**Amend means edit-then-accept (D-94), and the board never sees a version the developer did not
accept.** `amend_proposal` rewrites the staged row's `payload` and leaves it `pending` — it does not
accept. The developer accepts separately, and what materialises is their text. Do **not** route this
through `ItemDetailPanel`'s existing editors: D-94 rejects accept-then-edit explicitly, because the
board would hold a wrong statement in between, the agent would learn nothing, and against an
already-locked task the first edit would become a D-77 revision of something that arrived wrong.

The amend's event payload carries both the agent's original and the developer's replacement, so the
activity trail shows what changed rather than only the end state. Then the same
`authoring_turn` relay tells the session what the developer wrote, so the next batch of drafts moves
toward it instead of repeating the same miss.

**Terminal rows stay (D-83).** Neither function deletes anything; both are status transitions plus a
timestamp and an actor, matching `session_summary.rs`'s append-only discipline — a recorded row is
never rewritten. A second decision on an already-decided row is an error carrying the existing status,
never an overwrite: the first decision is the record.

**Rejecting a parent does not reject its children.** A drafted criterion under a rejected task stays
`pending` and decidable on its own — D-92's granularity is per-row and a cascade would be a wholesale
decision wearing a different name. The developer can reject each child too; that is three keystrokes
and it is the point.

Validate the amended payload with the same rules the tool schemas apply (non-empty title, non-empty
statement, length bounds matching the canonical commands), so an amendment cannot introduce text the
agent's own tool would have been refused for.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → decision commands | The accept/reject/amend commands are the only path that writes canonical board rows from an authoring session |
| staged payload → canonical writer | Model-authored text, possibly amended by the developer, becomes a board row |
| staged `target_id` → canonical row | A proposal names an existing row that may have changed or vanished since it was staged |
