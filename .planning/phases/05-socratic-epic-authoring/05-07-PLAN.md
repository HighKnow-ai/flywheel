<objective>
**As a** solo developer running a fleet of agents, **I want to** read and decide each thing the
session proposes while the conversation is still going, **so that** shaping an epic feels like
shaping it rather than reviewing a document afterwards.

`FEATURES.md` is blunt that this flow dies if it does not *feel* better than typing a prompt into a
terminal, and D-85 argued the whole surface against that sentence: same route, same chrome, one new
panel. The tray is that panel. It is where SHAPE-03's "which the user can edit before accepting" and
SHAPE-04's "rather than accepting the set wholesale" stop being backend properties and become
something a person does.

Purpose: make per-row deciding fast enough that the per-subtree habit forms on its own.
Output: the tray's query layer, its row anatomy, its amend editor, and its keyboard region.
</objective>

**(a) Accept and reject at the row.** Two controls per row, calling the Task-1 mutation hooks. Reject
opens a small optional-reason input — optional in the literal sense: submitting empty rejects with no
reason, and the control must not block on it. A reason typed there reaches the running session as a
turn (plan 05-06 wired that), so the input's placeholder should say what it is for — "tell the agent
why, and it can try again" — rather than reading like a required audit field.

**(b) `packages/desktop/src/authoring/ProposalAmendEditor.tsx`** (new). Amend opens the staged row's
payload for editing, field by field — a task's title and description, a criterion's statement and
verification hint, an assumption's assumption and answer — and saving writes the staged row and
leaves it pending. Accepting is a separate, subsequent action, and what materialises is the
developer's text.

Do **not** route this through `ItemDetailPanel`/`AcceptanceCriteriaList`. D-94 rejects accept-then-edit
explicitly: the board would hold a wrong statement in between, the agent would learn nothing from the
correction, and against an already-locked task the first edit would become a D-77 revision of
something that arrived wrong. The editor here writes to staging, which is the only place a correction
can happen before the board sees anything.

Validate with the same rules the backend applies (non-empty title, non-empty statement, the length
bounds the canonical commands use), so the developer is told at the keystroke rather than at the
round trip.

**(c) Accept subtree.** On a task proposal that has pending criteria under it, one action accepts the
task and its drafted criteria together, calling `authoring_subtree_accept`. Label it for what it is —
"Accept task and its N criteria" — so it never reads as a general accept-all. It appears only on a
task root with at least one pending child; a criterion row does not get it, and neither does the
tray header. There is deliberately no action anywhere on this surface that decides every pending
proposal at once, and that absence is asserted in Task 3's test rather than left to review.

**(d) Guard every action.** Each of the four uses a synchronous `useRef` checked before any `await`,
following the `ackActingRef`/`answeringRef`/`removingRef`/`stoppingRef` pattern this codebase has now
applied six times — two synchronous clicks in the same tick both observe the same stale React state
before the first re-render flushes `disabled`. For the subtree action, the guard is a `Set` keyed by
root id rather than a single boolean, mirroring `OrphanRecoveryModal`'s `killingRef`: two different
subtrees must both be able to act, and only a repeat of the same one is suppressed.

Release the guard only on the paths where the row survives. An accepted or rejected row leaves the
pending list and can never re-activate; a failed action must stay retryable, matching
`stoppingRef`'s recorded reasoning that the alternative is a control the developer cannot use again.

Extend `proposal-tray.test.tsx`: three synchronous clicks on each of the four actions issue exactly
one backend call each; two different subtree roots clicked in the same tick issue two calls; rejecting
with an empty reason still calls the backend; rejecting with a reason passes it through; the amend
editor saves and the row stays pending with the new text; accepting after an amend sends the amended
payload; the subtree action is absent on a criterion row and on a task with no pending children; and
its label names the child count.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model-authored text → the developer's screen | Proposal payloads are model-authored strings rendered into the UI |
| renderer → decision commands | Keyboard and click paths reach the only commands that write canonical board rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-07-01 | Tampering | model-authored payload rendered as UI | medium | mitigate | Every payload field renders as React text content, never as HTML and never through `dangerouslySetInnerHTML`; the window loads only bundled first-party code, and `01-SECURITY.md` AR-01-12 already flags that this assumption must be revisited when agent-authored content is rendered — this is that moment, and text-only rendering is the answer |
| T-05-07-02 | Elevation of Privilege | a keyboard action reaching an inapplicable backend path | medium | mitigate | `Shift+A` is gated inert on a criterion row and a childless task in the row's own handler, matching the destructive-card precedent, rather than letting the call reach a backend that rejects it |
| T-05-07-03 | Tampering | double-dispatch on a decision | medium | mitigate | Synchronous `useRef` guards on all four actions, a keyed `Set` for the subtree action, released only on the paths where the row survives |
| T-05-07-04 | Repudiation | a decision made without reading the criterion | low | accept | The surface cannot enforce reading. D-95's subtree scope is the structural mitigation — it keeps the decision unit the size of a coherent piece of work — and the absence of a tray-wide accept is asserted by a test rather than trusted to habit |
| T-05-07-05 | Information Disclosure | a proposal payload from another run appearing in the tray | medium | mitigate | `useRunProposals` is keyed by `agentRunId` and the backend read is scoped to that run; the query key includes the run id so a stale cache from another run can never be rendered under it |
</threat_model>
