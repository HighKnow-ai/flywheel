<objective>
Make the instrument able to observe what plans 05-44 and 05-45 made possible.

Three things stand between a working product path and a live run that can report it, and all three
are in this file:

1. **The drain is single-shot.** `uat-08-socratic-authoring.mjs:6429` awaits the FIRST
   `proposal_created`, makes ONE pass over `sidecar.eventsOfType("proposal_created")`, and
   immediately snapshots `list-pending`. The comment directly above that loop says it applies every
   event seen so far "and any that arrive over the next window". There is no next window:
   `eventsOfType("proposal_created")` has exactly one call site and `PROPOSAL_DEADLINE_MS` has
   exactly one use. This was filed as this gap's root cause, RETRACTED as wrong, and kept as a
   latent defect — the gap's own `superseded_root_cause` says so. It stops being latent here:
   proposals now arrive across two stage windows, so a single pass structurally cannot collect them.
2. **The live arm never reaches D-88's third stage.** It advances exactly once
   (`challenge -> decompose`) and a self-test asserts that count. The stage literally named
   `criteria` — the one plan 05-45 gave an instruction to — is never entered, so the criteria that
   instruction asks for are never asked for in a live run.
3. **`Drafted criteria: 0` reads as the model's choice.** It was, in fact, structurally impossible.
   The gap asked for a signal that distinguishes the two, by name.

Purpose: Item 8's standing rule is that every property a live script asserts must be provable
without a live run, and that an offline arm only proves a property if it exercises the same code
path, in the same order, with the same inputs the live arm hits. Two of the three items above are
that rule failing in the instrument itself.
Output: a drain that implements its own comment, a live arm that walks the whole stage machine, a
self-naming reachability reading, and an offline scenario that drives the new shape.

This plan adds no vertical path of its own — the round's tracer is plan 05-44 Task 2, and this
expands the instrument out from it.
</objective>

<measured_diagnosis>
Read out of the shipped source during planning.

- The drain: `await sidecar.waitForEvent((e) => e.type === "proposal_created", PROPOSAL_DEADLINE_MS,
  ...)` then `for (const event of sidecar.eventsOfType("proposal_created")) { runOps(...
  "apply-proposal-created" ...) }` then `runOps(... "list-pending" ...)` — one pass, no re-scan, no
  second wait.
- `sidecar.eventsOfType(type)` returns `this.events.filter(...)` — a fresh array over the live
  buffer every call, so re-scanning is free and needs no new harness API. `sidecar.eventCursor()`
  returns `this.events.length`, which is the watermark a re-drain should track against.
- `sidecar.waitForEvent` scans already-received events FIRST, so a second wait after the first
  returns instantly on an already-seen event. A re-drain must therefore be watermark-driven, not
  built out of repeated `waitForEvent` calls.
- The accept/reject/amend block (`:6443-6510`) is entered only `if (taskProposalId)` and the amend
  path only `if (criterionProposalId)`. In live run `01M3ENQMC3E4M2HP7014MA84PX` both were null, so
  the entire block was skipped and `epics`/`tasks`/`acceptance_criteria` stayed at 0 — which is why
  SHAPE-02 reported "no subtree was accepted" and SHAPE-03/04 reported "not enough proposals to
  exercise all three verbs". The block itself is correct; it was never reached.
- The advance-call-site self-test (`:1992-2015`) builds its pattern from parts at runtime, scopes
  the scan to the live body by finding the file's only column-zero `runScript(` call, and asserts
  the count is 1. It also asserts `driveChallengeConversation`'s own body never names the op.
- The replay body's advance call site (`:5902`) is ONE site, executed once per non-default scenario.
- `fake-authoring-claude.mjs`'s own header states it never opens a socket, never imports the MCP
  SDK, and never touches the network or filesystem. It emits stream-json only. A replay scenario can
  therefore prove ordering, capture and the readings computed from the event stream — and cannot
  prove that a row reaches the board. That leg is owned by `--board-read-check` (plan 05-44 Task 2)
  and by the Rust tests.
- `assertAllHeldRequestsAnswered(sidecar)` is called once today, right after the driver returns.
</measured_diagnosis>
