<objective>
**As a** solo developer running a fleet of agents, **I want to** shape a new epic by being
challenged rather than interviewed, **so that** I walk away with structured board items instead of
a document.

This is the phase's **tracer**: the thinnest end-to-end path through every layer the phase will
touch, wired for keeps. One authoring session starts from the board with no epic in existence, the
agent proposes exactly one task through a tool, the proposal appears beside the live feed, and
accepting it puts a real task on the board. Every other capability in this phase expands out from
that proven path.

It is production-quality, not a prototype. The schema it lands is the full D-80/D-81/D-83/D-84
shape, not a subset — the staging table accepts all three verbs and all four target types on day
one, because a schema is one shape and re-cutting a CHECK constraint is a second table rebuild.
What the tracer *exercises* is deliberately one path: `verb = 'create'`, `target_type = 'task'`,
one accept.

Purpose: prove the architecture end-to-end on the phase's first commit, so an architectural
dead-end costs one plan rather than ten.
Output: two migrations, the staging and session domain modules, the `agent_runs` generalisation and
its call-site audit, one MCP write tool on the existing server, the proposal tray, and the
`authoring_run_start` / `authoring_proposal_accept` command pair.

<assumption_delta_decision>
## Assumption delta — a run's subject lost its monopoly

**Signal:** `pluralization`. Until this phase `agent_runs` had exactly one kind of subject — a task,
`NOT NULL`. D-84 introduces a second (an epic being shaped) and, for a brand-new epic, a third case
with no subject at all yet.

**The noun that is now primary:** *the run's subject*. Not "the run's task".

**Decision: `promote`.** `agent_runs` is generalised to *an agent session with an optional subject*.
`task_id` is demoted to one variant of that subject rather than the field every consumer reads to
learn what a run is about. Concretely:

- `AgentRun.task_id` becomes `Option<String>` and a nullable `epic_id` joins it.
- A single accessor — `domain::agent_run::run_subject` returning
  `RunSubject::Task(id) | RunSubject::Epic(id) | RunSubject::Unbound` — becomes the one read path for
  "what is this run about". Every call site that currently reads `.task_id` to answer that question
  moves onto it.
- The schema carries `CHECK (NOT (task_id IS NOT NULL AND epic_id IS NOT NULL))`, so a run can never
  claim two subjects.

The rejected alternative was *add-alongside*: keep `task_id NOT NULL` and put authoring sessions in
their own table. `05-CONTEXT.md` D-84 already rejects it on cost grounds ("implement all of Phase 3
twice"); the identity argument is the second reason — a second table would leave two nouns
competing for "a run", and every fleet view, reconciler and cost rollup would have to learn both.

**Companion invariant test (adopted, Task 1):** `packages/core/tests/authoring_tracer.rs` asserts
(a) the CHECK rejects a row carrying both ids, and (b) a source-scanning gate that no file under
`packages/core/src` or `packages/desktop/src-tauri/src` reads `agent_runs.task_id` in a SQL literal
outside `run_subject`'s own module. The test goes red the moment a later phase reintroduces the
singular assumption.
</assumption_delta_decision>
