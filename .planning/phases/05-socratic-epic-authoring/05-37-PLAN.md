this entire repository, so the adapter normalises both to `unknown` and the harness dumps them to
stderr as truncated raw JSON.

assistant messages whose content was a reasoning block — every one classified `unknown` — and one
`rate_limit_event` carrying `rateLimitType=seven_day`, `utilization=0.81`, `status=allowed_warning`
and `surpassedThreshold=0.75`, which is real operational information a supervisor product will want
and which the seam threw away. The root cause is the one the ROADMAP already names for this phase:
the adapter's event model was built from the offline fixtures, and the offline fixtures contain
neither shape.

fact, and the instrument should not be reconstructing or discarding it. The fence lifted in round 7
stays lifted.

same pass rather than left to become a ninth round: `05-REVIEW.md` WR-02 (the wire's
`is_api_error_message` silently drops an explicit `false`, unlike its sibling introduced in the same
commit) and WR-03 (a stdout line that parses as JSON `null` crashes the sidecar for the whole fleet).

Purpose: the next live run must model what the backend actually says, and must not lose the
evidence needed to model whatever it says next.
Output: two modelled events, a real frozen capture that cannot drift or grow invented fields, two
review warnings closed, and a durable full-fidelity capture replacing a 200-character stderr slice.

<measured_ground_truth>
Read this before writing any code. Every line was read directly out of the committed log and the
committed source during planning. The first item is a constraint on what this plan can honestly
claim, and skipping it produces a fixture that lies.

1. **The log's captures are TRUNCATED PREFIXES, not whole lines.** The harness writes
   `` `[uat] unrecognised sidecar event: ${(raw ?? "").slice(0, 200)}` `` — 200 characters of raw,
   then nothing. Every one of the twelve captures in
   `05-LIVE-RUN-01M3C48C-FAILED.log` is exactly 234 characters long, prefix included. The rate-limit
   capture stops mid-key at a partial key beginning `unifiedW`; each assistant capture stops
   mid-value inside the reasoning block's `signature`. A fixture frozen from this log is a prefix
   and must say so. This is Task 3's whole reason for existing.

2. **What IS complete in the rate-limit capture**, and therefore what the fixture may carry: the
   top-level `type` is `rate_limit_event`; it has one object field `rate_limit_info` whose complete,
   visible key/value pairs are `status` `allowed_warning`, `resetsAt` `1790596800`, `rateLimitType`
   `seven_day`, `utilization` `0.81`, `isUsingOverage` `false`, `surpassedThreshold` `0.75`. Every
   field the gap report asks the product to surface is present before the cut.

3. **What IS complete in an assistant reasoning capture**: `type` `assistant`; `message.model`
   `claude-opus-5`; `message.id` a `msg_`-prefixed identifier; `message.type` `message`;
   `message.role` `assistant`; `message.content[0].type` `thinking`; `message.content[0].thinking`
   the EMPTY STRING. The block also carries a `signature` whose value is cut. An empty `thinking`
   string beside a signature is the redacted/signature-carried form of reasoning — the text is not
   in the stream, and the product must not pretend it can display one.

4. **Why these reach `unknown`.** `normaliseStreamEvent`'s assistant/user branch searches content
   for a `tool_use` block, then a `tool_result` block, then a `text` block, and falls through to
   `unknown` when it finds none. A reasoning-ONLY message finds none. A message carrying a reasoning
   block FOLLOWED by a text block already normalises correctly to assistant text today — the
   find-first strategy tolerates a leading reasoning block, and this plan must not disturb that.
   `rate_limit_event` matches no top-level branch at all and reaches the final `unknown` return.

5. **Where the reasoning branch must go.** Immediately before the assistant/user branch's own
   `unknown` return, i.e. AFTER the text-block search. Placing it earlier would silently reclassify
   every `[reasoning, text]` message as reasoning and delete the agent's speech — which is the exact
   class of defect this phase has spent eight rounds on.

6. **`normaliseStreamEvent`'s first statement reads `.type` off its argument.** `JSON.parse("null")`
   returns the primitive `null` without throwing, so the `try`/`catch` around the parse in the
   `readline` handler does not protect this. Reading `.type` off `null` throws a `TypeError` inside
   a synchronous event handler, uncaught, killing the sidecar for every run it supervises, not just
   the one. This is `05-REVIEW.md` WR-03, pre-existing and unfixed.
</measured_ground_truth>

<assumption_delta_decision>
The deterministic detector flagged two `pluralization` signals against the ROADMAP's eight-round
plan history — historical prose, not a live identity-model change. Judged against THIS round's
scope, the genuine candidate is the one the checkpoint names: `thinking` and `rate_limit_event`
joining the adapter's modelled stream-event set, which today funnels everything unmatched into a
single `unknown` bucket.

**The noun that is now primary:** the adapter's *modelled wire-event set* — the `AgentEvent` union —
gains two members, and the assistant branch's content search gains a fourth block kind. Beneath
that sits a second, larger generalization the detector is really pointing at: **`unknown` is doing
two jobs.** It currently means both "a well-formed backend event this product has not modelled yet"
and "a line that is malformed, or a shape nobody can interpret". Those are different facts with
different consequences — the first is a product gap worth surfacing, the second is noise.

**Decision: `add-alongside`.** The two specific shapes are promoted OUT of `unknown` into modelled
events; `unknown` itself is not split, and remains the destination for both of its current meanings.

**Rationale:** promoting the general representation — introducing a distinct `unmodelled` event and
demoting `unknown` to the malformed case — would change a member of a union consumed by the Rust
core, the desktop renderer's suppression list and the harness's own event scan, for a distinction
no consumer branches on today. That is a larger, separately-justified change than this gap opened.

**Accepted debt, named:** `unknown` still conflates the two. **What would force a promote:** a third
well-formed-but-unmodelled shape appearing in a live capture. This round does not merely accept that
debt — Task 3 installs the instrument that makes the forcing condition DETECTABLE, by capturing every
unmodelled event in full and durably instead of truncating it to 200 characters on stderr. The next
time this happens, the evidence will be complete and the promote will be arguable on data rather
than on a prefix.

Advisory only; recorded here, not acted on beyond the above.
</assumption_delta_decision>
