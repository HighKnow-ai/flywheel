<assumption_delta_decision>
## The file-set editor goes from one to two

**Signal.** The deterministic detector fired on the literal `also` inside the ROADMAP research-flag
prose ("Also needed before planning…"). That hit is a vocabulary coincidence, not an identity-model
change, and it is reported as such. The real seam in this phase's scope is the one below.

**The noun that is now primary.** The *declared entry set* for a task — not either editor. Both the
chip editor and the textarea are views that produce the same `entries: string[]` through the same
`edit(taskId, { entries })` write; `declare_file_set_in_tx` remains the one writer and
`approve_plan` remains the one accept.

**Decision: `add-alongside`.** A-09 records that the owner has already chosen this: criterion 1
requires the hand-typed field to be "still there as the same form with no prefill", which A-09 reads
as *retained and unprefilled*, not as *the only editor*. The chip editor is therefore added beside
it rather than promoted over it.

**Accepted debt, stated.** `add-alongside` is the move that silently contradicts generalized intent,
so it is named here as debt rather than left implicit: two editors over one value means two places a
future entry-shape change (a third `FILE_SET_FORMS` value, a per-entry rationale, a glob form) must
be taught, and the textarea is the one that will be forgotten because it is the one nobody uses.

**What would force a later promote.** Any of: (1) the entry shape gains a field the textarea's
newline-separated form cannot express; (2) plan 15-04's live measurement shows the planner declares
usable sets reliably, which makes the textarea genuinely dead rather than an escape hatch; (3) a
second surface needs the same editor, at which point the chip editor becomes a component and
carrying two of them stops being cheap.

**The invariant worth encoding (adopted — it is cheap).** Both editors produce byte-identical
`entries` for the same intent. Task 2's test asserts that typing `a/b.rs\nc/` into the textarea and
adding the chips `a/b.rs` then `c/` issue the SAME `edit` payload. One assertion, and it fails the
moment the two editors drift.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer chip/textarea → `task_file_set_set` / `dispatchPlanEdit` | developer-typed and autocompleted path strings cross into the database here |
| repository working tree → `repo_tracked_paths` | `git ls-files` output is untrusted-length text handed to the renderer |
| `events` + `actors` → the provenance chip | an actor-kind read decides whether text is labelled as the planner's or the human's |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-21 | Spoofing | the "drafted by the planner" mark | high | mitigate | The mark is derived in one Rust read from the declaring event's `actor_id` joined to `actors.kind`; the renderer receives a boolean it cannot compute itself, so a human edit cannot inherit an agent's label |
