<objective>
Make the destructive-gate card answer once per human decision, and make it describe the right act.

**Phase goal (quoted verbatim from ROADMAP.md):** "Cyril can quit, crash or interrupt Flywheel at
any moment and know that no uncommitted work was destroyed and no agent is still spending his
money."

**User story (MVP framing):** **As a** developer answering a destructive-action gate, **I want to**
read a sentence that names exactly what is about to be destroyed, and have my one click count as
exactly one answer, **so that** the question I am answering is the question that was actually
asked.

Purpose. Two defects on the single most consequential card in the product:

1. `PermissionRequestRow`'s `answer()` guards on `state.answering` and nothing else. Three separate
   plans in this phase independently diagnosed this exact bug and fixed it with a `useRef`
   (`WorktreeSummary.tsx`'s `actingRef`, `RunsSection.tsx`'s `ackActingRef`), each recording in
   STATE.md that a real failing test — not the plan — found it: two synchronous clicks both observe
   the same stale React state before the first re-render flushes the `disabled` attribute. This file
   contains no `useRef` at all. It is the destructive-gate card, so a double-click here double-answers
   a destructive permission request.

   The existing test `activating Allow twice in immediate succession calls the answer spy exactly
   once` does NOT catch this: it uses `fireEvent.click`, which wraps each call in `act()` and flushes
   state between them, so the second click lands on an already-disabled button. The in-repo pattern
   that DOES reproduce it is raw `element.click()` called three times in one tick
   (`item-detail/__tests__/runs-section.test.tsx`).

2. `branchDeleteTarget` resolves "the first non-flag positional after the subcommand", which is
   correct for `git branch -D feature-x` and wrong for every push spelling of a remote deletion —
   for `git push origin --delete feature-x` it returns the REMOTE, rendering "This would delete the
   branch origin." Plan 03-14 makes `classify_push` emit `branch-deletion` for those spellings for
   the first time, so this resolver is about to become reachable with a payload it mis-parses. A
   consequence sentence naming the wrong object is worse than a generic one: it gets a destructive
   action approved against a false description.

Output: the guard, the push-aware branch-deletion resolver, and tests for both.
</objective>
