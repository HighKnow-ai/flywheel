<objective>
Reopen the deletion D-40 blocked, now that the worktree-removal path D-40 was waiting for exists
(D-44, WORK-03).

**Phase goal (quoted verbatim from ROADMAP.md):** "Cyril can quit, crash or interrupt Flywheel at
any moment and know that no uncommitted work was destroyed and no agent is still spending his
money."

Purpose: D-40 blocks the deletion of any task with agent-run history and recorded that block as
"cheap to revisit once Phase 3 adds a worktree-removal path". Plan 03-01 added that path, so the
refusal becomes the actionable sentence D-40 intended: *remove this task's worktree first, then
delete*. One guard, one order of operations, and no new destructive combination — because D-43
forbids removing a dirty tree, a task can never be deleted out from under uncommitted work.

03-CONTEXT.md explicitly leaves **what the deletion does to the `triggers` / `agent_runs` /
`permission_requests` rows** to planning, and 03-RESEARCH.md's open question 3 confirms it has no
precedent in Phase 1 or 2. It is a data-lifecycle decision that destroys rows, so it opens with a
blocking decision checkpoint rather than being decided silently in an action body.
Output: `delete_task`'s new guard and whichever disposition the checkpoint settles.
</objective>

  <context>
    The schema makes this a genuinely constrained choice, not an open field.
    `triggers.target_task_id`, `agent_runs.task_id` and `permission_requests.task_id` are all
    `NOT NULL REFERENCES tasks(id)` with SQLite's default `NO ACTION`, and `foreign_keys = ON`.
    So "leave them pointing at a deleted task" is not expressible, and "orphan them by nulling the
    column" is not expressible either without a migration.

    Crucially, the **append-only `events` log is untouched by any option**: `events.task_id` is a
    plain nullable column with no foreign key, so the full chronological record of what the agent
    did — every `agent_run.started`, every permission decision, every status change — survives the
    task row's deletion regardless. The non-repudiable record lives in `events`; `agent_runs` is a
    mutable projection over it.

    Also relevant: the durable session transcripts live at `<app-data>/sessions/<agent-run-id>.jsonl`
    (D-34) and are not database rows at all. Whichever option is chosen, state explicitly whether
    those files are deleted too or left on disk.

    **The planner recommends Option A**, on the reading that D-44's wording is a decision already
    made about whether deletion succeeds, that the event log preserves the history the core value is
    actually about, and that Option C's blast radius across Phase 1's query layer is out of
    proportion to the question. Under Option A the session transcript files should be LEFT ON DISK:
    they are named by run id, are referenced by no surviving row, and deleting user-inspectable
    transcripts as a side effect of deleting a board item is the kind of silent destruction this
    phase exists to refuse.
  </context>
