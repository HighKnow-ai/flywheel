  <behavior>
    - Invoked with a worktree path, a branch name and a marker string, the harness writes a file inside the worktree, stages it and commits it, exiting 0 on success.
    - Every git invocation it makes resolves through the shim directory named in its own `PATH`, not through the system git directly — verified by the harness printing the resolved path of the `git` it actually used.
    - On a commit failure it exits non-zero and prints git's own stderr, so the driving test can report which of the concurrent attempts failed and why.
    - It prints one machine-readable summary line carrying the branch, the resulting commit hash (or empty on failure), and the exit status, so the test parses one shape rather than scraping prose.
    - It performs no worktree creation, no worktree removal and no prune — its whole job is the commit, because that is the contention window criterion 4 is about.
  </behavior>
  <action>
Register `[[bin]] name = "commit_stress_harness"` with `path = "tests/bin/commit_stress_harness.rs"`
in `packages/core/Cargo.toml`, immediately after the existing `crash_harness` entry. A `[[bin]]`
entry is required — a file under `tests/bin/` is not compiled without one, and `CARGO_BIN_EXE_…` is
how the driving test will locate it.

Write `packages/core/tests/bin/commit_stress_harness.rs` taking three positional arguments: the
absolute worktree path, the branch name, and a marker string used both as the file's content and as
the commit message. Its steps, in order: write `<worktree>/stress-<marker>.txt`; run
`git -C <worktree> add <file>`; run `git -C <worktree> commit -m <marker>`; run
`git -C <worktree> rev-parse HEAD` to capture the resulting hash.

Every one of those invocations must go through the shim. The harness does NOT call
`flywheel_core::git::git_at` — that is the supervisor's own path and no agent ever takes it. It
constructs `std::process::Command::new("git")` and relies on the `PATH` its parent gave it, which is
how a real agent's own `git commit` resolves. Before its first invocation it runs
`git --version` and also resolves and prints the absolute path of the `git` it will actually use (by
walking its own `PATH` entries and reporting the first match), so the driving test can assert the
shim — and not the system binary — is what ran.

Print exactly one summary line on stdout in a fixed, parseable shape carrying the branch, the commit
hash and the exit status; print git's own stderr verbatim on stderr when a step fails. Exit non-zero
with the failing step's own status.

Add a header doc comment naming what this binary is for, that it is spawned N times concurrently by
`lock_contention.rs`, and — explicitly — that it must never create, remove or prune a worktree,
because doing so would conflate the worktree-creation contention window (D-52's territory) with the
commit-time one (D-51's).

    - Setup creates one repository and ten worktrees on ten branches, sequentially, and asserts all ten exist BEFORE any commit is attempted — the setup is explicitly not part of the measured window.
    - Ten harness processes are spawned as close to simultaneously as the runtime allows and all ten are awaited; the test asserts all ten exited 0.
    - After the run, the repository shows ten distinct commits, one per branch, each carrying its own marker — asserted by reading each branch's tip commit message, not by counting objects.
    - After the run, `git worktree list` still reports all ten worktrees plus the main one; none was removed, pruned or auto-cleaned.
    - Each child's reported resolved `git` path is inside the shim directory, not the system binary path — if even one child bypassed the shim, the test fails naming that child.
    - The test reports the total observed collision count across all children, and passes whether that count is zero or non-zero — a zero-collision run is a valid outcome on a fast machine, and the number is recorded as evidence rather than asserted as a threshold.
    - Running the same ten-commit scenario WITHOUT the shim on `PATH` is exercised as a companion case whose only assertion is that it completes; its observed outcome (all ten landed, or some failed) is printed as the comparison evidence ROADMAP's research flag asked for.
  </behavior>
  <action>
Write `packages/core/tests/lock_contention.rs`.

Build the fixture in a `tempfile::tempdir`: initialise one real git repository with an initial
commit, set `FLYWHEEL_WORKTREE_ROOT` under the temp dir behind the same process-wide mutex
`stop_lifecycle.rs` uses, then create ten worktrees on ten branches **sequentially**, asserting each
exists before moving on. Sequential setup is the point: RESEARCH.md's Pitfall 2 is explicit that a
harness which creates worktrees and commits in the same tight parallel loop is conflating D-52's
contention window with D-51's, and would validate the stagger while claiming to validate the retry.

Install the shim once via `shim::install_for_run` and build the child environment from
`shim::shim_env_for_run`, so each child's `PATH` begins with the shim directory and carries
`FLYWHEEL_REAL_GIT`. Spawn ten `commit_stress_harness` children, each with its own worktree, branch
and marker, using `std::process::Command::spawn` in a loop and collecting the handles BEFORE waiting
on any of them — spawn-all-then-wait-all, never spawn-and-wait per child, which would serialise the
very concurrency under test.

Assertions, in the order they matter:
1. All ten children exited 0. On failure, print each failing child's stderr so the run is
   diagnosable rather than merely red.
2. For each branch, read its tip commit message and assert it equals that child's marker. Ten
   distinct markers, ten branches — this is what "keeps every commit" means, and counting commits
   would pass even if two children raced onto the same branch.
3. `git worktree list` output contains all ten worktree paths. This is the second half of
   `#55724`'s failure — a lock collision that got "fixed" by an auto-cleanup which deleted the
   worktree — and it is the assertion that makes the test about data loss rather than about exit
   codes.
4. Every child's reported resolved `git` path starts with the shim directory.
5. Print, do not assert, the summed collision count.

Give the whole test a generous but bounded deadline derived from `RETRY_MAX_ATTEMPTS` and
`RETRY_BASE_MS` rather than a magic number, and state in a comment that it is derived, so a later
change to the curve does not silently make this test flaky.

Add the companion no-shim case as a separate `#[test]` that runs the same ten children with an
ordinary `PATH`, asserts only that the run completes, and prints how many of the ten landed. Mark it
clearly in its own doc comment as *evidence gathering, not a guarantee* — its outcome is
machine-dependent and it must never be the thing that turns the suite red.
  </action>
