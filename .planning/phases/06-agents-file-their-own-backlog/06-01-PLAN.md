<objective>
**As a** developer supervising agents, **I want to** have a running agent file what it learns
straight onto my board as a proposal, **so that** the finding survives the session that found it
without becoming work I never agreed to.

This is the phase's tracer: the thinnest path that touches every layer Phase 6 will modify —
the agent's tool surface, the sidecar's argv and hook wiring, the staging schema, the Rust core's
write transaction, and the triage lane that already exists on the board. One `propose_item` call
from an ordinary task-execution run stages one `pending` row carrying its rationale and its
turn pointer, that row appears in the shipped project-scoped triage lane, and the shipped
`authoring_proposal_accept` command turns it into a real task. Nothing else in the phase is built
until that path is proven.

Purpose: prove the channel end to end before expanding it, and clear the one blocker
(`06-RESEARCH.md` Pitfall 1) that would otherwise make the tracer fail for a reason unrelated to
what it tests.
Output: migration 0015, the `propose_item` MCP tool, the execution-run hook fix, the provenance
columns, and the first tests that could have caught any of it.
</objective>

  <context>
    SQLite cannot `ALTER` a `CHECK` constraint, so D-97 (`target_type` += `issue`) and D-102

    against a table that by then holds real staged and decided rows, and the column set is also
    published to `query::authoring`'s read surface, to `ProposalDto`, and to the `propose_item`
    tool contract the model is told about.

    This checkpoint exists because the *bundling* is the door, not the individual decisions —
    once 0015 ships, the vocabulary and the column set are what every later migration must rebuild
    around.
  </context>

### Flagged Planner Assumptions

- **PROP-01, probe category `unclassified`.** The probe could not classify an edge for "a running
  agent can propose new tasks, issues and epics through a board tool interface exposed to it", so
  no acceptance criterion is auto-derived for it and none is invented here. The planner's own
  assumption, stated for the record and NOT treated as verified: the only agent-facing surface
  PROP-01 needs is `propose_item` on the existing `flywheel-permissions` MCP server, reachable from
  an ordinary execution run, and "exposed to it" is satisfied by the `--allowedTools`
  pre-approval — not by any additional discovery, listing or documentation surface. If a reviewer
  reads PROP-01 as also requiring the agent to be able to *read back* what it proposed, that is
  not planned in this phase and must be raised before verification.
