<objective>
**As a** developer, **I want to** be told when an agent hit its proposal limit instead of quietly
losing what it found, **so that** a chatty run costs me one notice rather than either forty queue
rows or a silent gap in what the agent learned.

PROP-05 is explicit that hitting the limit is surfaced rather than silently dropped, and the ROADMAP
note is explicit that backlog spam is how trust in an agent-authored backlog collapses. D-109 fixes
the number at 10 and refuses to make it configurable; D-110 puts the check inside the write
transaction where it cannot be raced; D-111 makes the refusal loud and points the agent at
`report_summary`'s `remains` field so nothing it knew is actually lost; D-112 tells the human through
an append-only event whose display is re-derived, never stored twice.

This plan also closes D-108 — the duplicate candidate 06-04 now stores reaches the agent in the tool
result, which is what takes pressure off this very limit.

Purpose: make the limit a real limit and the refusal a real message, and prove the second of this
phase's three prohibitions (nothing an agent proposed is silently discarded).
Output: the in-transaction count, the refusal path, the event and its re-derived read, and the two
values the tool call now resolves with.
</objective>
