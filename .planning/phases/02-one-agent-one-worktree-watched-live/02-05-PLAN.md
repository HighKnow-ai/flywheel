<objective>
Expansion slice: the agent pauses on a permission request and stays paused until a human answers.

Purpose: this is ROADMAP success criterion 3 and requirement AGNT-06, and it is the mechanism that
makes unattended running safe. The blocking is structural rather than watched-for: Claude Code calls
out to an MCP tool the sidecar hosts, and that tool call simply does not resolve until a decision
exists. D-38 adds the project-scoped allow-always rule that keeps prompt fatigue from killing
unattended running, without letting a rule earned on a scratch repository go live on a production
one.

Output: migration `0004`, the two permission domain modules, the MCP permission server, the answer
command, and the core→sidecar relay.

Boundary note: the card, the blocked row indicator and the project-rail count are plan 02-06. This
plan builds the mechanism and its database state, and leaves the surfaces to the plan that owns
them.
</objective>

## Flagged assumption carried into this plan

**RESEARCH.md assumption A2 is unresolved by documentation.** The `--permission-prompt-tool`
mechanism's flags and its wait-for-the-server-to-connect behaviour are documented; whether an
*individual* tool call can be held open indefinitely is not — the documented 30-second `MCP_TIMEOUT`
governs server **connection**, and the fetched docs do not say whether a per-call timeout also
applies. Task 2 measures this empirically and records the finding. The design is defensive either
way: a timeout must never become an auto-deny, because a silently auto-denied request would
contradict D-37's "visible until answered" intent exactly where it matters most.

Create `packages/sidecar/src/mcp-permission-server.ts`. It starts an MCP server over the stdio
transport exposing exactly one tool, named by an exported `PERMISSION_TOOL_NAME` constant so the
adapter and the server can never disagree about it. The tool's handler:

  1. Assigns the call a request id and emits a `permission_request` event upstream, carrying the run
     id, the tool name and the tool's input payload.
  2. Registers the call's resolver in a map keyed by request id, and returns a promise it does not

  3. Settles only when `resolvePermission(requestId, decision)` is invoked from the sidecar's stdio

settles the promise. Every allow-always lookup happens in the Rust core, which owns the

the board never shows as an event is the exact failure mode this avoids).

rather than letting the backend discover a configuration file from inside the worktree it is editing

one that gates its permissions. Keep the builder pure so the flags stay assertable without spawning.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `claude` process → MCP permission server | The agent asks for authority; the request payload is attacker-influenceable content the user will read before deciding. |
| worktree filesystem → backend configuration discovery | A worktree may contain its own tool-server configuration, which must never be able to substitute itself for the permission gate. |
| renderer → Rust core | A request id and a decision string cross the IPC seam and grant real authority to a running process. |
| Rust core → sidecar | The relayed decision is the only thing that settles a held call. |
