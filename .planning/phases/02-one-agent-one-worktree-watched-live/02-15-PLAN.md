<objective>
Close gap G-02-1 (`02-UAT.md`, blocker, test 1). The dev-time sidecar stub resolved
`packages/sidecar/dist/index.js` by a fixed three-level hop from its own directory. That hop is
correct only while the file sits at `packages/desktop/src-tauri/binaries/` — and that is not where
it runs from. Tauri copies every `externalBin` next to the app executable, so
`tauri-plugin-shell` executes the copy at `target/<profile>/flywheel-sidecar`, from which three
levels up escapes the repository root entirely. Node exited 1 before reading a single request, the
sidecar process was dead before any request was sent, and the failure surfaced far from its cause
as "failed to write request to the sidecar's stdin" on the user's first Start Work.

The entrypoint half is already patched in the working tree and is verified
(`./target/debug/flywheel-sidecar </dev/null` now exits 0 where it previously exited 1). **This
plan owns committing that patch** — it is deliberately uncommitted so the commit lands on this
plan's ledger rather than on verify-work's.

Purpose: the deeper defect is that `spawn_sidecar` treated `.spawn()` returning `Ok` as proof the
sidecar was alive, which it is not — it proves only that the operating system accepted the exec.
The module's own doc comment already promises the stronger contract ("a failure to resolve or
spawn the sidecar aborts startup rather than proceeding with a half-working app"); the code did
not implement it, and the reader loop matched only `CommandEvent::Stdout`, so process termination
passed silently. Any future cause of an immediately-dying sidecar — a bad stub, a missing Node, a
crash on boot — would present identically and just as undiagnosably.

Output: a committed and hardened stub, a bounded startup readiness handshake that aborts at the
cause, a reader loop that observes process lifecycle rather than only stdout, and a test that runs
the stub the way the application runs it.
</objective>

**In `packages/desktop/src-tauri/src/sidecar.rs`:**

Declare two module-level constants beside the existing timeout constants, each with a doc comment
in the same style:
- `READINESS_REQUEST_ID: &str` — the fixed request id the handshake uses. It names no run and is
  never reused for anything else.
- `STARTUP_READINESS_TIMEOUT: std::time::Duration` — five seconds. Document why it is generous
  relative to a Node process boot yet short enough that a wedged sidecar cannot make the application
  appear to hang at launch.

Rewrite `spawn_sidecar` so the child binding is mutable and the handshake happens between `.spawn()`
and the construction of `SidecarHandle`:

1. Write one newline-terminated JSON request to the child's stdin naming `READINESS_REQUEST_ID` and
   the `ping` op, built with `serde_json::json!` exactly as `interrupt_run` and `shutdown_all_sessions`
   build theirs. A write failure returns `Err` with context saying the sidecar's stdin was not
   writable at spawn time.
2. Drive a bounded wait over the spawn receiver with `tauri::async_runtime::block_on` wrapping a
   single `tokio::time::timeout(STARTUP_READINESS_TIMEOUT, ...)` around a loop that awaits
   `rx.recv()`. Inside the loop:
   - a stdout line that parses as `SidecarStdoutLine::Ack` whose `id` equals `READINESS_REQUEST_ID`
     ends the wait successfully — regardless of the ack's `ok` field, because ANY ack carrying that
     id proves a live process reading stdin and writing its own protocol on stdout, which is the
     whole question being asked;
   - a stderr chunk is appended to a bounded local tail (cap the retained text at 4 KiB; once the cap
     is reached, stop appending rather than growing) so the eventual error message can carry the
     process's own explanation;
   - process termination ends the wait with an error naming the exit status and the retained stderr
     tail;
   - a process-level error ends the wait with an error carrying that message;
   - the receiver closing with nothing left ends the wait with an error saying the sidecar's event
     stream closed before it answered;
   - any other event is skipped. Include a catch-all arm so a future `CommandEvent` variant cannot
     break the build.
3. On the timeout elapsing, return `Err` naming `STARTUP_READINESS_TIMEOUT` and the retained stderr
   tail.
4. On success, construct `SidecarHandle` exactly as today and move `rx` into the reader task
   unchanged.

In the reader task, keep the existing `CommandEvent::Stdout` arm byte-for-byte — its persist-then-emit
ordering, its ack arm, its malformed-line arm and the permission-request dispatch are all out of
scope here. Add three sibling arms: a stderr arm that writes the sidecar's own stderr to
`eprintln!` as a developer breadcrumb; a termination arm that writes a breadcrumb naming the exit
status and then ends the loop, because nothing further can arrive on a receiver whose process is
gone; and a process-error arm that writes a breadcrumb. None of these three may panic, and none may
emit to the renderer — surfacing a mid-session sidecar death to the user is explicitly out of this
plan's scope (see `## Adjacent Open Items`).

Update the module doc comment: it already claims that failing to resolve or spawn the sidecar aborts
startup. State the now-true, stronger contract — that `spawn_sidecar` returns only after the sidecar
has answered on its own protocol, that an immediately-exiting sidecar aborts startup naming its exit
status and its stderr, and that the wait is bounded. Reference gap `G-02-1` by id.
