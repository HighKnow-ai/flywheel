<objective>
Expansion slice: the board itself answers the question "what needs me?".

Purpose: D-37's whole argument is that an agent can sit blocked and silent for an hour, and that
this is the failure mode that sends people back to cycling terminal tabs. Surfacing the request only
in the session feed does not fix it. This plan builds the per-project half of the mechanism
FLEET-02 generalises across projects in Phase 10, so it is the real mechanism rather than a
placeholder — and it makes ROADMAP success criterion 3's "the user answers it from the board"
literally true.

Output: the permission-request card as one component with two mount points, the blocked row pill,
and the project-rail count.

Boundary note: OS notifications are deliberately not built here — FLEET-04 owns them in Phase 10
(D-37). Do not add one.
</objective>

Create `packages/desktop/src/session/PermissionRequestCard.tsx` as one component with a `variant`
prop taking `feed` (inline in the session transcript) or `compact` (inside the 480px item detail
panel). Reusing one component across two mount points is the pattern `ParentPicker` already
established in this codebase; do not build a second card.

Visual treatment per 02-UI-SPEC.md: a 4px left border stripe in `--blocked-text-rack`, the
`ShieldAlert` glyph resolved from the published `blocked-indicator` mark rather than named directly,
the tool name in the Heading role, the label `{tool_name} wants to:` and the input payload rendered
read-only in the Mono utility beneath it. A bare tool name is not enough information to approve or
deny responsibly, so the payload is not optional.

Three actions, deliberately unequal: `Allow` as an accent-filled button at chrome radius, `Deny` as
an outline button at the same visual weight so denying is never harder to reach than allowing, and
`Allow this tool for this project from now on` as a smaller text-style tertiary action beneath both
— visually secondary on purpose, so a blanket rule is a considered action rather than the reflexive
click (D-38's prompt-fatigue reasoning, inverted: reduce fatigue with a rule the user chose, not
with a rule they clicked past).

**Not dismissible.** The card owns no local key handler, no `onKeyDown` prop and no dismissable-layer
wrapper — plan 02-03 deliberately left it out of the shared dismissal ladder, which is the only
place that decision lives. Closing the card without answering would hide the blocked state rather
than resolve it, and the agent would still be blocked. Record in a comment that this is an
intentional deviation from every other inline and overlay pattern in the product, referring to the
ladder by name rather than restating the key.

Keys come from the shared binding table's `permission-card` region — subscribe to the three
`answer-permission-*` action ids rather than comparing keys locally.

Resolve E3's open considerations concretely rather than leaving them to run time:
  - *loading*: on activation, disable all three actions immediately and keep them disabled until the
    mutation settles; a second activation while disabled invokes nothing. That is what prevents a
    double answer at the UI layer, complementing the core's guarded once-only write.
  - *error*: on rejection, keep the card mounted, re-enable the actions, and render the error text
    inline beneath them. The card must never vanish on a failed answer — a vanished card would read
    as "answered" while the agent is still blocked.
  - *overflow* and *long-text*: in the `compact` variant, the payload block has a fixed maximum
    height with its own internal scroll, and the tool name truncates with an ellipsis rather than
    widening the panel.
  - *zero-one-many*: render every pending request for the run, stacked in creation order, each
    independently answerable — never only the first, which would hide authority the agent is waiting
    on.
  - *partial*: the card reads its pending set from the shared query and re-reads on the pushed
    delta, so answering elsewhere clears it here; this is exercised in Task 2.
