Close gap G-02-4 (`02-UAT.md`, blocker, test 1) — the most important of the four.

`close_agent_run` — the one function that writes a terminal status, an end time, a cost and token
counts — has no production caller. The terminal event's own type string does not appear anywhere in
`packages/core/src` or `packages/desktop/src-tauri/src` at all. The sidecar emits the terminal
event, the Rust reader loop persists it to the session log and forwards it to the renderer, and no
consumer ever maps it onto the run's row. Only the explicit Stop path writes a terminal status,
which is exactly why the one run the user stopped is the only one that has one. Two runs sat at
`running` long after their sessions ended; the second one's own persisted log contains its terminal
event.

This is the Core Value failing, not a cosmetic gap. `PROJECT.md`: "Every unit of agent work is
anchored to a structured board item with real acceptance criteria." A run that ends on its own stays
`running` on the board forever, with no end time, no cost and no token counts — and finishing without
being manually stopped is the normal case, not the edge case.

The function itself is correct and thoroughly unit-tested. Nothing tested that anything CALLS it. A
unit test of a function production never invokes passes perfectly while the product is broken — the
precise failure mode UAT exists to catch, and the reason this plan's test must drive a real session
rather than call the function again.

**A correction the executor must not get wrong.** The UAT's `impact` note says "this module's own
docstring says that transition is close_agent_run's responsibility", referring to moving a task out

out of `in_progress`, and that is `close_agent_run`'s explicit NON-behavior — and decision **D-29**
locks it: "Starting a session moves the task to In Progress; nothing ever moves it out." The
docstring and D-29 are authoritative. Do not implement the note.

Purpose: the missing piece is a call site, so the work is to create one that cannot silently
disappear again — and to decide the token-accounting question the gap leaves open, with the header
made to reflect that decision rather than showing an em-dash forever.
Output: usage carried on the terminal event, a terminal applier owning the idempotency decision, a
reader-loop call site, a real end-to-end test, and a structural gate on the call site itself.

## Ground truth captured during planning

Run live against the installed CLI (claude 2.1.236) with the patched argv, in a scratch repository,
during this planning session. These are measured facts, not assumptions:

- The terminal `result` line carries `subtype`, `is_error`, `session_id`, `total_cost_usd` and a
  `usage` object.
- That `usage` object carries `input_tokens`, `cache_creation_input_tokens`,
  `cache_read_input_tokens` and `output_tokens`, among other fields.
- For a single trivial turn the observed values were `input_tokens` **2**,
  `cache_creation_input_tokens` **17080**, `cache_read_input_tokens` **16016**, `output_tokens`
  **4**, and a total cost of roughly **$0.18**.
- Each `assistant` line also carries a per-turn `usage` object of the same shape.

## Token accounting decision (closing the gap's second `missing` item)

**Token counts are written ONCE, from the terminal result event — not accumulated from per-message
usage.** Three reasons, in order of weight:

1. The backend's own `result.usage` is the authoritative session total. Accumulating per-turn usage
   would add `cache_read_input_tokens` again on every turn, overcounting a multi-turn session by
   whatever its cached prefix costs — which, per the measurement above, is most of it.
2. `close_agent_run`'s existing signature already takes per-run totals and its columns are per-run
   totals. Accumulation would need a second, separate running-total write path for no gain.
3. The backend emits a usage block on its result line unconditionally, so nothing is lost by waiting.

**`tokens_in` is the sum of `input_tokens`, `cache_creation_input_tokens` and
`cache_read_input_tokens`; `tokens_out` is `output_tokens`.** Recording `input_tokens` alone would
store a number that is right about the uncached prefix and wrong about the session: it read 2 for a
turn that actually consumed roughly 33,000 input tokens. A header reading "2 in" for that session
would be re-reported as a defect at the next UAT, correctly.

**The header's consequence, made explicit.** `StatusStrip` in `SessionSurface.tsx` already scans the
loaded log entries newest-to-oldest for a top-level numeric field named `inputTokens`, among two
aliases. Carrying the figures as TOP-LEVEL fields on the result event therefore makes the header flip
from an em-dash to the real numbers the moment the result line arrives, with no renderer change at
all. The counters legitimately read an em-dash for the duration of a running session, because no
session-total figure exists until the backend reports one — that is correct behaviour under this
decision, not residue of the defect, and the doc comment in that file which currently says the
sidecar "does not yet stream live token counts" must be updated to say so.
