# Accepting a Proposal applies its effect in the deciding transaction

Decided in [Propose spec changes as ghost fields and decide them inline](https://github.com/HighKnow-ai/flywheel/issues/125) (PR [#140](https://github.com/HighKnow-ai/flywheel/pull/140)), and extended by [#129](https://github.com/HighKnow-ai/flywheel/issues/129) (PR [#142](https://github.com/HighKnow-ai/flywheel/pull/142)), [#133](https://github.com/HighKnow-ai/flywheel/issues/133) (PR [#146](https://github.com/HighKnow-ai/flywheel/pull/146)) and [#127](https://github.com/HighKnow-ai/flywheel/issues/127) (PR [#147](https://github.com/HighKnow-ai/flywheel/pull/147)). Accepting a Proposal changes the board in the same transaction that records the decision. `proposal::decide_in_tx` checks the actor is human, marks the Proposal accepted and calls `proposal_apply::apply_in_tx`, which runs the record's own writer (`update_epic_in_tx`, `create_story_in_tx`, `move_milestone_in_tx`, `set_epic_state_in_tx` and so on). The decision and its effect commit together or not at all. If the writer refuses (a Done Milestone is frozen, a Milestone still holds an open Epic), the Proposal stays pending. **Amend** is Cyril's edit and his acceptance in one act: the edited payload is applied and stored on the row, and the `proposal.accepted` event keeps the agent's `original` beside the `applied` one.

We rejected keeping acceptance as a recorded decision with the effect applied by a later step, which is what M2 shipped: accepting recorded the decision and changed nothing. A separate apply step can fail after the decision is recorded and leave an accepted Proposal whose change never happened. It also lets a direct edit land between decision and effect. We also rejected Amend as "reject, then file a corrected copy", which would lose the link between what the agent proposed and what Cyril accepted. That link is what a later packet and the timeline need.

## Consequences

- `apply_in_tx` is called only from inside `decide_in_tx` and decides nothing. Who may accept is `proposal.rs`'s question, and what accepting does is `proposal_apply.rs`'s. A new Proposal kind gets its effect by adding a branch there and a check in `validate_payload`. Until then it is recorded only (`Applied::RecordedOnly`).
- Shaping is made of Proposals, so a shaping session is exempt from the soft cap of 3 open Proposals per session (`OPEN_PROPOSALS_PER_SESSION`, spec §5). Story sessions keep the cap. A Stage cannot close while any of its Proposals is undecided, which bounds them instead.
- Deciding a Proposal is always its own act. "Accept all recommended" (`round::accept_all_recommended`) answers a Round's ordinary questions only. It never decides a Proposal and leaves an ADR question open, so the Stage stays open until that question is answered Yes or No.
- An ADR answered Yes in a Round goes through the same path, never around it: the answer's transaction files a `create adr` Proposal as Cyril and accepts it (`file_proposal_in_tx`, then `decide_in_tx`), and `round_questions.adr_proposal_id` points at it. The Epic's Story packets carry it as full text until the repo holds the file, as ADR-0002 requires.
- A decision that settles a roadmap Round closes the Round and releases its held `round_wait` call (ADR-0006) inside the same transaction.
